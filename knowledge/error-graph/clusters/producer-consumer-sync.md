# Cluster: プロデューサー/コンシューマー同期漏れ

> Layer 1 Community Summary — 関連ノードの蒸留サマリー。
> スキーマ・カタログ・enum・キー一覧など「定義を作る側」と「参照する側」が
> 分かれている構造を拡張する時にロードする。

**対象タグ**: `producer-consumer-sync`, `schema-sync`, `skill-sync`, `renderer`, `catalog`

---

## 蒸留ルール（Distilled Rules）

### R1: 定義の拡張は「消費側の全数同期」まで1コミット
カタログ・スキーマ・frontmatterフィールド・enum・キー一覧を拡張したら、
それを参照する**全消費側**（レンダラー・SKILL.md・skill_refs・バリデーション）を
grepで洗い出し、同一コミット内で結線または明示的に対象外と記録する。
- 消費側が2箇所以上ある定義は特に危険 — 「1箇所直して満足」が定型の事故
- 例1: kintone_shotカタログ拡張 → writer SKILL.mdキー一覧未同期 → 偽UI図解量産
  （[[../nodes/catalog-key-added-without-consumer-sync.md]]）
- 例2: heroImage追加 → /articles/ のみ結線・トップページ未結線 → 本番プレースホルダ露出
  （[[../nodes/frontmatter-field-not-wired-into-all-renderers.md]]）
- 例3: reviewer checklist が ng_phrases.md を引用 → reviewer manifest の skill_refs に未同梱 →
  LLM が「手元にないため部分照合」と自己申告して静かに劣化（rc=0・NGなし）
  （[[../nodes/checklist-references-file-not-in-skill-refs.md]]）
  → **プロンプト/checklist で `xxx.md` を引用したら、そのエージェントの manifest に同梱されているか grep で確認する**

### R1f: 次の工程が読む場所に書くまでが1つの作業 — print は受け渡しではない
上流ツールが生んだ値を **標準出力に出して終わり**にし、DB など下流の入口条件へ書く作業を
人（またはAI）の手順に委ねると、静かに抜ける。
- 例: BOOTH 出品ランナーが URL を print するだけで `product_ideas.booth_url` に書かず、
  告知ワーカーの `WHERE status='listed' AND booth_url IS NOT NULL` に一生入らなかった。
  **出品は成功・status も listed・ダッシュボードも「発売済み」**なので無症状だった
  （[[../nodes/published-but-never-announced-because-url-stayed-in-stdout.md]]）
- **「完了の定義」を散文で複数項目に書いたら、どれが機械でどれが人の手順かをその場で分ける**。
  人の手順として残すものには、落としたと分かる警告の口を必ず作る
- 失敗が無症状な連鎖（起きるはずだった別のことが起きないだけ）は通知できない。
  下流の入口条件を上流のツールに満たさせる

### R1b: 定義への「同期」だけでは足りない — 上流の指定は下流の能力表と契約させる
消費側一覧の同期（R1）を守っていても、**上流エージェントが自由記述で「指定」を出す構造**なら
能力外の指定が素通りする。指示を出す側（FS・企画・仕様書）にも能力表（カタログ）への参照を
必須化し、検閲側の合格条件も「理想」でなく「実行可能集合」に接地する。
- 例: researcherのFS「SS指定」が撮影カタログと無契約 → writerが物理的に満たせず →
  reviewerがFS指定を正としてfail → **改稿しても絶対に受からない記事**が5本連続破棄・
  公開64時間停止（[[../nodes/fs-demands-uncapturable-screens-deadlock.md]]）
- 兆候: 同型の差し戻しが自動再試行で2回以上解消しない＝ラウンド不足でなく契約矛盾を疑う
- テンプレの例文は契約内の実例にする（例文はエージェントが最も模倣する仕様 — 当該事故では
  テンプレ例文自体がカタログ外画面を教えていた）

### R1c: 消費側の「前提条件」が題材依存で崩れる場合を、契約と同じ強さで扱う
R1（一覧の同期）とR1b（能力表との契約）を満たしても、**その能力が「特定の要素が存在すること」を
暗黙の前提にしている**と、題材次第で間欠的に失敗する。カタログにキーがあることは、
そのキーが常に撮れることを意味しない。
- UI操作のセレクタは 候補列 → 総称セレクタ → 明示的な「構造的に不能」シグナル の3段で書く
  （候補はプローブで実測してから追加する。推測登録は外れる）
- 例: `field_settings` が単一行テキスト固定でホバー → その型を持たないアプリ（シフト表）で
  10秒Timeout → 3記事連続破棄・review.passed 40時間停止
  （[[../nodes/shot-selector-assumes-absent-field-type.md]]）
- 兆候: 「特定の記事/題材のときだけ落ちる」。他の題材では成功し続けるので壊れて見えない

### R1d: 縮退（グレース）は下流への申し送りと代替表現までがセット
上流が縮退したのに下流がそれを知らないと、下流は**別の担当を罰する**。
- 縮退したら ①構造化して記録（`grace_events`）②下流ゲートのプロンプトへ申し送り
  ③成果物には読者に意味のある代替を必ず残す（HTMLコメント等の「見えない穴」を残さない）
- 再試行ループを作る時は「差し戻し先の担当がそれを直せるか」を必ず検査する。
  原因工程と差し戻し先がズレたループは救済でなく破棄への近道
- 変換で捨てる情報（除去したマーカー等）は原文をDBへ退避してから捨てる（復元可能性）

### R1e: キーの「意味」を変えるのは、キーを追加するより同期漏れが起きやすい
カタログのキーを**追加**したら消費側の一覧を同期する、というルールは既にある。
しかし**既存キーの中身（何が撮れるか・何を返すか）を変えた**時のほうが危険。
名前が変わらないので、消費側を読んだ人（AIも人も）が「知っているキー」として素通りする。

実例: 撮影キー2つの用途を「メニューの場所」から「設定パネルの中身」へ変えたところ、
消費側の説明文は**旧用途のまま**残っていた（「フィールドの歯車→設定メニュー」「グラフタブ」）。
放置すれば書き手は旧用途のつもりでマーカーを置き続け、画像と本文が食い違う。

- **意味を変えたら、キー名で grep して *説明文* を全部読む**（存在確認では足りない）
- **同一セッションで自分が入れたルール変更の伝播も点検する。**
  同じ調査で、直前に「推奨→必須」に変えたはずのルールが、消費側ドキュメントの
  別の箇所で「推奨」のまま残っているのが見つかった（自分の直し残し）
- 変更点にはコメントで**変更日と旧用途**を残す（「戻したい時」の判断材料になる）

### R2: 「表示されていない」の一次切り分けは「データは存在するか」
プレースホルダ・空欄・画像なしを検知したら、先にデータ実在を確認する。
- データあり×表示なし ＝ コード欠陥（修正レーン・high）
- データなし ＝ コンテンツ課題（企画/design助言）
誤診すると検知済み欠陥が知見DBに沈み、人間の指摘まで直らない。

### R3: 時間軸のproducer-consumer — 収集が付ける日付と集計窓の交差を検証する
データを書く側（コレクタ）と読む側（レポート・学習）が分かれている時は、
書く側のタイムスタンプが読む側の窓に**実際に入る**ことをデータで確認するまで結線完了としない。
- 「レポート直前に収集」は収集日付=当日・窓=過去で全量窓外になる定型の罠
- 周期ジョブの二重実行ガードは**暦単位**（日/ISO週/年月）で切る。「直近N日」窓は
  週途中の初回・手動実行で定時スロットと位相ズレし、次周期まるごとスキップする
  （[[../nodes/weekly-guard-day-window-phase-skip.md]]）
- `last_at`型の増分窓の後付けは、実装前に発生済みのイベントを永久に取りこぼす
  （遡及するか「過去分は捨てる」と明示記録するかを設計時に決める）
- 観測の周期は成果物の発生周期・初速の時間スケールに合わせる（週2公開に週1観測は不整合）
- 例: note KPIが週1収集×窓外日付で、不振の検知が最大2週遅れた
  （[[../nodes/note-kpi-weekly-cadence-window-blind-spot.md]]）

### R4: 消費側の窓に供給し続ける義務 — 公平キューは「巡回目的の時刻」でソートする
コンシューマが「直近N日の観測」等の鮮度窓で読む時、プロデューサの巡回ローテは
その窓を満たし続ける責務を負う。ソートキーに**別レーンの実績時刻**（例: engage時刻）を
流用すると、条件を永遠に満たさないメンバー（engage不可アカウント等）がNULL最優先で
全枠を独占し、消費側が静かに枯れる（starvation）。
- 共有予算を複数セクションが先着順で食う設計も同型 — セクション別の床/天井を機械で切る
- 「対象0件でスキップ」の正常系ゼロはrc=0で失敗監視に乗らない。ゼロ継続を活動量異常として
  拾う経路（ops-auditor）を設計時に確認する
- 例: X観測ローテがcandidate22件に独占され、いいね/リプが8/26に完全停止
  （[[../nodes/rotation-starvation-by-unengageable-accounts.md]]）

### R3: 名前を抽象化したら、旧名をリポジトリ全体で grep して残存 0 を確認する
文字列リテラルは import で辿れないため、**依存グラフを追う発想では見つからない**。
OS 抽象化で警告文だけ `STORE_LABEL` に置換し、情報ログ・使い方・別コマンドのエラー文・コメントが
旧名（Keychain）のまま残った。型も通り例外も出ず、selftest 26 件も全部緑だった。
- **表示の正しさは実行でしか確かめられない。** 移植・抽象化の後は「実際に 1 回動かして出力を読む」を出口条件に
- 利用者に見える語は定数 1 箇所から供給する
- 詳細: [[../nodes/abstraction-left-old-name-in-user-facing-strings.md]]

### R4: 識別の単位を「経路」にしない — 同じ相手が 2 経路から来ると状態が矛盾する
同じ企業がママワークスとインディードから接触し、**2 つの返信案が別スレッドにでき、
片方だけ保留になった**。利用者には 1 人の相手なので「返信案がこない」と見えた。
- 経路は「どこへ返すか」の情報であって、**同一性の根拠ではない**
- 2 つ目の経路を足す時は、1 つ目で暗黙に「経路 = 相手」としていた箇所を洗う
- 統合は**材料（本文の保存）→ 突き合わせ → 利用 → 表示**の順。表示を先に変えると迷子になる
- 詳細: [[../nodes/same-counterpart-two-channels-two-truths.md]]

### R5: 鮮度の窓は生産側と消費側で 1 つの定数にする — 片方だけ足りても 0 件になる
消費側が「直近 N 日に観測されたもの」を要求し、生産側が「誰を観測するか」を別の理由で
決めていると、**両方とも rc=0 のまま結合結果だけが恒久的に 0 件**になる。
- 例: X の交流プールは「engage_ok=1 の台帳 × 直近 2 日の観測」の JOIN。生産側の観測
  ローテーションは公式アカウント（engage_ok=0）を無条件で先頭に置き、読み取り予算を
  食い尽くしていた。交流可の 6 件は **19 日間**一度も観測されず、プールは 12 日間空。
  「いいね0 リプ0」が毎サイクル出るだけで、理由はどこにも残らなかった
  （[[../nodes/uc-x-zero-impressions-engage-pool-starved-12-days.md]]）
- **優先枠は予算が届かなければ存在しないのと同じ。** 「A を必ず先に見る」を足す時は、
  同じコミットで「押し出される B が窓から外れたら A より先に見る」床も入れる
- 候補源の条件（`source LIKE ...`）を書いたら、**実際にデータが入っているレーンが
  その条件に合致するか**を実データで数える。同じ障害で開拓レーンは `search:` 限定のまま
  だったが、search は 6 週間前に止まり、実際に集まっていたのは `trend:` だった
- 0 件は正常ではなく調査対象。JOIN で候補を作る処理は、0 件のとき
  **左右どちらが欠けたか**をログに書いてから return する

| 状況 | 適用するルール |
|---|---|
| 生産側と消費側が「鮮度の窓」で結合する | R5: 窓を 1 定数に。押し出される側に床。0 件の理由を残す |
