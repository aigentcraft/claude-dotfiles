## ユーザーの指摘（原文）

「lineの通知がまだ随時読み違えたものがディスコードにきてる」

前日（10/03 21 時）の「なんて書いてあるかわかんないし、何でもかんでも雑多に通知している」の再発。

## 1. Plan / Context

LINE デスクトップ（742×490 の小さなウィンドウ）を背景のまま撮り、Haiku に会話一覧を
`{name, preview, unread, official, work}` で読ませる。前回の読みを `相手名 → 未読数` で保存し、
**未読が増えた名前**を新着として、`work && !official` のものを #🗂秘書 に出していた。
10/03 の直しは「仕事の連絡だけ出す」（work の判定）で、名前の読み自体には手を入れていなかった。

## 2. Do / The Error

10/04 に #🗂秘書 に出た LINE の通知 6 件が全部読み違い。

- 1 つの会話（ライバー事務所の配信）が「ライバー兼競市NeoBring」「ライバー募集内NeoBrig...」「ライバー事務所NeoBrig...」と
  **3 通りに読まれ、3 回通知**された。冒頭の文も毎回崩れていた（「主要さん。お昼ずきてて害甲阪リスト」）
- ほかに個人 1 件・店舗 1 件・配信 1 件も、それぞれ前回と違う名前として通知
- 半日で同じ十数件の会話に **29 通りの名前**が記録されていた（人名の最後の 1 字が 3 通り、店名が 3 通り、配信元が 4 通り …）
- 8 時・10 時は「仕事でない新着 9 件」、9 時・11 時は 1〜2 件。**実際の新着ではなく、読みの揺れの数**だった

## 3. Check / Root Cause

- **画像から読んだ名前（OCR の出力）を、そのまま会話を見分ける鍵にしていた。** 読みが 1 字ずれると `previous[name]` が無い
  → 未読 0 から増えた扱い → 「新着」。読み違いはランダムなので、未読が残っている会話ほど毎時「新着」になる
- 10/03 の直しは「出すかどうか」の判定（work）を足しただけで、**同じ会話かどうか**という前提を疑っていなかった。
  仕事に見える会話（ライバー事務所）は、読み違えるたびに出続けた
- 読み手が最小モデル（Haiku）で、742×490 の画面全体（右側の会話まで）を渡していた。小さい漢字ほど崩れる

## 4. Act / Prevention Strategy (Fix)

`src/core/line.ts` の「会話の台帳」（`applyReading` ほか）・`src/cli/watch.ts` の `lineCycle`・`scripts/windows/capture-line.ps1`

- **会話の台帳**（設定キー `line.roster`）: 会話ごとに「読まれた名前と回数・未読・冒頭の目印・読めた回数」を持つ
  - 近い名前（正規化した編集距離の近さ 0.6 以上。社名は「株式会社」などを外して比べる・3 字未満は完全一致だけ）は同じ会話に寄せる。
    本物（2 回以上読めた）の会話を優先して 1 対 1 で結ぶ（似た名前の別の会話が同じ一覧にあれば取り違えない）
  - どれにも寄らない名前は**1 回では知らせない**。次の巡回でも読めたら本物として扱う（崩れた読みは 1 日で捨てる）
  - 未読が 1 回だけ下がって戻った（冒頭も同じ）なら新着にしない。前回の読みにいなかった会話は、未読が前より増えた時だけ新着
  - 冒頭は 2 字組のハッシュの集合だけを残す（本文は保存しない）。「冒頭が変わった」は新しい読みが 2 回続いた時だけ（今夜の精読の候補）
  - 通知の名前は、その会話で一番多く読まれた読み
- 読み手を haiku → sonnet（`MODELS.vision`）。撮った画像を約 115 万画素まで拡大して渡す（742×490 → 1319×871）
- 本人宛ての「〇〇様」で結ばれた紐づけ（job#285）は巡回・精読とも使わない。紐づけの照合も読みの揺れを許す（job#21 の「マママワークス…」）
- 独立レビュー（code-reviewer）の指摘で直したこと: **近さで寄せる仕組みは、近い別の相手（「株式会社サンプル東京／大阪」）を取り違える**。
  台帳は完全一致を最優先に結ぶ・紐づけは一番合うものだけ（2 番手と差が無ければ結ばない）・精読の相手の重複は完全一致だけで除く。
  読み落とし扱いで新着を止めた会話と、一覧の外から未読を増やさずに戻った会話は、黙って捨てずに今夜の精読（本文の目印で確かめる）へ回す
- selftest 558 件。10/04 の実際の読み違いの並び（名前は架空に置換）を再現して固定。
  故障注入 6 種（名前の完全一致に戻す・初めて見る名前をすぐ新着にする・PATH 任せの起動に戻す・完全一致を先にしない・古い記録でも読み落とし扱い・最初の紐づけを使う）で FAIL を確認
- 残した弱点: 同じ読み違いが 2 回続くと別の会話として確定し、通知済みの未読がもう一度出うる
- 記録済みの 29 通りの読みは、新しい比べ方で 19 のまとまりに寄った（実際の会話はおよそ 14〜15 件。残りは「1 回では知らせない」側で止まる）

同じ調査で、Claude Code が 10/04 11:45 に npm 版からネイティブ版へ切り替わり、常駐からの claude 呼び出しが全部失敗していたことも見つけた
（`~/.local/bin/claude.exe` が常駐の PATH に無い）。`src/core/claude-bin.ts` で実体を探してから起動するようにした。

## 予防ルール

- **読み取り（OCR・画像の LLM）の出力を、そのまま同一性の鍵にしない。** 揺れを前提に、近い名前は同じ相手として寄せ、
  初めて見る名前は 1 回では信じない（次の読みでも現れたら本物）
- 新着の判定は「前回の読みとの差」なので、読みの誤差がそのまま新着に化ける。**差分を取る値ほど、読みの安定を先に確かめる**
- 「出すか」の判定を直しても、「何を数えているか」が間違っていれば止まらない。再発したら判定ではなく前提（鍵・単位）を疑う
- **あいまい一致は「同じものか」を決める 1 か所（1 対 1 の照合）だけで使う。** 重複除去・紐づけ・記録の引き当てに近さを持ち込むと、近い別のものを黙って落とす・取り違える
- 誤通知を止める側に倒した判定は、落とした分を後で確かめる経路（夜の精読）につないでおく。黙って捨てると取りこぼしが見えなくなる
