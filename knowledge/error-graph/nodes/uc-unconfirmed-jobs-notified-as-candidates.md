## ユーザーの指摘（原文）

「メールでまだ、私が受ける要件であるフルリモート、PC作業のみ、業務委託の3点を満たさない案件の通知が来たり、案件の内容をサイトで確認せずに通知を出している。各サイトの中の企業からのスカウトもフィルタリングせずに通知してきている。私の要件に合わないものは無視で良くて、対応がそもそも不要。」

## 1. Plan / Context

案件・誘いが Discord に出る経路は 3 つ: ①案件探索（検索結果とママワークスのスカウト箱を Sonnet で判定し 📝応募前 に投稿）
②サイト内のスカウトの新着（同じ判定）③メール（Haiku で関係あり/なしを分け、関係ありはメール担当が本文を読んで通知）。
受託条件（criteria.md）の最後に「条件が本文から読み取れない場合は unclear（判断保留）とし、unfit にはしない」とあり、
2026-09-17 の方針「unclear は落とさない（書いていないだけで条件に合う案件はある）」で保留も候補として出していた。

## 2. Do / The Error（2026-10-05 朝）

- 8 時の案件探索で 📝応募前 に投稿した 7 件が**全部 unclear**（fit は 0 件）。「フルリモート表記だが『港区勤務』とあり出社要否が矛盾」
  「Zoom での応募者面接対応が業務にある」のように、合わないと読めるものまで候補として出ていた
- サイト内のスカウトは判断保留を「条件を読み取れないスカウトが N 件」とまとめて知らせていた。判定はスカウトの本文だけで、求人ページを見ていなかった
- 9 時のメールで、エンゲージの「企業からオファーが届きました（スタッフサービス・エンジニアリング）」を条件を見ずに通知し、
  後から秘書に「オファー詳細を確認する」を頼んでいた（エンゲージは Chrome でログインが切れていて見られなかった）
- 受託条件では「業務委託」が**歓迎条件**に入っているだけで、絶対条件ではなかった

## 3. Check / Root Cause

- **「確かめられない」を「候補」に倒していた。** 取りこぼしを恐れて保留を出す方針が、本人には「条件を見ずに知らせている」に見える。
  本人の要件は「合うと分かったものだけ」で、保留を確かめるのは本人の仕事ではない
- メール担当の手順は「最後に必ず通知する」で、新しい誘い（スカウト・オファー・求人の紹介）を受託条件で確かめる段が無かった
- 本人の核の条件（フルリモート・PC 作業のみ・業務委託）が受託条件の書き方と一致していなかった（業務委託が歓迎条件のまま）

## 4. Act / Prevention Strategy (Fix)

- `criteria.md` に「核の条件（3 点）」を新設し、業務委託を絶対条件に。核の 3 点が確かめられなければ unfit（知らせない）。
  それ以外の絶対条件は、抵触の記載がある時だけ unfit（書かれていないだけなら問題にしない）
- 判定の指示（`core/screen.ts`）: fit は核の 3 点を確かめられた時だけ。unclear は使わない
- 案件探索は fit だけを出す。判定できないスカウトのまとめ通知をやめる（ログに件数だけ）
- メール担当: 新しい誘いは求人ページで核の 3 点を確かめた時だけ知らせる。確かめられなければ知らせず、やることも作らない
- 出ていた保留 8 件を `rescreen --unclear` で判定し直した（fit 2・応募しない 6）。selftest 570 件

## 予防ルール

- **知らせる側の条件は「合うと確かめた」で定義する。** 確かめられないものは知らせない（ログに件数だけ）。
  取りこぼしが心配なら、確かめる手段（求人ページを開く）を足す。保留を本人に回さない
- 本人が要件を言葉で言い直したら、受託条件のファイルと突き合わせて、ずれ（絶対条件か歓迎条件か）を直す
- 「最後に必ず通知する」型の手順には、「知らせない」で終われる出口を同じ重さで書く
