## 1. Plan / Context
「セッション失効から無人で自己回復できるか」を実測する必要があった。
待っていては失効しないので、**劣化条件を意図的に作る**方針で `logout` を実行した。

## 2. Do / The Error
`logout` 直後の再ログインから、サイトが応答しなくなった。

```
初回 status: 429
title      : Security Check - Indeed.com
body       : 追加認証が必要です / このリクエストのRay ID：…
```

30 秒観察しても自動では解けない。以後すべてのアクセスが 429 になった。

## 3. Check / Root Cause

**① `logout` が消したのはセッションだけではなかった**

`logout` はプロファイルディレクトリごと削除する。そこには Cookie が丸ごと入っており、
**Cloudflare の通過実績（clearance）も一緒に消えた**。Cookie を持たない新規訪問者として
再訪した結果、チャレンジが提示された。

**② 作った劣化条件が、本番で起きる状態より過酷だった**

実運用で起きるのは「プロファイルは在るがセッションが失効している」状態であって、
「プロファイルが存在しない」状態ではない。**初回セットアップの条件で
回復テストをしていた**ことになる。テスト対象を取り違えていた。

**③ 短時間の試行回数が多すぎた**

同じ日に調査・ログイン・OTP 送信を何度も繰り返しており、429 はその累積でもある。

## 4. Act / Fix & Prevention

- レート制限は**突破しない**。要求を止めて時間を置く。
  チャレンジを解く実装はボット検知の回避であり、作らない。
- 初回のチャレンジ通過は有人で 1 度行う（「人間の介在は初回のみ」の設計と整合する）。
- 通常運用で `logout` を使わない。セッション失効からの回復はプロファイルを保ったまま行う。

### 予防ルール

1. **劣化条件は「本番で実際に起きる状態」に合わせて作る。**
   壊しすぎると、本番で起きない失敗を追いかけることになる。
   ここでは「セッション失効」を試すべきところで「初回訪問」を作ってしまった。
2. **破壊的な検証の前に「それが何を一緒に消すか」を数える。**
   セッション削除はサイト側から見た同一性（通過実績・信頼）も消す。
3. **外部サービスを相手にした試行には回数の意識を持つ。**
   ローカルのテストと違い、繰り返し自体が相手側の状態を変える。
