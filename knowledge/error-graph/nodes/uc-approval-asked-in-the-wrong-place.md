## 指摘（原文）
> ディスコードでの承認通知の依頼内容が、ディスコード上での承認ではなく、クロードコードで承認するような
> 依頼になっている。承認、非承認のボタンをつけて、非承認の場合には内容を返信できるようにして。

## 何が起きていたか
承認依頼は Discord に届く。文面は「2. Claude Code のチャットで『承認』か『差し戻し：理由』を送る」。
**通知が届く場所と、操作する場所が違った。** 同じ誘導がリマインドにもあり、半年近くそのままだった。
返信での承認は 2026-09-03 に実装済みだったのに、依頼文はそれを案内せず Claude Code を指していた
（作った経路を、依頼文が知らない）。

## なぜ気づけなかったか
- 通知の**文面**を検査するテストが 1 つも無かった（grep で 0 件）。ゲートは「送ったか」を見て「何と書いたか」を見ない
- 書いた本人（私）は Claude Code の中にいるので、「チャットで承認」が自然に読めてしまう。
  読み手は Discord の通知だけを見ている

## 修正（2026-09-21）
- 送信: Bot が embed + ボタン 3 つ（承認 / 差し戻す（理由を書く）/ 保留）で出す。
  **Webhook ではボタンを送れない**（application 所有でない Webhook の interactive component は Discord が無視する・実測）
- 受信: 既存の無料枠 Pages Functions に受け口を新設（Ed25519 署名検証 → D1 に押下を 1 行 → その場でメッセージを書き換え）。
  差し戻しはモーダルで理由を受け取り、同じ行に入れる
- 取り込み: D1 を透かしで読み、家の DB を正として反映。取り込みを 30 分おきの独立タスクにした
  （従来は記事生産 run の最後だけ = 最大 4 時間・時間切れの run では未到達）
- 落とし方: 受け口が未登録なら**ボタンを貼らない**（押しても「This interaction failed」しか出ないため）。
  `GET /applications/@me` の実データで確かめ、貼れない時は「このメッセージに返信」に落とす

## 予防ルール
- **「あなたのやること」は、その通知が届く場所で完結する手順にする。** 別のアプリを開かせない
- 通知の文面は検査の対象にする（「承認」を含む行に別アプリの名前が出ていないこと）
- 作った経路（返信での承認）は、**依頼文からも到達できる**ようにする。経路の実装と案内はセットで直す
- 押せる UI を出す前に「押したら本当に効くか」を機械で確かめる。確かめられないなら出さない

## これは 2 回目（知識はあったのに新しいプロジェクトへ運ばれなかった）
2026-08-07 に参照プロジェクトで**同じ指摘**を受けている（[[uc-approval-flow-not-operable-from-notification]]
「ディスコードから承認・差し戻しの操作ができないと意味ない」）。そのノードの「修正」欄には、今回作ったものと
**同じ構成が既に書かれていた** — Discord Interactions（ボタン + 差し戻し理由モーダル）→ Cloudflare の受け口 →
D1 → パイプラインが回収。

weevee は参照プロジェクトのアーキテクチャ移植で始まったのに、承認 UX だけ 45 日前の結論を持って来ず、
「通知は届く／操作は Claude Code」で作り直してしまった。指摘は再発ではなく**未移植**。

予防（上のルールに追加）:
- **新しいプロジェクトで同じ部位を作る時は、着手前に error-graph をその部位名で引く**
  （承認 / 通知 / 公開 / 課金 …）。参照プロジェクトの「修正」欄がそのまま設計になることがある
- 移植したのは**コード**（workers/shared）だけで、**決定**（UX の完成条件）は運ばれない。
  移植のチェックリストに「その部位で過去に受けた指摘」を入れる
