## 1. Plan / Context
運用監査のDiscord報告（review.passed 64時間停止）の根本原因を特定し、ユーザーへ報告した。
初回報告は ①報告の正体 ②3エージェントの契約対比表（researcher/writer/reviewerの各ルールと問題）
③時系列の発火条件 ④修正案4択 — 正確だが情報密度が高く、記号（Q05/Q09・FS・カタログ13キー）を
前提知識なしに使った。

## 2. Do / The Error（ユーザー指摘 2026-09-01）
- 「つまりどういうこと？わかりにくい」

## 3. Check / Root Cause
1. **正確性を優先して圧縮を怠った** — 調査直後の脳内構造（表・コード参照・チェックID）を
   そのまま出力した。読者は調査を追体験していない
2. 固有記号（Q05/Q09等）は書き手には便利なポインタだが、読み手には解読タスク
3. 「何が起きているか」の直観像（=詰み構造）より先に部品の説明を並べた

## 4. Act / Prevention Strategy (Fix)
言い直しで通じた構成（再現テンプレ）:
1. **一言の直観像から始める**: 「絶対に合格できない試験を毎日受けては落ち続けている状態」
2. **登場人物の流れを番号付き4ステップで**（調査担当→ライター→検閲→振り出し）
3. **責任の所在を明言**: 「誰かのバグではなく、ルール同士が矛盾している」
4. 修正方針は2点まで・専門語はここで初出させる
- 予防ルール: **インシデント報告の第一声は「たとえ+流れ」。表・チェックID・ファイルパスは
  質問されてから**（技術的裏付けは持っているが先に出さない）。報告の宛先は開発者ではなく
  意思決定者と想定する
