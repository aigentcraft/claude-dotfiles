# 「今日を終端とするN日窓」は、供給側の確定遅延がNに近いと空振りし続ける

## 症状
kpi_snapshotsのGSCデータが8/11の1日分きり。8/14〜16の3runは毎回 `gsc(0行)` で
エラーなし正常終了。GSC API直叩きでは8/10〜14のデータが実在 = 収集側の構造問題。

## 根本原因
- GSCの確定データ（dataState=final・APIの既定）は**2〜3日遅れ**で公開される
- 収集窓は「今日を終端とする3日窓」`[today-2, today]` — 遅延が3日に達すると
  **窓内の確定日が0日**になり、正常応答の空集合が返る（エラーが出ない沈黙系）
- 窓は毎日1日ずつ進むため、取りこぼした日付は**窓が通り過ぎた時点で恒久欠損**になる
  （8/12・8/13は誰も再収集しない状態だった）
- 8/13の初回runだけ偶然、遅延2日・窓端1日が重なり43行取れた — **初回成功が
  「結線は正しい」という誤った安心を与え、その後の0行を「まだデータが無いだけ」に見せた**

## 修正（2026-08-16・実走検証済み）
GSC専用の収集窓を7日に拡大（`GSC_LOOKBACK_DAYS=7`・GA4は速報が当日から出るため3日のまま）。
UPSERT設計なので窓の重複は自己修復として働く。実走で8/10〜14の5日分143行が即復旧。

## 予防ルール（一般化）
- **供給側にデータ確定遅延があるAPIの収集窓は「遅延の最大値+安全余裕」で設計する**。
  窓終端を今日にするなら、窓長は遅延最大値の2倍が目安（GSC: 遅延3日→窓7日）。
- 「0行・エラーなし」は正常と区別できない沈黙系。**収集系には「最終取込日からの経過」
  監視が要る**（X無活動ウォッチドッグ [[instant-approval-path-skips-sns-fanout.md]] と同型 —
  失敗の検知でなく活動の検知）。
- 初回の成功は結線の証明にならない。タイミング依存の系は「翌日以降も増えているか」までが検証。
