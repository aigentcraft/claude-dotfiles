## 1. Plan / Context
pullie週次レポートの `_kpi_totals()` は kpi_snapshots を source×metric でGROUP BYし
既定でSUM（GA4/GSCの日次フロー値には正しい）。note課の03_metricsは
noteアクセス状況ページの「週ビュー」= **直近7日累計のゲージ値** を毎日保存する。

## 2. Do / The Error
2026-08-31週次レポートが「noteはビュー139→518・スキ23→73と急伸」と報告。
実際は 53+60+66+66+85+92+96=518 — 累計ゲージを7日分SUMした水増し値。
真の週実績は窓内最終日の96ビュー/スキ11。レポート内の別節（note課実績）は
最新値を正しく採っており、同一レポート内で518と96が併記される矛盾として表面化。
人間質問「ビューが500いくつと90いくつで差があるのか、なんでなのかよくわかんない」。

## 3. Check / Root Cause
1. **指標の型（フロー vs ゲージ）を区別しない汎用集計**にゲージ系ソースを合流させた。
   siteソースには「スナップショットだからMAX」の分岐が既にあったのに、
   note追加時に同じ分岐を与えなかった（既存の例外分岐は新ソース追加時のチェックリスト）
2. analystは矛盾に気づき「ロジックが異なり要継続確認」と書いたが、
   誰も調査タスクにせず人間が先に気づいた（違和感の放置）

## 4. Act / Prevention Rule
- **kpi_snapshotsに新ソースを足す時は各metricがフロー（日次発生量→SUM）か
  ゲージ（累計/残高/現在値→窓内最新値）かを宣言し、集計側の分岐に必ず登録する**
- ゲージ値のSUMは「日数×水増し」になる。逆にフローのMAX/最新値は過少報告になる
- LLMレポートが「数値が一致しない・要継続確認」と書いたら、それは調査タスク。
  次回レポートまで放置せず即日で照合する（人間より先に気づく）
- 同族: weekly-guard-day-window-phase-skip（窓・暦の扱い）/ utc-timestamps-render-as-last-night
