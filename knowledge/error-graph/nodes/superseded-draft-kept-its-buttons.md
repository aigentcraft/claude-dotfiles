## 1. Plan / Context
応募文の生成方針を変えたため、既存 11 件を作り直した。
古い案と取り違えないよう、作り直し時に「上の古い案は使わないでください」と注意書きも出した。

## 2. Do / The Error
投稿を見ると、**古い案にも承認ボタンが残っていた**。

```
**応募文案**                    [承認して応募する/修正指示]  ← 古い
♻️ 方針を変えたため作り直しました
**応募文案**                    [承認して応募する/修正指示]  ← 新しい
```

## 3. Check / Root Cause
実際に送信されるのは DB の `apply_draft`（最新版）なので、**誤送信は起きない**。
だが利用者は古い文面を読んで承認できる。つまり

  **読んだ内容 ≠ 送られる内容**

注意書きで「使わないでください」と書いたのは、**押せる状態のまま言葉で止めようとした**
ということ。押せてしまうなら、いずれ押される。不可逆操作でこれは許容できない。

プロジェクトの方針書には既に
「ボタンは状態に応じて変える。同じ状態に留まる操作のボタンを残さない」
と書いてあり、その原則に自分で違反していた。

## 4. Act / Fix & Prevention
新しい案を出す前に、古い案のメッセージからコンポーネントを外す
（`retireApplyDraftButtons`）。整合コマンド `repair` にも
「ボタンが残ってよいのは最新の 1 件だけ」という規則として入れ、
後からでも揃えられるようにした。

### 予防ルール

1. **言葉で止めない。押せなくする。**
   「使わないでください」は、押せる状態を放置した言い訳にしかならない。
2. **同じ操作のボタンが 2 つ以上見える状態を作らない。**
   作り直し・再通知・再掲示を実装したら、必ず「古いほうをどうするか」を同時に決める。
3. **「実害が無いから良い」で済ませない。**
   送信内容が正しくても、利用者が違うものを読んで判断しているなら設計は壊れている。
