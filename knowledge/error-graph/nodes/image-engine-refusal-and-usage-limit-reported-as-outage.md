## 症状（Symptom）
Discord の運用チャンネルに「情報図が全件フォールバックしています（GPT Image が 1 枚も応答していません）」
（warn）が届いた。調べると GPT Image は動いていた（直後の 15:03 に画像の加工が成功）。同じ日に別の問題が 3 つ重なっていた:
1. **誤報**（記事 31）: 画面の加工 2 枚を、GPT が**返事をしたうえで断った**（「このスクショには Pro の記載が
   写っていないので印を付けられない」）。それが「1 枚も応答していない」と数えられた
2. **利用上限を呼び続けた**（記事 30）: ChatGPT（Plus）の画像生成が上限に達し、1 回目で分かっていたのに
   残りの節で 12 回呼んだ。通知は「フォールバック多発」で、上限であることも解除時刻も書かれていなかった
3. **代用の描画まで落ちた**（記事 30）: 上限のあとの HTML 描画が 6 枚とも `expected string or bytes-like object,
   got 'NoneType'` で落ち、節が画像なしになった
4. **断られても図の担当に戻らない**: 担当は、スクショに写っていない文字に印を付けるよう頼んでいた

## 根本原因（Root Cause）
- 1: 実経路（`plan["_source"]`）を記録していたのは情報図と冒頭画像だけで、**画面の加工は記録していなかった**。
  2026-09-11 に「応答したが検査で不採用」を分けた修正は、種別を列挙して直したため画面の加工が漏れていた
- 1・2: 画像エンジン（imagegen）は失敗を `None` でしか返さず、**失敗の種類（上限・断った・故障）と GPT の返事**が
  呼び出し側に届かなかった
- 3: node が出力する保存先パス（日本語を含む）を、UTF-8 モードでない Python が cp932 で読み、読み取りスレッドが
  `UnicodeDecodeError` で死んで `stdout` が None になった。2026-08-09 の windows-subprocess-cp932-decode-crash の**再発**
  （当時の修正は「その時に落ちた箇所」だけで、`tools/diagram_render.py` が漏れていた）
- 4: 断った理由を担当に渡す経路が無く、最初の企画でも「スクショを開いて確かめる」は任意だった

## 修正（Fix）
- `imagegen.classify_failure` / `last_failure()`（usage_limit / declined / timeout / error と GPT の返事）
- 上限は `logs/imagegen_limit.json` に解除時刻を残し、**解除まで codex を呼ばない**（別工程・X 課にも効く）
- 05: 全種別で `note_failure(plan)` が実経路と理由を記録。上限は経路 `limited`・通知は
  「利用上限に達しました（12:26 に解除）」、断ったときは GPT の返事を通知に載せる
- 断られた画面の加工は、返事を材料にして図の担当に 1 回だけ選び直させる（同じスクショ・同じ指示は不採用）。
  最初の企画でも「スクショを Read で開き、印を付ける箇所が写っていることを確かめる」を必須に
- 文字列で受け取る子プロセス呼び出しは全数に `errors="replace"`（10 箇所）。**`tests/test_subprocess_text_decoding.py`
  が ast で全ファイルを検査**し、付け忘れを赤にする
- テスト 27 件（すべて今日の実ログの文言で、旧コードで赤を確認してから採用）

## 予防ルール（Prevention）
1. **「使えない」と通知してよいのは、相手が応答しなかった時だけ。** 失敗は少なくとも
   「上限（待てば戻る）／断った（相手は動いている・理由がある）／故障」に分け、理由と相手の返事を運ぶ
2. **外部の上限を 1 度検出したら、解除時刻まで呼ばない**。状態は工程をまたいで共有する
3. 同じ型の修正は**種別・ファイルを列挙して閉じない**。全数を機械で検査するテストで閉じる
   （この日の 2 件はどちらも「前回の列挙から漏れた 1 本」だった）
4. 担当が別の担当に頼んで断られたら、断った理由を頼んだ側に返す経路を作る
