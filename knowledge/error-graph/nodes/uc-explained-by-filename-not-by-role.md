## ユーザー指摘（原文）
「「静かな不発」（.ps1 と publish-batch.sh）はどちらも同じ型でした。とか言われても何のことか全くわからん。
名前で言われてもいちいち全部覚えてないし、機能と役割で言ってくれないとわかんない。」

## 何をやったか
セッションの締めで、その日直した 2 件を **ファイル名**（`.ps1` / `publish-batch.sh`）と
**自分が名付けた呼び名**（「静かな不発」）だけで指し、「同じ型だから横断チェックしよう」と提案した。
ユーザーには「何の話か」が伝わらない。

同じ日に自分でも書いていたはずのこと（[[feedback-with-no-address-never-arrives]] の
「文言もゲートと同一にする — 違う言葉で言うと本人は同じ指摘だと気づけない」）を、
人間相手にはやっていなかった。

## 根本原因
**書いた本人にとっての識別子（パス・スラッグ・自作の造語）を、そのまま読み手の識別子として使った。**
- ファイル名は「どこを直したか」であって「何が動かなかったか」ではない
- ユーザーはリポジトリの全ファイルを記憶していない。覚えているのは**機能**（記事が公開される／X に投稿される）
- 自分が付けた呼び名（「静かな不発」）は、その場で定義しない限り相手の語彙に存在しない

## 修正（言い換えの型）
報告は **「何が動かなかったか（機能）→ どんな影響が出たか → どこを直したか（ファイル名はここで初めて）」** の順にする。

- 悪い: 「`.ps1` と `publish-batch.sh` が静かな不発でした」
- 良い: 「**毎晩 X に投稿を出す定時処理**と、**承認した記事をサイトに公開する処理**の 2 つが、
  どちらも『中身のプログラムを一度も起動していないのに正常終了と報告する』状態でした。
  前者は 7 日間 1 件も投稿しておらず、後者は今日 7 本公開したつもりで 0 本でした」

## 予防ルール
0. **この規則は「人が読むすべての出力」に適用する。** 自分の返答だけでなく、
   Discord 通知・ログ行・承認依頼・日次サマリー・エラーメッセージを含む。
   散文で書くと適用範囲を自分で狭めてしまうので、**対応表と関数にしてコードから通す**
   （weevee では `workers/shared/naming.py`）。
1. **固有名詞を出す前に、その主語を機能で一度言う。** ファイル名・スラッグ・記事 ID・テーブル名・
   自作の呼び名は、**役割を説明した後の補足**として括弧に入れる。
2. **自分で名付けた概念は、使うたびに 1 行で定義するか、使わない。** 造語は自分の思考の道具であって、
   相手との共通語彙ではない。
3. **「同じ型です」と言うときは、型の中身を具体で 1 文にする。** 抽象ラベルだけの類型化は情報量ゼロ。
4. 影響は**ユーザーの言葉**（記事が公開されない／投稿が出ない／お金にならない）で書く。
   内部指標（rc=0・ゲート不合格・run_id）は根拠として後ろに置く。

## 再発（2026-09-12）— 予防ルールが**人間向けの文章にしか効いていなかった**

ユーザー指摘（原文）:
  「ディスコードへの通知がファイル名ばっかりで何を言ってるのか意味がわからん。
    役割とか機能に言い換えてくれないとなんの参考にもならないよ」

1 回目の翌日、私は**新しい通知を作り、そこに識別子を並べた**:
  `**started_but_never_finished**: 未完了 run 2 件` / `・img-fill-2.log: rc=127` /
  `・writer: 11%（60/570）` / `・tips: 3.7 日沈黙`
ノードには「固有名詞を出す前に主語を機能で一度言う」と書いてあったのに、
**私はそれを自分の返答にだけ適用し、機械が出力する文字列には適用しなかった**。

なぜ効かなかったか: 予防ルールを「私の話し方」の問題として書いたから。
実際は**人が読むすべての出力**（Discord 通知・ログ・承認依頼・日次サマリー）が対象だった。
散文のルールは適用範囲を自分で狭められる。コードにすれば狭められない。

処置: `workers/shared/naming.py`（役・投稿レーン・定時処理の対応表と純関数）を単一ソースにし、
人が読む行は必ずここを通す。テストで「識別子だけの行を出さない」を固定した。

## 3回目（2026-09-13）— 2回目の処置が**別プロジェクトの通知文にしか入っていなかった**

ユーザー指摘（原文）:
  「何度かこの回答のファイル名、英語で出してくるのやめてくれって言ってるけど
    一向にやめてくれないんだよね。機能と役割で答えるように再発防止して。」

pullie の稼働状況をまとめた返答で、地の文にこう書いた:
  「shadow は `app_graphs` / `field_settings` の2キー限定」
  「`ORG_STATUS.md §6「未構築」が固定文`（gen_org_status.py:191 のハードコード）」
  「`05_generate_images.py` の後ろでしか走らない」

2回目のときに私はこう結論していた —
「散文のルールは適用範囲を自分で狭められる。コードにすれば狭められない」。
そして対応表を作った。**ただし weevee の Discord 通知文にだけ。**
このノードを読むべき当の私の返答には、ゲートが1つも無かった。

つまり2回目の教訓の適用範囲すら、また自分で狭めていた。
「コードにする」と書いたとき、私は**機械が出す文字列**のことしか考えておらず、
**自分が書く文章**を対象に入れていなかった。3回目はそこで起きた。

### なぜ「読んで守る」が3回とも失敗したか
このノードは 77 個ある UC ノードの1つで、セッション開始時に索引ごしに存在を知るだけ。
**報告を書く瞬間には何も起きない。** 知識の所在と、適用の瞬間が繋がっていない。

### 処置（pullie 側）
`.claude/hooks/plain_language_report.py` を **Stop フック**として登録した。
最終返答の地の文に拡張子つきファイル名が裸で出ていたら **exit 2 で差し戻す**。
許す形は3つだけ:
  1. 役割のあとの括弧 … 記事の画像を作る処理（05_generate_images.py）
  2. Markdownリンクのリンク先（リンク文が役割）
  3. コードブロックの中（実行してもらうコマンド）

実走検証: 今日の私の悪い文2つで exit 2・言い換えた形で exit 0・
安全弁 `PLAIN_LANGUAGE_HOOK=0` と壊れた入力で fail open を確認。

**この処置自体が横展開の対象**（Quick Rule #9）。weevee にも同じ Stop フックを置く。

ユーザー指摘（原文）:「人間待ちの詳細を教えて。Q3とか言われても分からんからそういう表現やめて。」

私は「記事 7 は score 70 だが Q03・Q11 不合格、Q11 は前回合格からの回帰」と書いた。

2 回の再発で「役・レーン・定時処理」の対応表は作ったが、**検閲項目・ゲート名・イベント名は入れていなかった**。
対応表を「思いついた分類」で作ると、次の分類で同じ穴が開く。

根本: 返答を書く前に「英数字の記号が裸で出ていないか」を自分で確認する。通知だけでなく私の返答にも機械的に適用する。

## 再発 4 回目（2026-09-19）— Discord 通知にファイル名だけ

ユーザー指摘（原文）:「ディスコードへの通知なんだけど、ファイル名だけで言われても何もわからん。役割と機能で説明させて。」

3 回目までの処置は **対応表（naming.py）を作り「人が読む行は必ず通す」と決めた**だけで、通す場所を機械で強制していなかった。
Discord への送信は 27 ファイル・51 箇所から直接 `notify.discord()` を呼んでおり、そのどれかが `daily/02a_replenish_topics` や
`keyword-research-20260919.log`、`tools/keyword_research.py` のような識別子をそのまま流した（私自身が当日書いた Jina の警告文にも
`tools/keyword_research.py` が入っていた）。**書く側 51 箇所の注意に頼る限り、次の 1 箇所で必ず再発する。**

処置（今回は出口で機械的に）:
- `naming.WORKER_LABELS`: 日次/X/週次/案件/L4 の全ワーカー・tools/*.py・scheduler の全スクリプトに役割名を付ける
- `naming.humanize(text)`: ワーカー id（`daily/02a_…`）・スクリプトのパス（`tools/x.py` / `.ps1` / `.sh`）・ログ名（`x-20260919.log`）を
  「役割（識別子）」に書き換える。すでに「（識別子）」の形なら二重にしない。URL は触らない
- `notify.discord` / `discord_embed` の**出口**で title / description / fields すべてに humanize を掛ける — 送り手が何を書いても届く前に直る
- 役割名の無い識別子は送りつつ `execution_logs` に warn（未登録を放置しない）
- **テスト**: リポジトリの全スクリプトに役割名があることを検査 — 役割名を書かずにワーカーを足すと CI が赤

根本: 「必ず通す」というルールは、通さなくても動く場所に書いても守られない。**通らないと動かない場所（出口）に置く。**

### 4 回目の追記（2026-09-20）— 出口に通しても「表に無い種類」が素通りした
翌日「まだなんかディスコードに届いてるけど」。Bot で #ops の実物を読むと、残っていたのはファイル名ではなく
**検査名**（started_but_never_finished）・**工程番号の並び**（02c/03/04/05）・**設定名**（ARTICLES_MAX_MINUTES）・
**材料ファイル名**（candidates.md）・**番号だけの参照**（記事 27・signal 109）だった。出口の仕組みは正しく、表の種類が 1 つしか無かった。
→ 種類ごとの表を足し、番号には題名を添える。**表は想像で作らず、届いた実物を読んでから作る。**

### 4 回目の処置の続き（2026-09-20 夜）— 作業ログをそのまま送る設計をやめる
人間「日誌の書式も運営者向けに変えて」。出口で識別子を直しても、担当の**作業ログをそのまま送る**限り運営者には読めない。
実演担当の日報と X課 活動報告を「機械の封筒（台帳から数えた事実）+ 担当が運営者に向けて書く短い節」に変え、作業ログは保存だけにした。
節が無ければ黙って旧書式で流さず、警告つきで冒頭を代わりに載せる。**人が読むものは、人に向けて書かれた節だけを送る。**
