## 1. Plan / Context
2026-08-14、X自発リプの403規制対応（[[x-api-reply-restriction-403]]）で送信経路を三分岐した際、
引用ポスト（quote_tweet_id）は「非リプライなので規制対象外（"Non-replies unchanged"）」と判断し
API（xmcp）経路のまま 07_amplify を新設した。dry-runでツールのパラメータ実在は確認したが、
**実弾送信は「次の朝runで初排出」として未検証のままリリースした**。

## 2. Do / The Error
8/14〜8/21の8日間、毎朝 x-strategist が引用を企画（LLMコスト消費）→ C系ゲート通過 →
createPosts が `403 Forbidden - {'detail': 'You can only ...'}` → `except`で
`db.log(warn, str(e)[:150])` → continue → **rc=0で正常終了**。x.quoted=0件。
- 既存の障害監視（同一ステップ2run連続失敗→🚨介入要求）は**rc≠0のステップ失敗だけを見る**ため、
  握り潰されたwarnは8日間一度も昇格しなかった
- `str(e)[:150]` の切り詰めでエラー本文が "You can only" で切れ、ログからも規制起因と読めなかった
- 発覚は人間の指摘「業界記事への引用リプライとか、情報の発信がない」

## 3. Check / Root Cause
1. **引用も規制対象だった**: 2026-02規制はreplyだけでなくquote_tweet_idにも及ぶ（実弾8日間全滅が証拠）。
   「対象外」の根拠は当時の推測で、実弾検証前提の機能を検証せずレーンとして数えていた
2. **失敗の握り潰し**: 「1件の失敗で他候補を止めない」ためのwarn+continueが、「全件失敗」でも
   rc=0を返す設計になっており、失敗監視の入口（ステップrc）に信号が届かない
3. エラーログの過剰な切り詰め（150字）が診断情報を破壊した

## 4. Act / Prevention Strategy (Fix)
**Fix:**
- x_browser.quote_post 新設（本文末尾に元ポストURL→Xが引用カード化する標準挙動。
  セレクタは実証済みのreplyと同一ペア）。07_amplifyの送信をブラウザUI経路へ切替、実弾1件成功
- 「送るべき通過案があるのに全件送信失敗」なら rc=1 で終了 → 既存の2run連続失敗監視に自然結線
- エラーログは300字に拡大。候補も強シグナル+高エンゲージ観測の二本立てに拡張

**Prevention:**
1. **部分失敗の許容（warn+continue）を入れる時は、「全件失敗」の集約判定を必ずペアで入れる** —
   1件の失敗は握り潰してよいが、全滅はrc≠0で監視系に渡す。グレース設計には下流ゲートをペアにする
   原則（2026-08-15）と同型: 例外の飲み込みには全滅検知をペアにする
2. **「◯◯は規制対象外」というプラットフォーム仕様の推測は、実弾1件が通るまでレーン完成と数えない**。
   ⏳未検証マークを付けたまま日次運転に入れるなら、初回実弾の成否を能動的に確認するタスクを残す
3. 例外メッセージの切り詰めは最低300字（外部APIのエラー本文は後半に本質があることが多い）
