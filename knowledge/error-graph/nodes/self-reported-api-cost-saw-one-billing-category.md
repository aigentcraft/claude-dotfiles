## 症状

人間「XのAPIの消費が激しい」。X デベロッパーコンソールの直近30日は **$43.87**（1日 約$1.46）。
システム自身の推定（観測イベントの `est_cost_usd`）は 1日 約$0.93 で、**実額の6割強しか見えていなかった**。
コンソールの内訳を開くまで、誰も次の3つを知らなかった:

1. **ユーザー読み取り $12.17（28%）**: 相手リサーチの `searchUsers`（1人 $0.010）。毎回同じ上位20人が返り、
   **30日で新規候補は1件**。成果ほぼゼロの支出が2番目に大きかった
2. **URL入り投稿 $6.80（16%）**: 2026-04-20 から URL を含む投稿は1件 **$0.20**（通常 $0.015 の13倍）。
   記事・製品・note の告知は全部 URL 入り。料金改定は誰も読み直していなかった
3. いいね $2.40（1回 $0.015）— 推定に入っていなかった

## 原因

- 推定は「最初に費用がかかった処理（投稿の読み取り）」を作った時に書かれ、**後から足したレーン
  （ユーザー検索・いいね・URL入り投稿）は推定に入らなかった**。費用の計算が処理ごとにばらばらで、
  全体を数える場所が無い
- 料金表は一度読んだきり。提供元が単価を変えても、自分の推定は古い単価のまま正しそうに見える
- **支出と成果が別々に記録されていた**。ユーザー検索の成果（新規候補の数）は毎回ログに「相手候補0」と
  出ていたが、その横に費用が無いので「無駄な支出」として目に入らなかった

## 対処（2026-10-03）

- 提供元のコンソール（使用状況ページ）で、**課金カテゴリ別の件数**を実測してから手を付けた
  （件数 × 単価の和が総額 $43.87 と一致することを確かめた）
- 高い順にブラウザ経路へ移した（他人の投稿の読み取り・ユーザー検索・投稿・いいね）。自分の投稿の数字は
  「自分のデータ」枠（1件 $0.001）に切り替え。代替が起きたら記録してその日1回だけ知らせる
- 観測イベントに経路（browser / api / api_fallback）と経路別の推定費用を残す

## 予防ルール

- **R-COST1: 費用の自己申告は、課金の全カテゴリを数える。** レーンを足したら同じコミットで推定に入れる。
  推定が実額より小さい間は、推定があることがかえって「把握している」錯覚を生む
- **R-COST2: 月に1回は提供元の請求・使用状況画面と突き合わせる。** 料金改定は自分のコードには届かない。
  ズレが出たら、まずカテゴリ別の件数を見る（総額だけでは原因が分からない）
- **R-COST3: 支出は成果と並べて記録する。** 「検索した・0件」を毎回ログに出していても、費用が横に
  無ければ無駄は見えない。成果ゼロが続く支出は、まず止めるか頻度を落とす候補
