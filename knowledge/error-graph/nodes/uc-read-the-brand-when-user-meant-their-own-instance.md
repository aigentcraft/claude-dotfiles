## ユーザーの指摘（原文）

1 回目: 「クロニウムじゃなくて普通にクローム使えばいいじゃん」
2 回目: 「**また同じ画面に戻された、ふつうのクロームじゃなかったよ。クロードインクロームにしなよ。**」

## 何が起きていたか

自動化用のブラウザ（Playwright が起動する Chromium）が Cloudflare の関門で止まっていた。
利用者は直前に「**普段の Chrome では入れた**」と報告していた。

「普通にクローム」を **Chrome という製品（ブランド版のバイナリ）** と読み、
Playwright の `channel: 'chrome'` で本物の Chrome を起動した。
中身は Chrome でも、別プロファイル・自動操作下なので、結果は同じく関門でループした。

利用者が指していたのは **「普段自分が使っている、あの Chrome」（個体）** だった。
関門を通れた理由はブランドではなく「人が普段使っている個体であること」なので、
製品名だけ替えても効かないのは、事前に分かったはずだった。

## 根因

**比較の軸を取り違えた。** 利用者は「通った方（普段の Chrome）」と「通らない方（自動化ブラウザ）」を
対比していた。両者の違いは複数ある（ブランド / プロファイル / 自動操作の有無 / 人が使っているか）。
そのうち**自分が直せる軸（ブランド）** を選び、**問題を決めている軸（自動操作の有無）** を確かめなかった。

さらに、自分で立てた根拠（「Chromium は `153.0.0.0` と名乗るのが不自然」）が
検証前の推測だった。実際には本物の Chrome も `153.0.0.0` を名乗る（UA の版数縮約）。
推測を根拠として利用者に示し、試行を 1 回無駄にした。

## 予防ルール

- **「普通の X を使えば」と言われたら、ブランドか個体かを確かめる。** 特に利用者が
  「普段の X ではうまくいった」と言った直後なら、指しているのは**その個体**である可能性が高い
- **成功例と失敗例の差分を列挙してから、どの差分を埋めるか選ぶ。**
  直しやすい差分ではなく、原因になっている差分を選ぶ
- **根拠として示す前に、その根拠を 1 回測る。** 「〜と名乗るのが不自然」は、本物を 1 回起動すれば確かめられた

## 結果

Claude in Chrome（利用者が普段使っている Chrome の個体を操作する）で開くと、
関門なしで `jp.indeed.com` が開け、ログイン済みだった。
`claude -p --chrome` で常駐の子プロセスからも操作できることを実測した（費用 $0.61 / 4 ターン）。
