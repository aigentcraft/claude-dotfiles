## 1. Plan / Context
pullie のkintoneデモアプリDSLは複数行前提（1行=フォーム1行・行頭`[見出し]`=ラベル行、
1行DSLは2列自動詰め）。writerが記事内マーカー `<!-- スクショ: キー | アプリ名 | DSL -->`
でフィールドを指定し、05がデモアプリを構築して実画面を撮る。

## 2. Do / The Error
2026-08-28朝、記事#23が3ラウンド検閲失敗で破棄（本日コスト$20.89）。連鎖:
- writerはDSLをHTMLコメント**1行**に平坦化し「仕入先(文字列) [在庫管理] 数量(数値)」の形で出力
  （コメントを1行に潰すのはLLMとして自然な変形。見出しの位置も意図は一意に読める）
- パーサは`[見出し]`を**行頭のみ**認識・フィールド区切りは「,、」のみ → 上記が1フィールドと
  解釈され「未知の型」DemoAppError → スクショ3枚ともグレーススキップ（コメント残置）
- 検閲Q05/Q09「スクショ未挿入」で毎ラウンド確定fail → 再執筆しても05が同じ地雷を踏む
  決定論ループ → 3ラウンド超過で記事破棄・トピック再キュー
- 発覚はops-auditorの朝の監査報告（high: 公開2日停止）→人間がDiscordで検知

## 3. Check / Root Cause
1. **LLMに書かせるDSLは「教科書どおりの形」以外が必ず来る**。意図が一意に復元できる変形
   （1行化・インライン見出し）を拒否する厳格パーサは、グレーススキップと組み合わさると
   「静かな確定失敗ループ」になる
2. リトライ（再執筆）が効かない失敗だった — 落ち方が「writer出力の揺れ×決定論パーサ」なので
   何度書き直してもほぼ同じ形で出力され同じ場所で死ぬ。ラウンド制は品質問題向けの装置で、
   決定論欠陥には無力（$20を燃やして破棄しただけ）
3. 同族: [[llm-output-fence-heuristic-matches-inner-code-block]]（LLM出力の構造切り出しの
   脆さ）・[[catalog-key-added-without-consumer-sync.md]]（DSL契約の生産者/消費者ずれ）

## 4. Act / Prevention Strategy (Fix)
- 修正: パース前にインライン`[見出し]`を行頭へ正規化（`\s*\[..\]\s*`→改行挿入）。
  explicit判定（1行DSLの2列自動詰め）は正規化**前**の物理行数で行い既存挙動を保存。
  selftestに実弾マーカーの回帰ケースを追加
- **予防ルール**: ①LLMに書かせる構造記法は「意図が一意に復元できる変形」を列挙して
  パーサ側で受容する（1行化・区切りの揺れ・見出し位置）— 拒否してよいのは意図が曖昧な
  入力だけ ②「LLM出力→決定論パーサ→グレーススキップ→品質ゲートfail」の経路は、
  リトライで回復しない決定論ループになっていないか設計時に検査する（パース失敗は
  グレースでなくwriterへの差し戻し材料に載せる方が回復可能性が高い）
