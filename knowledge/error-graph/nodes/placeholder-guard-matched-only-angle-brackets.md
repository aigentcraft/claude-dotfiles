## 症状
Windows で資格情報を 3 件登録したところ、`npm run credentials` は 3 件とも
`[ OK ] 登録済み` と報告した。しかし Gmail への実接続だけが `curl: (67) Login denied` で失敗。
調べると **account に案内文の日本語がそのまま入っていた**。

| 項目 | 登録されていた account | 本来の値 |
|---|---|---|
| gmail | `Gmailアドレス` | 実際のメールアドレス |
| mamaworks | `あなたのメールアドレス` | 同上 |
| indeed | `Indeedのメールアドレス` | 同上 |

秘密（アプリパスワード 16 文字）は正しく入っていた。**壊れていたのは利用者が置換しなかった側**。

## 根本原因（2 つある）
1. **ガードの前提が狭い。** `checkCredential` のプレースホルダ検出は `/^<.*>$/`、
   つまり**山括弧で囲まれている時だけ**反応する。案内の例文から山括弧が外れた瞬間、
   同じ「置き換え忘れ」を一切検出できなくなる。ガードが見ていたのは**表記**であって**意味**ではない
2. **AI が渡した例文が悪かった。** コマンド例を
   `cmdkey /generic:... /user:あなたのメールアドレス /pass` の形で提示した。
   日本語の説明語は**そのまま実行できてしまう**ため、置換すべき箇所だと気づけない。
   `<...>` を外したのは「山括弧ごと消す」という以前の誤登録への対策だったが、
   その結果ガードの検出条件まで外していた

## なぜ「登録済み」に見えたか
`checkCredential` が見るのは ①account が空でない ②山括弧で囲まれていない ③秘密が空でない、の 3 点。
**値が意味を成すかは見ていない。** 疎通確認（`-- --verify`）を走らせて初めて嘘だと分かった。
site 系は `--verify` に相当する検査が無く、**実ログインまで誤りが表面化しない**。

## 修正
- 人に渡すコマンド例のプレースホルダを `taro@example.com` に統一（明らかに架空と分かる形）
- DEVELOPMENT_POLICY §10 に原則 17 として追加

## 見送った修正（理由つき）
account の形そのものを検査する案（メール系なら `@` を含むこと）は**入れていない**。
稼働機（Mac）に登録済みの値がこの検査に通る保証が無く、通らなければ
`update.sh` の資格情報ゲートが落ちて更新が巻き戻る。**稼働機で実測してから入れる。**

## 予防ルール
1. **人に渡す例文のプレースホルダは `taro@example.com` のように明らかに架空の値にする。**
   説明語（「あなたのメールアドレス」等）を置かない。そのまま実行できてしまう
2. ガードは「表記」ではなく「値の形」を見る。ただし**既存データを落とす検査は稼働機で確認してから入れる**
3. **「登録済み」は疎通まで確かめて初めて意味を持つ。** 形だけの検査しかない項目は、
   その旨を出力に書く（本プロジェクトは「疎通は未確認」と明示している）
4. 関連: [[abstraction-left-old-name-in-user-facing-strings.md]]（同じセッションで、
   どちらも「自動検査が全部緑でも実行すると嘘が出る」形だった）
