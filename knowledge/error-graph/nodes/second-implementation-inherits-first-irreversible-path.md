## 1. Plan / Context

副業サイトを横断するエージェント基盤に、2 つ目のサイトを足した。
1 つ目は求人検索・受信箱・応募のすべてを実装済み。2 つ目は**求人検索だけ**。

案件は Discord の「案件ボード」にカードとして出る。カードのボタンで
状態を進め、応募まで行ける。この UI は 1 サイトしか無い頃に作られていた。

## 2. Do / The Error

2 サイト目の案件をボードに出した時点で、**その案件にも応募フローのボタンが付く**。

押すとどうなるかを追うと:

```
［応募検討へ］→ 状態を considering へ → 応募文を自動生成（LLM 課金）
            → ［承認して応募する］→ executeApply
                 └─ withAuthenticatedPage('mamaworks', …)   ← 1 サイト目に固定
                      applyToJob(page, { jobUrl: <2 サイト目の URL> })
```

**1 サイト目のブラウザプロファイルで 2 サイト目の URL を開き、
1 サイト目のセレクタで応募を試みる。** 幸い失敗はするが、
利用者には「応募できませんでした」としか見えない。

しかも失敗する前に LLM を呼んで応募文を作っている。行き先の無い文章に課金していた。

## 3. Check / Root Cause

**案件が「どのサイトのものか」を、経路のどこも持っていなかった。**

- 案件レコードの型（`JobRow`）に `site` が無い（DB の列はあるが SELECT していない）
- カードのボタンを組み立てる関数はサイトを知らない
- 不可逆操作の実行関数はサイト ID をハードコードしていた

1 サイトしか無い間、これは「省略」であって誤りではなかった。
2 つ目が入った瞬間に、**省略が「1 つ目への固定」として振る舞い始めた**。

暗黙の前提は壊れる時に音を立てない。型の上では何も矛盾しておらず、
コンパイルも通り、テストも（1 サイト分しか無いので）通る。

## 4. Act / Fix & Prevention

**できないことを型で宣言し、呼ぶ前に止めた。**

```ts
export interface SiteCapabilities {
  readonly search: boolean;
  readonly inbox: boolean;
  readonly apply: boolean;   // 不可逆
}
```

省略可能（`?`）にしない。既定値も持たせない。省略できると、サイトを足した人が
何も書かずに「できること」にしてしまう。**宣言を強制することが目的**なので、
書く手間はそのまま安全側に効く。

遮断は 1 箇所にしない。

- 文案を作る前（**LLM を呼ぶ前**に止める。課金してから断らない）
- 実際に不可逆操作が走る直前（古いカードのボタンが残るなど、経路は 1 つとは限らない）
- カードの表示（押す前に「自動化していません」と分かる）

### 予防ルール

1. **2 つ目の実装を足す時、まず「1 つ目に固定されている場所」を探す。**
   ハードコードされた ID、引数に無い前提、型に無いフィールド。
   1 つしか無い間は省略と固定の区別が付かない。
2. **未実装は型で表す。** 「まだ無い」をコメントや暗黙の前提に置くと、
   呼び出し側は「できる」と仮定して呼ぶ。能力を必須フィールドで宣言させる。
3. **不可逆操作のガードは、最も外側と最も内側の両方に置く。**
   外側（UI・生成）は無駄な処理を防ぎ、内側（実行直前）は経路の見落としを防ぐ。
   どちらか一方だと、想定していない経路が残る。
4. **黙って何もしないガードを書かない。** 押したのに反応が無ければ、
   利用者は壊れているのか処理中なのか判断できない。
   何ができないかと、代わりにどうすればよいかを必ず返す。
5. **ガードは実行して確かめる。** 「押しても応募されない」は読んでも証明にならない。
   実際にボタン相当の関数を呼び、状態が進まないことと課金が発生しないことを見る。

## 5. 並行化のついでに見つかった 2 つの共有状態

サイトを増やすと、「1 本で足りていたもの」が足枷になる。

- **ブラウザ操作の直列化が全サイト共通の 1 本の鎖だった。**
  直列化が要るのは「同じプロファイルを同時に開かないため」なので、鎖はサイト単位でよい。
  共通のままだと、片方がレート制限で待つ間もう片方も止まる
- **スケジュールの実行記録が共通キーだった。**
  `schedule.lastrun.hunt` に 1 つだけ書くので、**最初に実行したサイトが
  「実行済み」を立て、残りのサイトが丸ごと飛ばされる**

> キーを分ける時は、**古い記録の引き継ぎ先を間違えない**こと。
> 単一サイト時代の記録は最初のサイトのもので、全サイトへ配ると
> 後から足したサイトの初回が「実行済み」として飛ぶ。
