## 1. Plan / Context

案件を保存する `upsertJob` は、**既知の案件なら既存 id を返して何も書き換えない**。
状態（`screening` / `applied` など）を後から勝手に戻さないための設計で、これ自体は正しい。

```ts
const existing = conn.prepare('SELECT id FROM jobs WHERE job_key = ?').get(input.jobKey);
if (existing) return { id: existing.id, isNew: false };   // ← 触らない
```

一方、2 サイト目（インディード）は**一覧に業務内容が無い**。判定に使う本文は
求人ごとに詳細ページを開いて取る。**1 件 1 リクエスト**で、レート制限の的もここに集中する。
システムの中で最も高価な取得処理だった。

## 2. Do / The Error

実行ログは成功に見える。

```
[INFO] 求人検索: 40 件
[INFO] 本文取得: 10 件
```

DB を見ると、本文を持つ案件は **3 件のまま増えていなかった**。
その 3 件は初回（全件が新規だった時）に挿入されたもので、
**2 回目以降に取得した 10 件はどこにも残っていない**。

## 3. Check / Root Cause

**「既存行を触らない」が、状態だけでなく本文にも効いていた。**

新規なら本文ごと INSERT される。既知なら丸ごと素通りする。
候補オブジェクト（メモリ上）には本文が載るので、**その実行の中では正しく判定に使える**。
だから機能しているように見える。消えるのは実行が終わった瞬間。

被害は「保存されない」だけではない。

1. **毎回買い直す。** 次回も同じ案件の本文が空のまま集まるので、また取りに行く
2. **繰り越しが永久に減らない。** 上限 10 件で 40 件を処理するつもりが、
   何度回しても同じ 10 件を取り直して終わる。収束しない
3. **最も高価な操作を、最も無駄に繰り返す。** レート制限に当たりやすい処理が、
   何の蓄積もせずに毎回走る

ログは嘘をついていない。**10 件は確かに取得した。** 取得したものがどうなったかを
報告していなかっただけで、「処理の報告」と「残った結果」がずれていた。

## 4. Act / Fix & Prevention

取得の直後に本文だけ書き戻し、取りに行く前に既に持っていないか見るようにした。

```ts
// 取った直後に書き戻す（未登録なら 0 行更新。後段の upsert が本文ごと挿入する）
saveJobSummary(jobKey, description);

// 取りに行く前に、既に持っているものは候補に戻して再取得しない
const stored = getJobSummary(jobKey);
```

### 予防ルール

1. **冪等性のガード（upsert・no-overwrite・skip-if-exists）を入れる時は、
   「触らない」対象に高価な取得結果が混ざっていないかを確かめる。**
   状態を守るためのガードが、コストを払って得たデータまで守ってしまう。
   守るべきは「勝手に戻ってはいけない値」だけで、追記的な値は別扱いにする。
2. **「取得した件数」ではなく「残った件数」を見る。**
   処理の報告（`本文取得: 10 件`）は真実でも、効果の報告ではない。
   ログが成功を示す時こそ、成果物の側を数えに行く。
3. **繰り越し方式は「収束するか」を確かめる。** 上限を設けて次回へ回す設計は、
   1 回ごとに残りが減って初めて成立する。減らなければ、それは繰り越しではなく空回り。
4. **メモリ上でだけ正しい状態に注意する。** その実行の中では動くので、
   単発のテストも目視も通る。実行をまたいだ時に初めて壊れる。
