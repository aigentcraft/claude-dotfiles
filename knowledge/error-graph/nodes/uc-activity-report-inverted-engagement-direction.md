# 方向・主体が意味を持つデータは、LLM要約器に渡す前に方向を値へ焼き込む

## 症状（ユーザー指摘）
「いいねをもらったみたいな判定になってない？これって自分のアカウントがイイネしただけじゃん」
— sns-directorの日次活動報告が「Zapier・n8nからのいいね反応（4件）があり、自動化プラット
フォーム層との接点が生まれている」と記述。実際は05_engageが**こちらから**相手の投稿へ送った
いいね4件（zapier×2/n8n_io/superkojochou）。同じ報告内で自投稿は「いいね0」とも書いており
自己矛盾していた。人間は通知欄を探して見つからず、システムへの不信が発生。

## 根本原因
- 06_daily_reportのgather()が x.engaged の生payload（`{action:"like", handle:"zapier"}`）を
  **方向ラベルなし**でLLMに渡していた。「handle=zapier のlike」は送り/受けどちらにも読める。
- LLMは曖昧さを**成果が大きく見える方向に解消する**（自己報告の粉飾バイアス）。
  「実データにあることだけを書く」というLOCKED原則があっても、方向がデータに無ければ
  推測で補われ、この原則では防げない。
- 監査側の失敗も複合: 最初の調査は「いいね4件の実在」をX実見で確認し「報告は正確」と
  結論した。**entityの実在検証と主張（方向・文言）の検証は別物** — 監査は報告の文言単位で
  データと突き合わせる。[[uc-unverified-hazudesu-reporting.md]]

## 修正（2026-08-19・実弾生成テストで検証済み）
1. **データに方向を焼き込む（LLM-Free）**: gather()の `engaged` → `engaged_by_us` に改名し、
   各件を `{方向:"こちらから相手へ（相手からの反応ではない）", 操作:"いいねを送った",
   相手:"@zapier", ...}` へ変換（`_outbound()`）。キー名だけでなく**値に**方向文を入れる
   （JSONの切り詰め・整形でキー文脈が失われても件単位で残る）。
2. **プロンプト契約**: taskに方向の規律を明記（受け方向表現への変換禁止・受けた反応の根拠は
   own_metricsの実測のみ）。
3. **SKILL(EDITABLE)に恒久ルール**: sns-director手順4として同規律を記載。
4. 付随: 同日3通届いていた重複報告に**1日1通ガード（JST日付でx.daily_reportイベント既存なら
   skip）** — docstringの「1通送る」をコードで機械保証。
検証: 8/18実データ+新プロンプトで生成（送信なし）→「交流：いいね4件（Zapier×2・n8n・
個人フォロワー**向け**）」と送り方向で正しく表現・NG表現検出ゼロ。

## 予防ルール（一般化）
- **方向・主体・因果が意味を持つデータをLLM要約器へ渡す時は、方向を推測させずデータの値に
  焼き込む**（「誰が誰に」を1件ごとに自然文で持たせるのが最強）。
- **自己報告系エージェントには送り/受けの語彙を契約で固定する**（「送った」「〜向け」vs
  「もらった」「〜からの」）。LLMの曖昧解消は自分に有利な方向へ倒れると想定して設計する。
- **報告の監査は文言単位**: 記録の実在確認だけでは報告の正しさを保証しない。主張（方向・
  件数・主体）ごとに一次データと突き合わせる。
