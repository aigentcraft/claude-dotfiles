## 症状（Symptom）
人間「ディスコード上に承認依頼が来ているけど、チャット欄のどれなのか探すのが面倒。該当するメッセージに飛べるようにして。
また、GPTimageじゃない画像のままの記事も承認依頼が来ている」。

実データ（2026-09-26・承認待ち 8 本）:
- 記事 33: 冒頭画像 + 図 5 枚が 9/23 の簡易版（HTML の代用描画）のまま承認依頼
- 記事 47: GPT で 7 枚描けていたのに**本文に 1 枚も入っていない**版で承認依頼（残り 1 枚の上限待ちの間は原稿に触らない設計）
- 記事 48: 画像 0 枚で承認依頼
- 記事 42: 9/24（待機の仕組みの前）に簡易版 7 枚。06b が途中で落ち、依頼が 1 通も出ないまま承認待ちに残った
- リマインドは 8 本を並べたが、うち 3 本（31・37・50）は画像待ちで**押すボタン（依頼）がそもそも無かった**。
  依頼へのリンクも無く、人は #approvals を遡って探していた

## 根本原因（Root Cause）
1. **「グレース（止めずに続行）」が一時的な失敗を「完了」として記録していた。** 05 は図の担当の企画が落ちると
   「企画失敗でも公開を止めない」として `images.generated`（= 描き終えた）を記録していた。9/25 夜の再開は 1 日の
   コスト上限（$150）で企画が全件落ち、33・47・48 がそのまま 06b → 承認依頼へ進んだ
2. **承認依頼の手前に「画像が GPT で描けているか」を見る所が無かった。** 9/25 の待機の仕組みは「上限に当たったら待つ」
   という**原因側**の条件だけで止めていて、**結果側**（本文が使っている画像の経路）を誰も数えていなかった。
   原因側の条件は、別の原因（企画失敗・仕組みより前に描かれた記事）を通してしまう
3. 依頼メッセージの id は記録していたが、リマインド・成果チェックは**その id からリンクを作っていなかった**。
   さらにリマインドの対象は「status=review」だけで、依頼が出ているかを見ていなかった

## 修正（Fix）
- `image_stage.gpt_gaps`（純関数）: 本文が参照する画像と manifest の engine から「GPT で描けていない画像」を数える
  （冒頭画像なし / 簡易版の冒頭画像 / 簡易版の図 / 画像 0 枚）。`is_fallback` を image_stage に一本化し 05 は別名で使う
- `ensure_images`（05 の後）と 06b（承認依頼の直前）の両方で見て、足りなければ `images.waiting(reason=gaps)` で待機 →
  次の記事生産が描き直す。出ていた承認依頼は取り下げ（ボタンを無効化して理由を書く）。
  `GAP_HOLD_MAX`=3 回描き直しても残る分は待たずに、**どの画像が簡易版かを依頼の題と本文に書いて**人に渡す
- 05 の企画失敗は `images.waiting(reason=plan_failed)`（完了にしない）
- 承認依頼に `channel_id / guild_id / jump_url` を記録。リマインドと毎朝の成果チェックに記事ごとの「承認ボタンのある依頼へ移動」リンク。
  画像待ちの記事はリマインドから外し、依頼の無い承認待ちは run_pipeline が 1 日 1 回やり直す（`resend_missing_requests`）
- テスト +28（旧コードで 27 件の赤を実測）。conftest で本物の Discord への通信を遮断

## 予防ルール（Prevention）
1. **グレース（止めずに続行）で「完了」の記録を書かない。** 一時的な失敗は「待機・やり直し」として記録する。
   完了の記録は後段の関門を全部素通りさせる — グレースの影響範囲は「その工程」ではなく「それ以降の全工程」
2. **関門は原因ではなく結果で書く。** 「上限に当たったら止める」は上限という 1 つの原因しか止めない。
   「公開面に出るものが基準を満たしているか」を成果物（本文の参照 + 作られ方の記録）で数えれば、原因が何でも止まる
3. 人に何かを押させる通知は、**押す場所へのリンク**と「押す対象が本当にあるか」を一緒に出す。
   押せない項目を並べると、人は存在しないものを探し続ける
