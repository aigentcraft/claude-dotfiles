## 症状

記事用のデモアプリ構築が失敗し、その記事のスクショが撮れず、検閲Q05/Q09で不合格になる。
2026-09-10〜09-12 に6件。撮影レーンの並走比較（移行計画Phase 2）も、
本番撮影が成功した後ろでしか走らない設計のため**データが1件も貯まらなかった**。

```
DemoAppError: 未知の型: 品番(ルックアップ)
DemoAppError: 未知の型: ステータス(申請中,承認済み)
DemoAppError: POST form/fields.json -> 400 CB_VA01
  errors: properties[【廃止予定】旧特約条件].code
          「先頭に数字が使用されているか、使用できない記号…」
```

## 根本原因

**writer が書く自然な日本語を、kintone の機械的な制約にそのまま通していた。**

1. **記号入りの項目名** — kintone の *フィールドコード* は記号をほとんど受け付けない
   （英数字・かな・カナ・漢字・`_`・`・`・全角通貨記号のみ）。
   一方 **ラベル** は何でもよい。実装は `code = label = 項目名` と同一視していたので、
   「【廃止予定】旧特約条件」のような見出し語でアプリ構築ごと 400 になった
2. **型名を書かない選択肢** — 「ステータス(申請中,承認済み)」。
   DSL は `選択:a,b` を期待するが、意図は一意
3. **デモアプリ単体で作れない型** — 「品番(ルックアップ)」。参照元アプリが要る

いずれも「writer が悪い」形にしてある。しかし **記号を使うな・型名を正確に書けという制約は、
書き手に課すべきものではない**。機械が吸収できるものは機械が吸収する。

## 修正

- ラベルはそのまま保ち、**コードだけを安全化**（不正文字を `_` に・先頭数字に接頭辞）。
  副作用として計算式の参照がズレるので、式の中のラベルもコードへ置換。
  安全化でコードが衝突したら連番で逃がす（黙って項目を落とさない）
- 型名なしのカンマ列はドロップダウンとして受容
- ルックアップ／関連レコードは文字列へ機械降格（`計算:TODAY-...` の降格と同じ方針）
- 実際に落ちていた仕様そのままでアプリ構築が通ることを実機で確認（app=165）
- 3件とも selftest に固定

## 予防ルール

- **LLMが書く自然な表現を、外部システムの識別子にそのまま使わない。**
  表示名（label）と識別子（code）は別物として持ち、識別子は機械が生成する
- DSL が「未知の型」で例外を投げる前に、**意図が一意な書き方は受容**する
  （既存の「日時」「行中の [見出し]」受容と同じ方針）
- 機械降格したときは、下流の不一致判定が拾える形にしておく（握り潰さない）
