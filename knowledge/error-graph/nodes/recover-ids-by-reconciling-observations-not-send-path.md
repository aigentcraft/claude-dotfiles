## 症状

外部SNSへの投稿の **30%（29/98）が永久に未計測**だった。
引用ポストだけはブラウザUI経由で送信しており（API規制でAPIからは送れない）、
送信関数は投稿IDを読まず `'browser-ok'` という文字列を返すだけ。
そのため投稿レコードに `x_post_id` が入らず、
観測ワーカーの更新条件 `x_post_id IS NOT NULL` に**一生入らない**。

素直な直し方は「送信直後に投稿URLを読む」だが、
**それを検証するには実際に外部へ投稿するしかない＝不可逆**。
検証できない修正を本番に置くことになる。

## 解決

**送信経路（不可逆）に触らず、観測側で照合して回収した。**

自分のタイムラインを期間指定で取得し、未結線の投稿レコードと突き合わせて `x_post_id` を埋める。
この形にすると **過去の遡及補完と、今後の投稿の結線が同じ1経路**で片づく
（送信側に足す修正では、過去分は永久に救えない）。

照合の作り方（誤結線はメトリクスを恒久的に汚すので厳しく）:

- 「投稿時刻の近接（±180秒）」と「本文の先頭一致」の**両方**を要求する
- 候補が**ちょうど1件**のときだけ結線する。0件でも複数でも**触らない**
- 既に他の行が使っているIDは候補から除外する
- `UPDATE ... WHERE id=? AND x_post_id IS NULL` で、既存値を絶対に上書きしない
- 対象が無ければ API を1回も叩かない（定常運転でコストが増えない）

### 落とし穴: 外部サービスは本文を書き換える

最初は本文の**完全一致**で照合し、**29件中0件**しか当たらなかった。
原因は X が引用ポストの本文末尾に引用元の短縮URL（`https://t.co/xxxx`）を自動で足すこと。
末尾URLを剥がして**先頭一致**に変えたら **29/29 が一意に一致**した（曖昧一致0・衝突0）。

## 結果（これが本題）

回収された実測は **impressions 4,499 / likes 20**。
それまでDBが知っていた**全体（1,709imp / 11likes）を上回った**。
1本あたり155impで、他の型（約25imp）の**6倍**。

つまり **未計測だった型が、実際には最も伸びている型だった**。
未計測を0として扱っていれば、組織は「引用は効かない」と学習し、
最良の打ち手を自分で捨てていた。

## 予防ルール

- **不可逆な経路の欠陥は、可逆な側（観測・照合）で回収できないか先に考える。**
  送信・課金・公開のような戻せない経路を直すと、検証自体が不可逆になる
- **遡及と将来を同じ経路で片づける。** 送信側に足す修正は過去を救えない。
  観測側の照合なら、既に起きた分も次に起きる分も同じコードが拾う
- **照合は「ちょうど1件」のときだけ実行する。** 曖昧なら触らない。
  誤結線は「測れていない」より悪い（間違った値が測定値として残る）
- **外部サービスは本文を書き換える**（短縮URL付与・正規化・切り詰め）。
  完全一致を前提にせず、まず実データで照合率を測ってから方式を決める
- **「未計測の型は成績が悪い」と思い込まない。測れていない側に最良が隠れていることがある。**
