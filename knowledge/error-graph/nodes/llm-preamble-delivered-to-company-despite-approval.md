## 1. Plan / Context
副業HOOTL は、企業からの連絡への返信案（`core/draft.ts`）と応募文（`core/apply-draft.ts`）を `claude -p` で作り、
Discord の承認ボタンで企業に送る。指示文の出力ルールは「返信本文だけを出力する。前置き・見出し・解説・マークダウン記法は一切書かない」。
承認カードには全文が出る。ママワークスは利用者の指定で、検討中のカードに確認なしの［応募する（即実行）］がある。

## 2. Do / The Error（2026-10-03 に利用者が DB で発見）
企業に届いた 3 件（`messages.sender='me'` と送信記録で確認）:
- ユニタス（インディード・9/26 19:05）: 先頭「確定した事実に基づいて返信文を作成します。」
  — 情報待ちの答えから作る `generateDraftWithFacts`。19:01 に作成 → 約 1 分半後に承認 → 普段の Chrome で送信
- ケイビーカンパニー（ママワークス・10/01 9:42）: 先頭「…の求人は絶対条件に抵触しないため、応募メッセージを作成します。」
- 川勝電気（ママワークス・10/01 9:43）: 先頭「400〜600文字の応募メッセージ本文のみ出力します。」と `---`
  — 2 件とも［応募検討へ］から 26〜36 秒で応募（文面を読む時間は無い）
送られていないが残っていたもの: 応募文に「415字で400〜600の範囲に入った。これで最終版とする。 ---」・
本文の代わりに「この求人は応募文を書く前に確認させてください。**…抵触する可能性が高いです。**」、
**承認ボタンが生きている返信案**に「返信文の下書きは作成しませんでした。理由は以下の通りです」（太字つきの分析）・
前後に判断の説明と `---`・書き出し「土屋様」（相手の書き出しの写し）。
※ ママワークスの応募メッセージ先頭の「> 「求人名」について」はサイトが入力欄に入れている引用で、LLM の出力ではない。

## 3. Check / Root Cause
1. **指示で禁じるだけで、出力を検査する層が無かった。** LLM は判断（受託条件に合うか）や作業（字数の確認）を独り言として書く。
   指示文に「受託条件」「確定した事実」などの見出しがあるほど、それに触れる前置きが出る
2. **人の承認は検査にならない。** カードに全文が出ていても、承認は数十秒で押される。即実行ボタンは文面を見ずに押せる
3. 生成に失敗した時の経路が投げっぱなし・ログだけの箇所があり、「止める」を足すと黙って止まる経路になりかけていた
   （情報待ちからの返信案・応募文の作成・非承認の作り直し）

## 4. Act / Prevention Strategy (Fix)
- `core/preamble.ts` の純関数 `findPreamble`: 手紙の外（宛名・挨拶より前と署名より後）の「この文面を作る話」（返信文/応募メッセージ×作成します/出力します）、
  指示文の写し（「確定した事実に基づ」「絶対条件に抵触」）、作業メモ（「これで最終版」）、マークダウン（太字・`---`・見出し）、
  「本人」と三人称で呼ぶ説明、書き出しの自分宛て宛名。**実データ 170 件で既知の 11 件だけを検出・誤検出 0**
- **生成直後**: `writeWithoutPreamble` で 1 回だけ書き直させ（混ざった文を見せて頼む）、2 回とも混ざれば投げてカードを出さない
- **送る直前**: 返信は 3 サイト共通の `onApprove`、応募は 3 方式共通の `executeApply`、メール・フォームは提案時と承認時に通る検証関数。
  止めたら、その文を書かないよう指示してその場で作り直す（承認ボタンは押した時点で外れているので、止めるだけだと行き止まり）
- 応募文が無いまま即実行が押されたら応募しない（止めたことで「文面の無い応募」が増えないように）
- 作り直しで会話を取り直せない時（インディードは受信箱を読めない）は DB に保存した会話で作る（止めた後の行き止まりを無くす）
- selftest に実物の文（届いた 3 件・承認待ち 5 件）・ありがちな形 16・似ているが正しい文 25・規則ごとの単独 14
- **コードレビュー（別エージェント）で 2 つ見つかった**:
  ① 前置きが 2 段落・署名の後の後書き・「返信を作成いたします」「以下が本文です」が素通し、「② 志望動機（400字）」「これで最終版です（納品）」が誤検出
  → 「手紙の外」（宛名・挨拶・応募の書き出しより前の段落と、署名より後の段落）を全部見る形にし、字数の報告は最後の行だけにした
  ② 自己診断は文字の前後関係しか見ておらず、**止めた後の `return;` を消しても・検査をコメントに隠しても緑のまま**だった（「止めたと言って送る」を見逃す）
  → コメントを除いたソースで `if (leak) {…}` の中の `return;` まで見る。送る文の取り出しは 3 方式の偽の案件で動作として確かめる。
  故障注入 4 種（return の削除 3 か所・コメントに隠す・規則を壊す・検知の無効化）で FAIL を確認

**予防ルール**:
1. **LLM の出力をそのまま外へ出すなら、出口（生成直後と送る直前）に決定論の検査を置く。** 指示で禁じるのも人の承認も、検査の代わりにならない
2. 検査で止める経路を足したら、**止めた後に人が次に押すものがあるか**を確かめる（ボタンは押した時点で外れる）。無ければその場で作り直す
3. 検査の正規表現は**実データ全件**に当てて、止めるべきものだけが止まることを数で確かめてから入れる
4. 生成側を直しても既に出たものは直らない。承認待ちに残っているものは送る直前の検査で止める（[[uc-internal-handoff-note-live-on-published-page]] と同じ）
5. **検査の配線を自己診断で固定するなら、文字の有無ではなく「止めた後に return する」まで見る**（コメントを除いて）。
   故障注入は「検査を消す」だけでなく「return を消す」「コメントに隠す」も入れる。消すだけの注入では、最悪の退行（止めたと言って送る）を試していない
6. 前置きの位置は「最初の段落」ではなく「**手紙の外**」で決める（宛名・挨拶より前、署名より後）。前置きが 2 段落でも後書きでも拾え、手紙の中の経歴・答えは止めない
