## 1. Plan / Context
応募は取り消せない操作なので、「ボタンを押しただけで成功としない」という原則を入れていた。
押した後に**応募済み表示が出るまで待ち**、出なければ失敗として人間に手動確認を促す。
原則としては正しく、実際にそう実装されていた。

```ts
const APPLIED_MARKER = '.p-recruit__stop';
await page.waitForFunction((sel) => document.querySelector(sel) !== null, APPLIED_MARKER, { timeout: 25000 });
```

## 2. Do / The Error
承認を受けた 11 件の応募が、5 分間で**すべて同じ失敗**を出した。

```
[22:21:12] [FAIL] 応募失敗 job#43: 応募ボタンは押しましたが、応募済みの表示を確認できませんでした。
… 11 件すべて同文
```

実際にサイトを見に行くと、**10 件は応募が成立していた**。
決定打は受信箱で、応募時刻と 1 分以内に各社から自動返信が届いていた。

```
22:21:21 TELUS International   ← 応募 22:21:12
22:21:55 株式会社想結び          ← 応募 22:21:48
```

## 3. Check / Root Cause

`.p-recruit__stop` はサイトから**消えていた**。常に 0 件なので、応募が通っても待ち続けてタイムアウトする。
現在の実装では、応募後に応募ボタン自身が操作不能な「応募済み」表記へ変わっていた。

```
button.p-recruit-show__entry-btn.u-cursor-default → 「応募済み」
```

被害は誤報告だけではなかった。

1. **DB が実態とずれた** — 10 件が `considering` のまま残り、応募中として追跡されない
2. **後続処理が丸ごと飛んだ** — 失敗と判断した時点で return するため、
   その先の「企業へ応募文を送る」に到達せず、**10 社に文面なしの応募だけが届いた**
3. **同じセレクタを事前チェックにも使っていた** — 「既に応募済みか」の判定も壊れており、
   重複応募を防ぐ防壁も同時に失われていた

診断コマンド（`doctor`）は**ログイン判定のセレクタしか検査していなかった**。
最も壊れて困るのは不可逆操作の成否判定なのに、そこに診断が無かった。

## 4. Act / Fix & Prevention

セレクタを実測値へ更新し、Playwright のロケータで待つよう変更した
（`waitForFunction` + `querySelector` は `:has-text()` を解釈できないため）。

### 予防ルール

1. **「状態変化で成否を判定する」設計は、その状態変化の検出器が生きている前提に立っている。**
   検出器が腐ると、安全弁は「安全側」ではなく「毎回失敗」に倒れる。
   失敗が続いたら、操作の失敗ではなく**判定の失敗**を先に疑う。
2. **同種の失敗が連続したら、個別要因ではなく共通要因を疑う。**
   11 件が全部同じ文言で落ちるのは、11 回の不運ではない。
3. **対照実験で判定器を検証する。** 「成功していると分かっている対象」に判定器を当てる。
   今回は DB 上 applied の案件でも 0 件だったことで、セレクタ側の問題だと即断できた。
4. **不可逆操作の成否判定こそ診断対象に入れる。** ログイン判定だけを診断していた。
5. **失敗時に後続処理を飛ばすなら、何が飛ぶのかを把握しておく。**
   「応募は成功・文面は未送信」という中途半端な状態が生まれた。

## 5. 続き — 同じ症状が、別の原因でもう一度出た

セレクタを直した後、利用者が応募を承認すると**また同じ文言**が出た。

```
❌ 応募できませんでした。応募ボタンは押しましたが、応募済みの表示を確認できませんでした。
```

サイトを見ると、今回も**応募は成立していた**。しかもページを開き直せば
新しいセレクタは正しく「応募済み」を検出できた。つまりセレクタは正しい。

原因は**待ち方**だった。応募は form POST でページが遷移する。
クリック直後に待機を始めると、遷移で実行コンテキストが壊れ、
待機中のロケータが例外になる。押した直後に待つ、という順序自体が誤りだった。

```ts
await confirm.click();
await page.locator(APPLIED_MARKER).waitFor(...);   // 遷移で壊れる
```

修正は「押す → 遷移の完了を待つ → 改めて確認する」。
反映の遅れに備えて数回試し、途中で求人ページを開き直す保険も入れた。

### 追加の予防ルール

6. **1 つの原因を直しても、症状が消えたことにはならない。**
   同じ文言がまた出たら「直したはずだ」ではなく、もう一度切り分ける。
   今回は「セレクタが腐っていた」と「遷移で待機が壊れた」という
   **無関係な 2 つの原因**が、まったく同じ失敗メッセージを出していた。
7. **クリックで遷移が起きる操作は、待機の前に遷移の完了を挟む。**
   遷移するかどうかは実装依存なので、`waitForLoadState` を無害な保険として先に置く。
8. **不可逆操作の検証は本番実行を伴うため、気軽に試せない。**
   だからこそ「読み取りだけで確かめられる対照（既に成功した対象）」を先に用意する。
