# 「生成単位」と「排出単位」が違うキューは、内容の分散を明示的に設計しないと偏る

## 症状（ユーザー指摘）
「同じ記事のツイートを2回連続でしています」— 記事#10の告知が8/16朝run・8/17朝runと
連続投稿された（過去にも記事#1で同パターンが発生していた）。

## 根本原因
- 生成は記事単位で2本（バリエーション）を**同時にINSERT** → idが必ず隣接する
- 排出は `ORDER BY id LIMIT 1`（1本/run）→ 隣接ペアがそのまま連続runで出る
- つまり「タイムラインへの一斉発射を避ける」ための1本/run設計が、
  **内容の分散を保証しない**（時間は分散したが内容が連続した）
- さらに「公開直後は2本即時」の設計自体も同一記事の連投だった（当初仕様の見落とし）

## 修正（2026-08-17・選定ロジックは単体5ケース検証済み）
- `select_for_flush()` 純関数化: 直前に投稿した記事と同じarticle_idの候補はスキップして
  他候補（別記事・Tips）を優先。他候補が無ければ今回は見送り（次run以降に自然な間隔）
- 公開直後は「当該記事の1本のみ即時（prefer_article優先）+2本目はバックログ」へ変更
- Tips同士（article_id=None）は内容が別物なので連続許容

## 予防ルール（一般化）
- **バッチ生成→逐次消費のキューは「時間の分散」と「内容の分散」を別々に設計する**。
  FIFOは生成時の隣接性（同一ソースのバリエーション）をそのまま消費順に持ち込む
- 消費側に「直前と同じグループをスキップする」interleave則を入れるのが最小の対策
  （空になったら見送り = 分散が取れない時は出さない方がマシ、が原則）
