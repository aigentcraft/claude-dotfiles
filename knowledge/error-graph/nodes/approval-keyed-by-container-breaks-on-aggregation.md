## 1. Plan / Context

fukugyo-hootl で「同じ企業の会話を 1 つに束ねる」を実装していた。
設計書の手順は 1)本文を DB に貯める → 2)企業名で突き合わせる → 3)返信案に統合履歴を渡す →
4)案件ボードの投稿を企業単位へ寄せる、で、**4 を先にやるな**という警告まで書いてあった。

## 2. Do / The Error

4 に着手する前にコードを読んで、設計書が想定していなかった危険が見つかった。

```ts
// bot.ts — 押されたボタンから「何を承認したか」を決めている
await handlers.onApprove(interaction.channelId);

// store.ts — チャンネル（スレッド）ID で最初に見つかった 1 件を返す
allRecords().find((r) => r.discordThreadId === discordThreadId) ?? null;
```

4 を実装して 2 サイトの連絡を同じ投稿に寄せると、**2 つの記録が同じスレッド ID を持つ**。
どちらの返信案を承認しても `find` は先に見つかった方を返すので、

- ママワークス宛の下書きが**インディード経由で送られる**
- 承認していない方の下書きが送られる

が起こりうる。**送信は取り消せない。**

## 3. Check / Root Cause

不可逆操作の対象を**「入れ物」の識別子**（スレッド／チャンネル／ページ）で決めていた。
入れ物と中身が 1 対 1 のうちは正しく動くので、設計としての誤りが表に出ない。
**集約・統合・タブ化など「入れ物を共有する」変更が、この前提を静かに壊す。**

鍵を customId に載せる素朴な修正も塞がっていた。会話 ID が実測 **99 文字**で、
`approve:` を足すと Discord の customId 上限 100 文字を超える。

## 4. Act / Prevention Strategy (Fix)

**押された「そのメッセージ」の ID を鍵にする。**

1. 記録に `draftMessageId` を持たせ、下書きを投稿した時に必ず保存する
   （出し直し・救出・置き去り回収でも更新する。古い鍵を残すと押しても引けない）
2. `onApprove(channelId, draftMessageId)` にして、メッセージ ID → 記録 の順で引く
3. 鍵で引けず、かつ**そのスレッドに複数の記録がぶら下がっている時は送らない**。
   人に「特定できないので送らなかった」と返す
4. モーダル経由（非承認）にも ID を持ち越す。customId 上限に収まる長さであることを確認する

### 汎用ルール

> **不可逆操作の対象は「入れ物」ではなく「押された操作そのもの」から決める。**
> 入れ物（スレッド・チャンネル・ページ・フォーム）の ID は、中身が 1 つのうちだけ鍵として
> 機能する。集約・統合を入れる予定があるなら、**集約より前に鍵を直す**。

> **曖昧なまま不可逆操作をしない。** 一意に決まらなかった時は、
> 「たぶんこれ」で実行せず、実行しなかったことを人に伝える。

> **手順書に書かれた順序も検算する。** 「1→2→3→4 の順でやれ」と書いてあっても、
> 4 の前提が 1〜3 で満たされるとは限らない。特に**不可逆操作に触れる段**は、
> 着手前に「この変更で一意性が壊れる識別子はないか」を自問する。
