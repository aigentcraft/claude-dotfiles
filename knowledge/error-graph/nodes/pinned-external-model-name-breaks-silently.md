## 症状

自動生成メディアの**画像生成が丸ごと停止していた**。アイキャッチも図解も1枚も作れない。

エラーは全て同じ:

```
The model `gpt-5.5` does not exist or you do not have access to it.
```

**約18時間、誰も気づかなかった。** 気づいたのは人間が「通知の雰囲気がおかしい」と言ったから。

## 根本原因（2つある）

### 1. 外部CLIのモデル名を自分側で固定していた

画像生成は外部CLIのサブスク経由で動いており、呼び出しはこうなっていた:

```python
CODEX_MODEL = os.environ.get("CODEX_IMAGE_EXEC_MODEL", "gpt-5.5")
subprocess.run([BIN, "exec", "-m", CODEX_MODEL, ...])
```

`-m` の明示は、導入調査時（約1か月前）には**実際に必須**だった。その事実は
コメントにも残っていた。しかし提供側がモデルを改称し（CLIの設定ファイルの既定は
別名に変わっていた）、**こちらが固定した名前が404になった瞬間に全滅した**。

実測で確認したこと:

| 呼び出し | 結果 |
|---|---|
| 新しいモデル名を明示 | 通る |
| **`-m` を省略（CLI自身の設定に従う）** | **通る** |
| 旧モデル名を明示（現行実装） | **404 — 本番エラーの再現** |

### 2. 全損がグレース（縮退）に飲み込まれた

このシステムには「1枚撮れなくても記事を止めない」ためのグレース機構がある。
画像生成の失敗はその設計どおり1枚ずつ `warn` として記録され、記事は続行した。

しかし今回は**部分的な劣化ではなく100%の全損**だった。それでも
「個別の軽微な失敗がN件」としてしか記録されず、**介入要求は一度も出なかった**
（通知規約は「同一ステップが2run連続で失敗したら通知」だが、
グレースは *ステップの失敗ではない* ので、この条件に永久に該当しない）。

## 修正

```python
CODEX_MODEL = os.environ.get("CODEX_IMAGE_EXEC_MODEL", "")   # 既定を固定しない
_MODEL_ARGS = ["-m", CODEX_MODEL] if CODEX_MODEL else []      # 未設定なら渡さない
```

**モデル名の決定権を提供側（CLIの設定）に返す。** 明示したい時だけ環境変数で上書きする。
検証: 実際に画像を1枚生成し、日本語テキストが正しく描かれることを目視確認した。

## 予防ルール

- **外部サービスの「識別子」を自分側の既定値に固定しない。**
  モデル名・エンドポイント・APIバージョンは提供側が改称する。
  提供側が既定を持っているなら、**指定せずに委ねる**のが最も壊れにくい
  （明示は上書き手段として残す）
- **「導入時に必須だった」は永続的な仕様ではない。**
  必須だった理由をコメントに残すのは正しいが、それは*その時点の実測*であって
  未来の保証ではない。壊れたら再実測する
- **縮退（グレース）は部分的な劣化のための仕組みであって、全損の受け皿ではない。**
  同一種別の縮退が**連続・全件**発生したら、それは劣化ではなく障害。
  「N件中N件が失敗」を検知して介入要求へ昇格させる経路が要る
- **「エラー通知が来ない」を健全の証拠にしない。** 握り潰しの設計が入っている系では、
  沈黙は正常とも全損とも読める。**成功件数**を見る（0件が続いていないか）
