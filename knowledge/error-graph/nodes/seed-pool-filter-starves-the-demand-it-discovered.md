## 症状（Symptom）

weevee の週次キーワード調査（サジェスト回帰 → 全語のボリューム → 意図クラスタ → 競合全文）で、
その日に新しく見つけた **23 語すべてが Keyword Planner「データなし」**。
②ボリュームの段が 1 語も値を返さず、クラスタの並べ替えにも企画の優先順位にも寄与していなかった。

4 段階はどれも実際に動いており（SERP 指紋 21/21・競合 8 群 117,434 字・執筆まで到達）、
rc=0・テスト緑・Discord も静か。**「動いているのに効いていない」** ため誰も気づかなかった。
人間の「本当に動いてるの？」という問いで実データを数えて初めて出た。

## 根本原因（Root Cause）

段の故障ではなく **種（seed）の選び方**。

1. サジェスト回帰が見つけた語は `keywords.status='candidate'` で入る
2. 種を選ぶ `pick_seeds` も企画補充 02a も **`WHERE status='active'`** で絞る
3. candidate → active の昇格経路は「**企画に実際に使われたとき**」の 1 本しかない

結果、**自分が見つけた需要を自分で見えなくする**閉路ができていた。実測:

| 集合 | 未企画の語 | うち 100+/月 |
|---|---|---|
| `active`（種になれる） | 66 | 10（46 語が 0-9/月） |
| `candidate`（種になれない） | 153 | **20**（1,300 / 1,000 / 880 …） |

種は毎週 active の谷を掘り、そこから出るサジェストは当然ロングテールで「データなし」。
**掘るほど痩せる**。さらに GSC で実際に表示が付いたクエリは `kpi_snapshots` にしか入らず、
`keywords` には永久に来ないため、外から需要が補充される経路も無かった。

## 修正（Fix）

- `workers/shared/seed_supply.py` を新設（LLM 不使用・ネットワークに出ない・課金ゼロ）
  - `promote_candidates`: 実測ボリューム >= 100 かつ生きている企画が無い候補語を `active` へ
  - `promote_gsc_queries`: 直近 28 日で表示の付いたクエリを `keywords` に取り込む
    （`search_volume` には書かず `gsc_impressions_month` に分離。既存語は行を増やさず更新）
  - 自社名の除外は**掲載順位では切れない**（weevee 6.7 位 / we vee 64.5 位 / 非ブランドの
    claude code vps 60.3 位）ため、`GSC_SITE_URL` から導いたブランド名との**正規化編集距離**で判定。
    打ち間違い（wivvee 0.33 / wevei 0.33 / we vee 0.17 / weeve 0.17）を一覧に書き足す運用にしない
- **配線が本体**: **語を選ぶ処理は 2 つある** — 週次が通る `pick_seeds` と、02a の自前 SQL。
  02a は pick_seeds を**通らない**ので、両方の先頭で `replenish()` を呼ぶ（供給の実装は 1 つ）。
  `SEED_SUPPLY=0` で止まる
- `seed_supply.no_live_topic(alias)` を「未企画」の単一ソースにし、`pick_seeds` と 02a の直書き SQL を置換
- 外から数える検査 `seed_pool_has_the_demand` を `tools/daily_invariants.py` に追加
  （修正前の本番データで **20 語の赤を実測**してから採用）

実走: 候補語 20 語昇格 + GSC 由来 7 語。種の先頭が 880/月 → **1,300/月** に。

## 予防ルール（Prevention）

1. **発見したものを使う集合と、発見が入る集合を、違う状態で分けない。**
   「見つける」と「使える」の間に手動の昇格しか無い設計は、自分の発見を自分で捨てる。
   新しい状態（candidate / draft / pending 等）を足すときは、**そこから出る自動の経路**を同じコミットで書く。

2. **フィルタの内側が痩せていないかを、外側と比べて数える。**
   `WHERE status='active'` は単体では正しい。壊れているかは「弾かれた側に何が居るか」を
   数えて初めて分かる。絞り込みを書いたら、**弾かれた集合の分布を 1 回は見る**。

3. **「動いた」と「効いた」を別に数える。**
   この障害は fetched / errors / rc をいくら見ても緑だった。赤くなったのは
   「no_data 15/15」という**結果の分布**を見たときだけ。段ごとの成功数ではなく、
   その段が後段の判断に寄与した量を記録する。

4. **正しく動いている最中も赤が残る検査を作らない。**
   最初 1 回の昇格上限を 12 にしたため、20 語のうち 8 語が残り検査が赤のままになった。
   上限は「暴走止め」であって「絞り」ではない — 絞りは別の層（`--auto N`）が既に持っていた。
   閾値を足すときは「正常動作でこの検査は緑になるか」を実データで確かめる。

5. **ブランド語の除外を綴りの一覧で書かない。**
   打ち間違いは無限に増える。基準（サイト URL）から導き、距離で判定する。
   列挙で決めると次の綴りで静かに破れる。
