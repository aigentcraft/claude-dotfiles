## ユーザーの指摘（原文の意図）

「機械的なコード、ハードコードになってない？ llmのAIエージェントになってる？」

## 何が起きていたか

同じ日の朝、私は Q05/Q09 が4ラウンド落ち続けて記事が破棄された原因を
**「撮影カタログにハードコードされた状態が、記事の要求に届かないから」** と診断した。
その数時間後、通知を「機械的で状況が分からない」という指摘に応えて改善したのだが、
実装はこうなっていた:

```python
if always:                      # 全ラウンド共通の不合格項目がある
    lines.append("← 書き直しでは直らない問題（上流の能力不足）の疑い")
else:
    lines.append("・毎回違う項目で落ちています（書き直しの方向が定まっていない可能性）")
...
if n >= 5:
    lines.append(f"・{code} は直近7日で {n}件 不合格 — 慢性化しています")
```

**私が想定した2パターンの診断文を機械が選ぶだけ**で、想定外の状況では的外れなことを断言する。
`n >= 5` の 5 に根拠はない。**批判した構造をそのまま通知で再現していた。**

同様に:
- `run_pipeline`: 「このrunで走らなかった可能性が高い工程」を**固定リストで推測**していた。
  実際に何が走らなかったかはDBのイベントから事実として取れるのに
- `ops_audit`: 材料のラベルに「＝正常」「滞留と呼べるのは…だけ」と**結論を書き込んだ**。
  このファイルの docstring は「機械の仕事は生データの整形だけで、何が死んでいて何が仕様かは
  ops-auditorが毎朝判断する」と定めている（2026-08-23 の人間指摘で作られた設計）
- 移行計画 docs/12 の Phase 0 に自分で「凝った実装をしない。行数を増やさない」と書いたのに、
  63行の診断ロジック付き関数を追加していた

## 学び（Why）

- **線引き自体は間違っていなかった。事実の収集はPython、判断と説明はLLM。
  後半を実装者が奪っていただけ。** 「材料を集める」と「材料を解釈する」は別の仕事で、
  前者をやっているうちに後者へ手が伸びる
- **改善の実装は、批判した構造を再生産しやすい。** 「良い通知にしよう」と思うほど、
  作り手は自分の解釈を文面に埋めたくなる。それは相手（LLM・人間）から判断を奪う行為
- **固定文の診断は、想定内では親切に見え、想定外では自信を持って間違える。**
  カタログ・セレクタ・閾値・判定文はすべて同じ性質を持つ
- LLMに渡すと何が変わるか（実測）: editor-in-chief は同じ事実から、CLAUDE.md と
  移行計画を読んだ上で「これは既知の慢性課題で、Phase 2で根治予定だから今は撮影キーを
  足さずに予定通り進める」と書いた。**固定文には原理的に書けない接続**。コスト $0.156

## 適用方法（How to apply）

- **実装前に一度問う: これは「事実」か「解釈」か。** 解釈なら担当エージェントへ渡す。
  渡すのは目的・材料・受入条件（docs/12 原理1）で、結論の候補ではない
- **`if 条件: 断定文` の形を書いたら止まる。** それは判断のハードコード。
  条件と数値だけを材料に出し、断定は担当者に任せる
- **閾値を書くときは、それが「判定」なのか「機械的な足切り」なのかを区別する。**
  足切り（母数が無いものをLLMに渡さない等）は正当。判定はLLMの仕事
- **監視・監査の材料に結論を混ぜない。** 列の意味と仕様の説明までが材料。
  「＝正常」「〜だけ」と書いた時点で、監査役は自分で見る前に結論を渡されている
- **自分が今日書いた診断を、自分の実装に適用してみる。** 同じ形になっていたら作り直す
  （関連: ai-behavior R15「エージェントの所見は解釈。自分の原理を自分に適用する」）
