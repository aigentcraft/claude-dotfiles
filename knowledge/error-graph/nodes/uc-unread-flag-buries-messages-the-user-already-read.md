## ユーザー指摘（原文）
「Indeedの通知全く来てないけど、本当にちゃんと動いてる？」
（原因を示したあと）「未読のみだと、例えば私が自分で開いたメッセが拾われないしダメだね」

## 症状
常駐のログは毎回 `インディード: 新着なし（30 件を確認）` を出していた。
例外も警告も無く、30 件を読んでいるので**動いているように見える**。
しかし実際には、書類選考の質問や応募受付など**対応が要る連絡が一度も通知されていなかった**。

実測:
- 会話 30 件 / **未読 0 件**
- 通知済みの記録は **1 件だけ**
- 9/14 に届いた「書類選考の質問にご回答を」は既読のまま放置

## 根本原因
初見の会話を新着とみなす条件が `unreadCount > 0` だけだった。

```ts
if (!record) return c.unreadCount > 0;
```

導入時に過去の全会話を掘り返さないための判断で、意図は正しい。問題は
**「未読」がこちらの管理下にない状態**だったこと。利用者がスマホのアプリやブラウザで
先に開くとサーバ側で既読になり、以後この経路には二度と現れない。

**他人（この場合は利用者自身と外部サービス）が書き換える値を、自分の進捗管理に使っていた。**

## 修正
「未読」または「**最近（30 日以内）に相手から届いたもの**」を新着とする。
期間で区切ることで、導入時に過去を掘り返す問題は避けたまま、既読のものも拾える。
直後の巡回で 3 件を検出した（修正前は 0 件）。

## 予防ルール
1. **進捗の判定に、外部サービスや利用者が書き換える状態を使わない。**
   自分の DB に記録した「処理済み」で判定する。外部の状態は初期値の参考までに留める
2. 外部状態を使わざるを得ないなら、**それだけに頼らない**。時刻・ID など
   こちらで観測できる別の手がかりを併用する
3. **「N 件を確認 / 0 件処理」が続いたら異常を疑う。** 件数を読めていることは
   拾えていることの証明ではない（既存の原則 8 の再確認）
4. 利用者の「本当に動いてる？」には**実測で答える**。ログの読み上げは答えにならない。
   このときも DB と実受信箱を突き合わせて初めて穴が見えた
5. 関連: [[rate-limited-page-reads-as-zero-results.md]]（「0 件」が別の意味に化ける同型）
