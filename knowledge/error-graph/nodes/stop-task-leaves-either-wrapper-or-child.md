## 1. Plan / Context

Windows のタスクスケジューラで常駐を動かしている。
構成は `タスク → 起動スクリプト（run-watch.ps1）→ node`。
起動スクリプトを挟むのは、ログをファイルに書き、二重起動を止めるため。

停止は `uninstall-agent.ps1`（`Stop-ScheduledTask` → `Unregister-ScheduledTask`）。

## 2. Do / The Error

**停止したのにプロセスが残る。しかも残るものが毎回違った。**

| 状況 | 残ったもの | 見え方 |
|---|---|---|
| node が既に動いていた | **node**（起動スクリプトが先に死ぬ） | タスクは `Ready`。node だけが動き続ける |
| node をまだ起動していなかった | **起動スクリプト**（node は無い） | タスクは `Running`。**中身は何もしていない** |

後者が悪質だった。タスクが `Running` に見えるので、
**5 分ごとの見張りトリガーが「既に動いている」と判断して次を起動しない。**
止めたつもりのものが、永久に起動し直されない状態になる。

実測では起動スクリプトが CPU 0.39 秒・子プロセスなしで 3 分以上生きていた。

## 3. Check / Root Cause

`Stop-ScheduledTask` は**タスクのプロセス木を丸ごと終わらせない**。
どこまで届くかは、停止した瞬間にどこまで起動が進んでいたかで変わる。

同じ理由で `MultipleInstances = IgnoreNew` も当てにならない。
**タスク単位でしか効かず、孤児には効かない。**

## 4. Act / Prevention Strategy (Fix)

停止スクリプトで**親と子の両方**を明示的に終わらせる。

- 起動スクリプトを先に終わらせる（残したまま node を消すと、また起動しうる）
- 終わったことを**見てから**言う。残っていれば警告し、**非ゼロで返す**
- 掃除の順序は 起動スクリプト → node → ブラウザ
  （node を殺すと、その子のブラウザが掃除対象になる）

### 判定の広さを場面で変える（この件の核心）

同じ「常駐を見つける」でも、**何に使うかで正しい広さが逆になる**。

| 用途 | 判定 | 誤りの向き |
|---|---|---|
| 二重起動の門番（起動を**見送る**） | 広くてよい | 広すぎ＝起動しないだけ。安全側 |
| 停止（プロセスを**終わらせる**） | **狭くする** | 広すぎ＝**他プロジェクトの常駐を殺す** |

門番は `*index.ts*watch*` だけで見る。停止側はそれに加えてプロジェクトのパスで絞り、
**プロジェクト外の常駐は終わらせずに警告だけ出す**（黙って素通しにもしない）。

## 汎用ルール

> **「停止した」は、消えたことを見てから言う。**
> 停止命令が成功した ≠ プロセスが消えた。木の一部だけが死ぬことがある。

> **プロセスを探す判定は、用途ごとに広さを決める。**
> 起動を見送るための判定は広くてよく、終わらせるための判定は狭くなければならない。
> 同じ述語を使い回した瞬間に、どちらかが危険側に倒れる。

> **`Running` は「中身が動いている」を意味しない。**
> 親だけが生き残ると、タスクは正常に見えたまま何もしない。
> 生死の判定には、タスクの状態ではなく**実際の子プロセスか生存記録**を使う。
