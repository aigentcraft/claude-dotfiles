# push後の検品が旧デプロイに対して走った — 「200が返る」は「新ビルドが反映された」ではない

## 症状
プレビューblanchへpush→デプロイ待ちループ（HTTP 200で抜ける）→承認前検品、の流れで、
**push後わずか50秒**で検品が走り「修正済みのはずの欠陥」を検出してH01差し戻しした。
実際はCloudflare Pagesのビルド（1〜3分）が終わっておらず、**旧ビルドを検品していた**。
数分後に同URLを再測すると欠陥は解消済みだった。

## 根本原因
既存デプロイがある環境では、URLは**常に200を返す**（旧ビルドが配信され続ける）。
「200になったら反映済み」は初回デプロイでしか成立しない待ち条件だった。
以前は検品がなかったため実害が見えず（通知に「反映ラグあり」と書くだけで足りた）、
検品ゲートを足した瞬間にレースが顕在化した — **後段に判定を足す時は、
前段の完了条件がその判定に耐える精度かを見直す必要がある**。

## 修正
push**前**に配信中HTMLのsha256を記録し、push後は「200 かつ 内容ハッシュがpush前と
異なる」まで待つ（最大6分）。タイムアウト時は「差分なし再デプロイ（同一ビルド）」と
みなしwarnログを残して続行（その場合は配信中のものが正しい検品対象）。

## 予防ルール
1. **「新しい版が反映されたか」はステータスコードでなく内容の変化（ハッシュ・ビルドID・
   マーカー）で判定する**。旧版が生きている環境の200は何も保証しない。
2. デプロイ直後の自動検証・検品・スクショは、反映確認が取れるまで実行しない。
   反映確認が原理的に取れない場合（差分なし）はその旨をログに残して判断を分ける。
3. 誤fail時の状態復旧手順を持つ（今回: 差し戻されたarticleをreviewへ戻し再ゲート）。
