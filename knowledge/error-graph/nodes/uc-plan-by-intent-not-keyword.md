## 症状（Symptom）

さくら VPS × AI のサジェスト回帰（docs/07 §6）から企画 8 本（topics 26〜33）を立て、記事化に入ろうとしていたところで
ユーザー: **「各検索 KW で書くのではなく、同じ検索意図のものは 1 つの記事に統合して網羅する必要があるが、
そのように執筆されるようになっているか。穴の部分だけ書くようだと不足している。」**

実データを確認すると、8 本のうち **3 組が同じ検索意図**だった（`topics.search_intent` は DB の実値）:

- **26「さくらのVPSでLLMは動く？プラン別に実測」(review) + 27「さくらのVPSでAIを動かす3経路｜GPU不要の最短手順」(howto)**
  — どちらも「動くのか・GPU は要るのか・どう始めるのか」。読者は**両方読まないと answer が揃わない**（意図の前半と後半に分割していた）
- **30「Dockerを動かす最短手順」+ 31「Dockerでデプロイする手順」** — 読者にとって連続した 1 つの作業（Docker が動く状態は
  目的ではなく前提で、ゴールは 31 側にある）
- **32「VPS とクラウドの違い（どちらを契約すべきか）」+ 33「料金と SLA を AI 用途で読む」** — 契約前の同じ判断の表と裏

28（n8n）と 29（Dify）は対象製品が違うので別で正しい。つまり **8 本のうち 3 組 6 本が、キーワードの語数だけ増えた分割記事**だった。

## 根本原因（Root Cause）

1. **企画の単位がキーワードだった**。`02a_replenish_topics` / seo-strategist / `tools/suggest_matrix.py` の流れは
   「サジェストで面を取る → 用途の系統に割る → 系統ごとに企画」であり、**系統（用途語: ai / llm / docker …）を意図の代用にしていた**。
   docker 系統には「動かす」と「デプロイする」が同居するのに、意図で束ね直す工程がどこにも無かった。
   docs/07 §6.2 の絞り込みも「1 レーン = 1〜2 企画」という**数の制限**で、意図の判定ではない
2. **競合分析が「穴」を出す設計だった**。`competitor.gap_plan` が返すのは `missing_topics`（競合が扱い我々に無い論点）だけで、
   **上位競合が揃って扱っている論点（= その意図の必須要素）を出す口が無い**。06 の Q15（競合カバレッジ・2026-09-03 追加）も
   「穴を埋めたか」しか見ないため、**上位が普通に書いていることを飛ばして差分だけ書いた記事が合格してしまう**
3. **網羅性を検査する段が存在しなかった**。F 系（実測照合）・C 系（規約）・Q03（弁別性）・Q15（穴埋め）はあるが、
   「**この記事だけでその意図に答え切っているか**」「読者が同じ意図でもう 1 本読む必要が残っていないか」を問う項目が無い。
   意図が割れたまま企画が通り、割れたまま書かれ、割れたまま検閲を通過する経路が全段でつながっていた

構図としては [[uc-model-comparison-too-shallow-competitor-bypass]] と同じ — **競合分析の結果が採点に効いていない**問題の第 2 面。
前回は「超える方針が検閲されていなかった」、今回は「揃って書かれている前提が誰にも要求されていなかった」。

## 修正（Fix）

- **意図クラスタリング**: `workers/shared/intent.py`（純関数・LLM 不使用）— `cluster_by_intent(keywords)` が
  製品語 / 動作語（動かす・構築・デプロイ・設定）/ 判断語（違い・比較・どっち・料金・SLA・評判）/ 障害語（エラー・できない・重い）/
  対象語（n8n・Dify・Docker・LLM・GPU）でシグネチャを作って束ね、`intent_label(cluster)` が答えるべき問いを 1 文にし、
  `merge_candidates(topics)` が既存企画のシグネチャ衝突（= 統合候補）を返す。決定論にしたのは、同じ面から何度でも同じ束が出て
  統合の是非を後から検証できるようにするため。**束ねるのは機械・採否は seo-strategist の編集判断**（機械順選定への逆行禁止）
- **網羅性の 3 段契約**: ①企画 — `competitor.gap_plan` が `missing_topics` に加えて **`common_topics`（上位が揃って扱う必須要素）**
  を返し、outline は「必須要素をすべて含み、その上で穴を埋める」構成にする ②執筆 — writer / 04 の契約に
  「この記事だけで意図に答え切る。読者が同じ意図で別記事を読む必要が残ってはいけない」 ③検閲 — reviewer / 06 に
  **Q17 網羅性（重み 1.5）**（必須要素の欠落 / もう 1 本読む必要 / 別意図の詰め込みによる焦点のぼけ）+ 決定論ゲート
  （common_topics の未カバーが理由なしなら差し戻し — Q15 の `uncovered_without_reason` と同じ形）
- **既存 8 本の統合**: 26+27 / 30+31 / 32+33 を 1 本ずつに束ね直し（8 本 → 5 本）、outline は「両方の必須要素 + 両方の穴」。
  消える topic は `status='discarded'`（CHECK 制約に `'merged'` が無い）+ `workflow_events` に
  `event='topic.merged'` / `payload={"merged_into": <統合先 id>}` を残す。**行は消さない**（なぜ消えたかを辿れることが再発防止の記録）
- **記録**: docs/07 §7「意図で束ねる — 企画の単位はキーワードでなく検索意図」（判断基準・実例・3 段契約・統合の実務・落とし穴）と
  §6.2 の手順 2.5（系統に割った直後に意図で束ね直す）

C 系 / F 系の厳しさは変えていない。足したのは網羅性の検査だけ。

## 予防ルール（Prevention）

1. **企画の単位は検索意図。キーワードは素材であって記事の単位ではない**。KW が 8 語あっても意図が 5 つなら記事は 5 本
2. **1 本にする条件を機械可読な基準で持つ** — 意図が同じ = 1 本 / 読者の作業が連続 = 1 本 / 判断の表裏 = 1 本 / 対象製品が違う = 別。
   **記事タイプ（review / howto / comparison）の違いは分ける理由にならない**（型は 1 本の中の構成で表現する）。
   「長くなるから分ける」も理由にならない（分けるなら親が単独で答え切り、子は詳細を持つ）
3. **競合分析は「穴」と同時に「全員が書いていること」を出す**。差分（我々の実測）は必須要素の上に載せる価値であって、記事の骨格ではない。
   穴だけを埋める記事を作らせない
4. **面（サジェスト・KW 一覧）を取った直後に意図で束ね直す**。用途語の「系統」は意図ではない
5. **新しい検査を足すときは企画・執筆・検閲の 3 段すべてに配線する**。企画だけに書いたルールは生成物に現れず、
   検閲だけに置いたルールは差し戻しループになる（[[uc-model-comparison-too-shallow-competitor-bypass]] と同じ教訓）
6. **統合で消える企画は不可逆に消さない**。status の変更 + `merged_into` のイベントを残し、
   「破棄からの planned 返却」経路（[[discard-path-topic-requeue-leak]]）と区別できるようにする
7. 関連: [[uc-model-comparison-too-shallow-competitor-bypass]] [[uc-articles-too-advanced-for-beginner-readers]]
   [[uc-search-volume-missing-free-seo-stack]] [[uc-local-pattern-no-generalization]]

## 追記（2026-09-06 夜）— 主 signal を「語彙」から「SERP の重なり」へ格上げ

上の「修正」で書いた `workers/shared/intent.py`（語彙シグネチャ）**単独運用は初版**。実装直後に人間から次の提案があり、
**主従を差し替えた**（語彙 → SERP が主・語彙が従）。

> **「そのKWでの検索上位3つのうち、2つ以上が同じであれば同じクラスタとしてとらえるのでは対策として不足ですか？」**

### なぜ SERP のほうが優れているのか

**検索意図の判定は本来 Google の仕事で、SERP はその判定結果そのもの（グラウンドトゥルース）だから。**
語彙シグネチャは「Google の判定を自作の辞書（PLATFORM_RULES / SUBJECT_RULES / MODE_MARKERS）で近似したもの」でしかない。

| | 語彙シグネチャ | SERP 指紋 |
|---|---|---|
| 見るもの | KW 文字列 → 自作辞書への写像 | そのクエリで実際に返ってきた上位 URL |
| 判定者 | 自分（辞書の設計者） | Google（読者に答えを示している当事者） |
| 辞書に無い含意 | **取れない** | 取れる |
| 表記ゆれ・略語 | ルールを足した分だけ | 自動で吸収 |
| 再現性 | 完全 | 取得日に依存 |
| コスト | 0 | 検索 1 リクエスト / KW |

- **含意が取れるのが決定的**: 「スマホ Claude Code 操作」は語彙上どこにも VPS が出てこないが、実態は
  **リモート VPS に常駐させてスマホから叩く**話で、SERP は VPS 記事で埋まる。辞書に「スマホ → VPS」と書かない限り語彙では永遠に取れない。
  **読者の言葉と答えの場所がずれている KW ほど、SERP でしか束ねられない**
- **辞書のメンテ漏れで静かに劣化しない**: 新製品が出るたび語彙を足す運用は、足し忘れた瞬間に品質が落ちるのに誰も気づかない
- **競合分析と同じ土台に乗る**: 上位 URL は `competitor.top_pages` が見るものと同じ。統合の是非と「超える方針」を同じ証拠で語れる
- **実データでも一致した**: 2026-09-06 の企画バッチの競合レポートで、人間が「同じ意図」と指摘した組は SERP でも重なっていた
  （26「さくら VPS LLM」× 27「さくらのVPS AI」= 共通 4 URL・うち非ベンダーの記事級 `note.com/miccell/…` を含む /
  30「さくらのVPS Docker」× 31「さくら VPS docker デプロイ」= 共通 3 URL・うち非ベンダー 1 件）

### それでも SERP 単独では足りない 5 点とガード

**誤統合は誤分割より重い事故**（意図の違う記事が 1 本に潰れ、どちらの答えも出なくなる）。ガードは全て「迷ったら結合しない」側に倒す。

| # | 弱点 | 具体例・何が起きるか | ガード |
|---|---|---|---|
| ① | **ベンダー占有 SERP** | **「さくらのVPS 料金」と「さくらのVPS ログイン」は意図が正反対**（契約前の判断 ↔ 契約後のアカウント操作）なのに、どちらも `vps.sakura.ad.jp` / `secure.sakura.ad.jp` / `knowledge.sakura.ad.jp` の公式ページが上位を占め、**URL が重なって誤統合する**。実際 2026-09-06 の調査で「さくらのVPS AI」の SERP は公式占有（記事級 1 件のみ）だった | 共通 URL のうち **1 件以上がベンダー以外**であることを結合条件に追加（`same_intent(..., vendor_domains=...)`）。公式だけの重なりでは結合しない |
| ② | **未成熟 SERP** | 新語・発表当日は記事級が薄く、上位が公式と噂で埋まる。重なっても「同じ意図」の意味が弱い（`competitor.MIN_ARTICLE_PAGES=2` 未満の既存判定と同じ状況） | どちらかの指紋が **空 / 1 件**なら結合しない。未成熟 KW は語彙側で補う |
| ③ | **ドメイン単位だと全部同じになる** | qiita.com / note.com / zenn.dev は無関係な記事同士でも一致する。「Qiita が上位にいる KW」が全部 1 群になる | **URL 単位で比較**。domains は監査表示・ベンダー判定にだけ使う |
| ④ | **推移的結合の暴走** | A〜B・B〜C が成立すると union-find は A〜C も同群にする。橋渡しの 1 語で無関係な語まで飲み込み巨大クラスタができる | 群サイズ上限 `SERP_CLUSTER_MAX`（既定 6）。超えた群は**破棄せず「要確認」フラグ**を立てて編集判断に見せる（機械が黙って捨てない） |
| ⑤ | **SERP は動く** | 今日の束は 1 か月後には違う。古い指紋のまま統合を続けると、根拠が実在しない状態で企画が固定される | `keyword_serps.fetched_at` を必ず持ち、`SERP_TTL_DAYS`（既定 30）超過で再取得。企画根拠は**取得日つき**で書く |

- URL 正規化のずれも誤判定の温床（スキーム・`www.`・末尾スラッシュ・`?utm_*` 等のトラッキングパラメータ・フラグメント）。
  指紋化の時点で正規化し、**フラグメントは削除**する（`#section` 違いは同じページ）
- 各群に `evidence`（根拠 URL）を残す。**なぜ同じ意図と判定したかを後から検証できない束は採用しない**

### 取得コストと TTL（無料枠を焼かないための設計）

- **`jina_client.search` だけを使う。`read`（本文取得）は使わない** — 指紋に必要なのは顔ぶれ（URL の並び）だけ。本文は競合分析が別途取る
- 1 KW = 1 リクエスト（`num=10` で取り、比較は上位 3 件）。10 件保存するのは、後で `top` を 3→5 に変えても再取得せずに済むため
- **1 実行の取得上限 `SERP_MAX_FETCH`（既定 40 KW）を必ず持つ** — 面（サジェスト回帰）を取った直後は KW が数百件になる。
  上限なしの取得を走らせるとクォータを企画 1 バッチで焼く
- **TTL `SERP_TTL_DAYS`（既定 30）** — 期限内は保存済み指紋を再利用し、超過分だけ取り直す。同一キーワードは最新 1 行（UPSERT・履歴は持たない）
- **取得失敗は空指紋にして落とさない** — キー未設定・API 障害で企画パイプラインを止めない。
  空指紋はガード② で自動的に「結合しない」に倒れるので、失敗が誤統合に化けない

### 語彙（`intent.py`）の位置づけ — 捨てずに「従」に降ろす

1. **指紋が無い / 未成熟な KW を補う**（新語・ロングテール・取得上限超過分）
2. **ネットワーク非依存の土台** — キー無し・オフライン・テストで同じ束が出る（テストはネットワークをモックする）
3. **束の説明を作る** — SERP は「同じ URL が出た」としか言わない。答えるべき問いを 1 文にするのは `intent_label` の仕事
4. **SERP の変動に対する錨** — 先月と束が変わったとき、**変わったのは SERP か我々の解釈か**を切り分けられる

**優先順位は固定**: ①SERP で同じ（ガード全通過）= 統合候補 ②語彙だけで同じ = 「候補（語彙のみ）」（統合するなら理由を 1 行書く）
③どちらでも同じでない = 別記事。**語彙が SERP を上書きしない**（SERP が「別」と言うものを語彙一致で統合しない）。

### 追加の予防ルール

8. **「自分の辞書で近似できる」と思ったら、その判定を既にしている当事者がいないか探す**。検索意図は Google が毎日判定して
   SERP に出している。**外部のグラウンドトゥルースがある領域で自作ヒューリスティクスを主 signal にしない**（従・フォールバックには使う）
9. **強い signal に乗り換えるときは、その signal 固有の壊れ方を先に列挙してガードを書く**。SERP なら
   ①ベンダー占有 ②未成熟 ③粒度（ドメイン vs URL）④推移的結合 ⑤時間変化。**ガードのない乗り換えは前より悪化する**
10. **統合系の判定は「迷ったら結合しない」に倒す**。誤統合（意図の違う記事が 1 本に潰れる）は誤分割より回復しにくい
11. **外部 API を判定に使うときは、1 実行の取得上限・TTL・失敗時の挙動を同時に決める**。上限なしの取得と、
    失敗時に例外を投げる実装は、どちらも本番で必ず事故る（失敗は「結合しない」側に倒れる無害な値にする）
12. **機械が出した束には必ず `evidence` と取得日を持たせる**。根拠を再現できないクラスタリングは、
    1 か月後に「なぜこれが 1 本なのか」を誰も説明できなくなる
13. **主 signal を差し替えても「機械は候補、採否は編集判断」は変えない**（[[uc-mechanical-automation-wastes-llm-metacognition]] と同じ原則）

実装は `workers/shared/serp.py` + migration 015 `keyword_serps` + `tools/kwcli.py serp-cluster`。

## 実測で設計が変わった 2 点（2026-09-06・さくら×AI の 28 KW を Jina で実取得）

設計だけで書いたガードは、実データで**片側にしか効いていなかった**。実走の結果は
**28 KW → 11 束（serp 由来 5 / lexical 由来 6）・「要確認」群 0**。

### ① ベンダー占有は「誤統合」だけでなく「**誤分割**」も起こす → ガードを 2 層にした

当初のガード①は「共通 URL の少なくとも 1 件はベンダー以外」だけだった。実測すると
**28 KW 中 20 KW の上位 3 件が全部 `sakura.ad.jp`**（vps / knowledge / manual / secure / help のサブドメイン）で、
日本の VPS 系 KW では公式ドキュメントが強すぎて「上位が全部公式」が**普通の状態**だった。その結果:

- 「さくらのvps 料金」と「さくら vps 料金」は上位 3 件が**完全一致**（`vps.sakura.ad.jp/specification` /
  `vps.sakura.ad.jp` / `vps.sakura.ad.jp/windows`）なのに、全部公式なのでガード①に弾かれて**別の束になった**
- 人間が「同じになるはず」と指定した「さくらのvps ai」×「さくら vps llm」も、共通 URL は
  `knowledge.sakura.ad.jp/50023`（公式）の **1 件だけ**。閾値 2/3 にも届かず、ガード①にも弾かれた

**修正**: 指紋そのものを見る第 2 層 `is_vendor_dominated(fp, vendor_domains)` を足した。上位が**全部**その製品の
公式ページなら、その SERP は第三者記事を一切区別していない = **重なりも「重ならなさ」も意図の証拠にならない**。
そこで「SERP では判定できない」（`serp_ready=False` / `unusable='vendor'`）として語彙にフォールバックする。
結果、受け入れ条件が両方通った — 料金（`decide`）と ログイン（`nav`）は語彙の mode で分かれ、
ai / llm / gpu は語彙の subject（`ai-runtime`）で 1 束になった。

**一般化した予防ルール**:

14. **ガードは「誤って YES にする」側だけでなく「誤って NO にする」側も点検する**。
    弾くだけのガードは、その signal が使えない領域で**全部を弾いて**しまい、フォールバックへの道を塞ぐ。
    「判定材料が無い」と「判定した結果 別だった」は**別の状態**として持つ（`unusable` を返り値に持たせる）
15. **ガードの効き目は実データでしか分からない**。「公式が上位を占めることがある」と「上位が全部公式なのが普通」は
    設計上は同じ一文だが、実装の正解が変わる。**受け入れ条件は実取得して確かめてから配線を有効にする**

### ② キャッシュの鍵から空白を落としてはいけない（別クエリが 1 行に潰れる）

`keyword_serps.kw_norm` に既存の `intent.normalize`（NFKC + 小文字 + **空白を全部除去**）を流用したところ、
「さくらのvps n8n」と「さくら の vps n8n」が同じ鍵（`さくらのvpsn8n`）になり、**後から取った方が前の指紋を上書き**した。
実測ではこの 2 クエリは**上位 1 位が別ページ**（`vps.sakura.ad.jp/contents/startup-script/vps-ss-n8n` と
`sakura.ad.jp/corporate/…/announcements/…`）で、Google にとって空白は意味がある。

**修正**: `serp.normalize_keyword`（NFKC + 小文字 + **空白は 1 個に圧縮**）を別に定義した。
表記ゆれ（全角/半角・大小文字）だけを畳み、語の区切りは保つ。

**一般化した予防ルール**:

16. **既存の正規化関数を別目的に流用しない**。`intent.normalize` は**素性抽出**用（空白は素性ではない）、
    SERP キャッシュの鍵は**クエリ同一性**用（空白はクエリの一部）。同じ「正規化」という名前でも
    **落としてよいものが違う**。流用する前に「この関数が捨てている情報は、新しい用途で捨ててよいか」を問う
17. **キャッシュの鍵の設計ミスは、静かにデータを壊す**（例外もログも出ず、片方の値が消えるだけ）。
    鍵を決めたら「**異なる入力が同じ鍵に落ちないか**」をテストで固定する
    （`tests/test_serp.py::test_keyword_normalization_keeps_distinct_queries_apart`）
