## 症状（Symptom）

さくら VPS × AI のサジェスト回帰（docs/07 §6）から企画 8 本（topics 26〜33）を立て、記事化に入ろうとしていたところで
ユーザー: **「各検索 KW で書くのではなく、同じ検索意図のものは 1 つの記事に統合して網羅する必要があるが、
そのように執筆されるようになっているか。穴の部分だけ書くようだと不足している。」**

実データを確認すると、8 本のうち **3 組が同じ検索意図**だった（`topics.search_intent` は DB の実値）:

- **26「さくらのVPSでLLMは動く？プラン別に実測」(review) + 27「さくらのVPSでAIを動かす3経路｜GPU不要の最短手順」(howto)**
  — どちらも「動くのか・GPU は要るのか・どう始めるのか」。読者は**両方読まないと answer が揃わない**（意図の前半と後半に分割していた）
- **30「Dockerを動かす最短手順」+ 31「Dockerでデプロイする手順」** — 読者にとって連続した 1 つの作業（Docker が動く状態は
  目的ではなく前提で、ゴールは 31 側にある）
- **32「VPS とクラウドの違い（どちらを契約すべきか）」+ 33「料金と SLA を AI 用途で読む」** — 契約前の同じ判断の表と裏

28（n8n）と 29（Dify）は対象製品が違うので別で正しい。つまり **8 本のうち 3 組 6 本が、キーワードの語数だけ増えた分割記事**だった。

## 根本原因（Root Cause）

1. **企画の単位がキーワードだった**。`02a_replenish_topics` / seo-strategist / `tools/suggest_matrix.py` の流れは
   「サジェストで面を取る → 用途の系統に割る → 系統ごとに企画」であり、**系統（用途語: ai / llm / docker …）を意図の代用にしていた**。
   docker 系統には「動かす」と「デプロイする」が同居するのに、意図で束ね直す工程がどこにも無かった。
   docs/07 §6.2 の絞り込みも「1 レーン = 1〜2 企画」という**数の制限**で、意図の判定ではない
2. **競合分析が「穴」を出す設計だった**。`competitor.gap_plan` が返すのは `missing_topics`（競合が扱い我々に無い論点）だけで、
   **上位競合が揃って扱っている論点（= その意図の必須要素）を出す口が無い**。06 の Q15（競合カバレッジ・2026-09-03 追加）も
   「穴を埋めたか」しか見ないため、**上位が普通に書いていることを飛ばして差分だけ書いた記事が合格してしまう**
3. **網羅性を検査する段が存在しなかった**。F 系（実測照合）・C 系（規約）・Q03（弁別性）・Q15（穴埋め）はあるが、
   「**この記事だけでその意図に答え切っているか**」「読者が同じ意図でもう 1 本読む必要が残っていないか」を問う項目が無い。
   意図が割れたまま企画が通り、割れたまま書かれ、割れたまま検閲を通過する経路が全段でつながっていた

構図としては [[uc-model-comparison-too-shallow-competitor-bypass]] と同じ — **競合分析の結果が採点に効いていない**問題の第 2 面。
前回は「超える方針が検閲されていなかった」、今回は「揃って書かれている前提が誰にも要求されていなかった」。

## 修正（Fix）

- **意図クラスタリング**: `workers/shared/intent.py`（純関数・LLM 不使用）— `cluster_by_intent(keywords)` が
  製品語 / 動作語（動かす・構築・デプロイ・設定）/ 判断語（違い・比較・どっち・料金・SLA・評判）/ 障害語（エラー・できない・重い）/
  対象語（n8n・Dify・Docker・LLM・GPU）でシグネチャを作って束ね、`intent_label(cluster)` が答えるべき問いを 1 文にし、
  `merge_candidates(topics)` が既存企画のシグネチャ衝突（= 統合候補）を返す。決定論にしたのは、同じ面から何度でも同じ束が出て
  統合の是非を後から検証できるようにするため。**束ねるのは機械・採否は seo-strategist の編集判断**（機械順選定への逆行禁止）
- **網羅性の 3 段契約**: ①企画 — `competitor.gap_plan` が `missing_topics` に加えて **`common_topics`（上位が揃って扱う必須要素）**
  を返し、outline は「必須要素をすべて含み、その上で穴を埋める」構成にする ②執筆 — writer / 04 の契約に
  「この記事だけで意図に答え切る。読者が同じ意図で別記事を読む必要が残ってはいけない」 ③検閲 — reviewer / 06 に
  **Q17 網羅性（重み 1.5）**（必須要素の欠落 / もう 1 本読む必要 / 別意図の詰め込みによる焦点のぼけ）+ 決定論ゲート
  （common_topics の未カバーが理由なしなら差し戻し — Q15 の `uncovered_without_reason` と同じ形）
- **既存 8 本の統合**: 26+27 / 30+31 / 32+33 を 1 本ずつに束ね直し（8 本 → 5 本）、outline は「両方の必須要素 + 両方の穴」。
  消える topic は `status='discarded'`（CHECK 制約に `'merged'` が無い）+ `workflow_events` に
  `event='topic.merged'` / `payload={"merged_into": <統合先 id>}` を残す。**行は消さない**（なぜ消えたかを辿れることが再発防止の記録）
- **記録**: docs/07 §7「意図で束ねる — 企画の単位はキーワードでなく検索意図」（判断基準・実例・3 段契約・統合の実務・落とし穴）と
  §6.2 の手順 2.5（系統に割った直後に意図で束ね直す）

C 系 / F 系の厳しさは変えていない。足したのは網羅性の検査だけ。

## 予防ルール（Prevention）

1. **企画の単位は検索意図。キーワードは素材であって記事の単位ではない**。KW が 8 語あっても意図が 5 つなら記事は 5 本
2. **1 本にする条件を機械可読な基準で持つ** — 意図が同じ = 1 本 / 読者の作業が連続 = 1 本 / 判断の表裏 = 1 本 / 対象製品が違う = 別。
   **記事タイプ（review / howto / comparison）の違いは分ける理由にならない**（型は 1 本の中の構成で表現する）。
   「長くなるから分ける」も理由にならない（分けるなら親が単独で答え切り、子は詳細を持つ）
3. **競合分析は「穴」と同時に「全員が書いていること」を出す**。差分（我々の実測）は必須要素の上に載せる価値であって、記事の骨格ではない。
   穴だけを埋める記事を作らせない
4. **面（サジェスト・KW 一覧）を取った直後に意図で束ね直す**。用途語の「系統」は意図ではない
5. **新しい検査を足すときは企画・執筆・検閲の 3 段すべてに配線する**。企画だけに書いたルールは生成物に現れず、
   検閲だけに置いたルールは差し戻しループになる（[[uc-model-comparison-too-shallow-competitor-bypass]] と同じ教訓）
6. **統合で消える企画は不可逆に消さない**。status の変更 + `merged_into` のイベントを残し、
   「破棄からの planned 返却」経路（[[discard-path-topic-requeue-leak]]）と区別できるようにする
