## 症状（Symptom）

weevee の X トレンド収集は、公式発表を見つけると「⚡ release シグナル」を Discord に出し、
速報レーン（`tools/breaking.py`）を切り離し起動して定時を待たずに記事を作る設計だった（人間決定⑫）。
人間の指示「アラートが出たときに、スケジュールに関係なく記事を作成するようにして」を受けて実績を数えると、
**アラート 8 件のうち、定時を待たずに記事（承認待ち）まで届いたのは 1 件だけ**だった。

| 行方 | 件数 | 起きたこと |
|---|---|---|
| 承認待ちまで到達 | 1 | 約 2 時間で届いた |
| 途中で止まり定時に回った | 2 | 公開は 3.5 日後・7 日後（原因は当時の既知障害） |
| 企画段で例外終了 | 3 | 企画担当の出力が検査で弾かれ、`ValueError` で落ちた |
| 「手で起動して」の通知だけ | 2 | 日次上限 1 に当たった。1 件はその後も未着手 |

Discord に届いていたのは「**速報レーンを自動起動しました**」だけ。その後の成否は誰にも届かなかった。

## 根本原因（Root Cause）

1. **起動を知らせて、結果を知らせない。** 02_listen は `subprocess.Popen` で切り離した時点で
   「自動起動しました」を送り、以後そのプロセスを見ない。起動された側（breaking.py）は、
   企画段の例外もロック待ちの時間切れも**ログファイルに traceback を残して終わるだけ**。
   切り離したプロセスの失敗は、書いた側が通知しない限り、構造上どこにも出ない。
2. **直せる不備で即死する。** 3 件の例外はどれも「title_draft / outline が空」「docs/11 の必須要素が無い」で、
   理由を言えば企画担当が直せる種類だった。1 回で弾いて終わりにしていた。
3. **上限で「通知だけ」にする＝機械が「書かない」を決めていた**（人間決定⑮に反する形）。
   日次上限 1 は安全策のつもりだったが、超えた分は記事にならず、人が手で起動しない限りそのまま消えた。
4. **定時の記事生産が走っている間は、ロックが空くまで最大 2 時間半待つ**。定時側は速報が待っていることを知らない。

## 修正（Fix）

- 起動された側で、失敗を**全部**拾って ops に通知する（`main` を包み、`Exception` と `SystemExit` を捕まえる）。
  通知には「何のアラートか・理由・やり直しのコマンド」。企画ができた後なら `--topic-id N --resume`
  （`--signal-id` でやり直すと企画が二重にできる）
- 企画の検査で落ちたら、**弾いた理由を渡して 1 回だけ再提出**させる。2 回目も駄目なら理由つきで上へ
- 日次上限の既定を 0（上限なし）に。同時のアラートはパイプラインのロックで直列に進む。戻すなら env 1 行
- 速報がロックを待つ間は `.breaking-wait-<pid>` を置き、定時の記事生産は**次の 1 本に着手せず譲る**
  （進行中の 1 本と後段は完走させる。後段まで飛ばすと月曜朝の週次まとめが抜けるため）。
  印の持ち主が死んでいれば無視して掃除する（kill の残骸で永久に譲り続けない）
- 外から数える検査 `alerts_became_articles`: アラートから 8 時間で記事が承認待ち以降に届いていなければ赤。
  窓を 21 日に広げた本番データで、上の「記事にならなかった 5 件」を正確に拾うことを確認

## 予防ルール（Prevention）

1. **切り離して起動したら、起動された側が自分の結果を報告する。** 起動側の「起動しました」は
   「届きました」ではない。`Popen` で手放すなら、子の最上位で全例外を捕まえて通知する。
2. **「起動した」ではなく「成果が出たか」を外から数える。** 起動件数・rc ではなく、
   アラート 1 件ごとに「記事が承認待ちまで届いたか」を数える。
3. **検査で弾くときは、理由を持ち主に返す。** LLM の出力を正規表現で弾くなら、理由を渡して出し直させる経路を同時に書く。
   即死させるのは、直しようのない不備（法令・不可逆・物理）のときだけ。
4. **上限を足すなら、超えた分の行き先を決める。** 「超えたら通知だけ」は、通知を見た人が動かない限り消える。
   直列化（待たせる）か、次の枠への繰り越しにする。
