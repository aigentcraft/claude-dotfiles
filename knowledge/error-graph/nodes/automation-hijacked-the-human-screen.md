## 1. Plan / Context
初回ログインだけは人間が行う設計。エージェントはブラウザを開いて待ち、
ログインが成立したかをポーリングで監視する。

ログイン完了後に判定できないページへ着地した場合に備え、
「判定不能かつログイン画面を離れていたら、判定用ページへ移動して確認する」
という保険を入れていた。

```ts
if (state === 'unknown' && !page.url().includes('/login')) {
  await page.goto(adapter.probeUrl);
}
```

## 2. Do / The Error
2 サイト目（Indeed）で有人ログインを試した利用者から:

> ログインしようとしたら1秒ごとくらいにページ更新が連続でされて何も操作できなかった

## 3. Check / Root Cause
抑止条件が **1 サイト目の URL の形に依存**していた。

  - 1 サイト目: ログイン画面は `example.jp/login` → `/login` を含むので抑止が効く
  - 2 サイト目: 手続きは `secure.indeed.com/auth` → **`/login` を含まない**

さらにその画面には判定用セレクタが無いので、状態は毎回 `unknown`。
結果、条件が常に成立し、**1.5 秒ごとに利用者の入力画面が飛ばされ続けた**。

根本は「自動処理が、人間が操作中の画面を触る設計にしていたこと」。
抑止条件を足すのは対症療法で、条件が外れれば同じことが起きる。

## 4. Act / Fix & Prevention
**判定専用のタブを別に開き、利用者の画面には一切触らない**構造に変えた。
Cookie はブラウザコンテキストで共有されるので、別タブで確認すれば足りる。

  - 利用者の画面は「読むだけ」（通信も遷移も起こさない）
  - 判定用タブは要求を投げるので間隔を空ける（サイトのレート制限を避ける）

### 予防ルール

1. **人間が操作している画面を、自動処理が触らない。**
   触らざるを得ないなら、触ってよい条件ではなく**触らない構造**を先に探す。
   ここでは「別タブを開く」で完全に分離できた。
2. **抑止条件を特定サイトの URL の形に依存させない。**
   1 サイトでしか検証していない条件は、2 サイト目で必ず外れる。
3. **「判定できない」が続く経路は、無限に同じ処理を繰り返す。**
   `unknown` が固定される可能性を前提に、回数や間隔の上限を置く。
