## 症状

人間の「最近ちゃんと稼働できてる？」で調べて発覚。定時タスクはすべて「正常終了」だった。

| 実測（2026-10） | |
|---|---|
| 承認回収（15分毎）が日次処理を丸ごと再起動した回数 | **約380回**（10/6〜8・10/10〜12。9/22〜23 にも約80回） |
| 深夜0時以降に繰り返された朝の工程 | X画面観測・市場感知・知識整理が**1晩に約24回** |
| X 投稿 | 10/12 01:13〜05:50 に tips を**15分おきに18本** |
| 朝5時の定時run | 「別のパイプラインが実行中」で**3回スキップ** |
| LLM 呼び出し | 通常の3〜5倍の日が3日 → Claude の週の上限に2回到達（一因の可能性が高い） |

ops-auditor は「run 起動が1日77〜95回」を4回報告していたが、すべて「要確認」止まりで原因を追わず、
18本の連投も「排出が1日1本程度か要確認」と見落としていた。

## 何が起きていたか

1. リライトレーン（run_pipeline.start_rewrite_if_any）は着手時に **H01**（新しい執筆サイクルの開始）を書く。
   review_rounds() に過去サイクルの検閲を数えさせないための、正しい使い方
2. 承認回収の自己回復 rework_pending() は「最新 H01 の後に検閲が無い draft」を
   「人間が差し戻したのに書き直しが始まっていない」と読み、run_pipeline を**引数なしで丸ごと**起動していた
3. リライトの書き直しが**画像の利用上限**で進まない間、この条件は真のまま → 15分ごとに丸ごと起動
4. run_pipeline は「hour < 9 なら朝の工程」を走らせる。深夜0時を過ぎると毎回の起動が朝runになり、
   1日1回の前提で書かれた工程（観測・傾聴・知識整理・月曜の週次X計画→投稿の排出）が繰り返された
5. そのプロセスが .pipeline.lock を握るので、本物の朝5時の run はロックで退出した

**9/10 に同じ型を一度直していた**（[[gate-rejection-recorded-as-human-sendback-reset-the-limit]]）。
そのときは H01 を書く書き手の1つ（06b のゲート差し戻し）を G01 に分けたが、もう1つの書き手
（リライトレーン・8/13〜）が残っていた。「H01 は人間差し戻し専用に戻す」と書いたのに、
書き手を数え上げて潰す直し方だったため、数え漏れがそのまま再発の経路になった。

## 修正（2026-10-16）

- **「誰が書いたか」で判定する**: 自己回復は記録者が人間（reflections.agent='human'）の H01 だけを見る。
  書き手を列挙して除外する方式をやめた（H01 を書く処理が増えても催促しない）
- **起動するのは書き直しだけ**: `run_pipeline --rework <記事ID>`（記事レーンのみ。通知・完走記録・朝の工程は触らない）
- **進めない間は起動しない**: Claude / 画像の利用上限中、他の run の実行中は見送る（試行に数えない）
- **回数上限**: 同じ差し戻しにつき自己回復の起動は最大2回。超えたら1回だけ warn を残し、定時runの途中再開に任せる
- 本番DBの複製で 10/10 の状態を再現 → 旧判定「起動する」/ 新判定「起動しない」。人間の差し戻しは従来どおり拾う
- 独立レビューの指摘で追加: 書き直し専用runが 05:00 にロックを握ると、定時runは退出して朝の工程が丸1日飛ぶ
  （以前は丸ごとのrunだったので中で走っていた）→ ロックに run の種類を書き、定時runは書き直しrunの終わりを最大1時間待つ。
  上限に達した記事が先頭にいると後ろの差し戻しが永久に拾われない → 一覧を順に見る

## 予防ルール

- **自己回復（取りこぼしの拾い直し）には、回数の上限と「進めない理由がある間は起動しない」を必ず付ける。**
  拾い直しは「前回は偶然流れた」前提の仕組みで、決定論的に進めない状態では無限ループの原動力になる
- **意味を持つマーカーの読み手は、書き手を数え上げて除外せず、書き手の種類そのもので判定する。**
  書き手は後から増える。9/10 の直し方（1つ分けた）は、もう1つの書き手で再発した
- **定時の前提で書かれた処理を、別の契機から丸ごと呼ばない。** 1日1回が前提の工程には日次ガードが無いことが多い。
  別の契機から呼ぶなら、必要な工程だけの入口（--rework 等）を作る
- **監視が「起動回数が異常」を出したら、回数ではなく起動元を辿る。** 回数は症状で、要確認のまま置くと
  同じ報告が4回並ぶだけになる
- **入口を分けたら、分けた側がロックを握っている時に、元の側（定時run）が何を飛ばすかを確かめる。**
  丸ごとのrunが「ついでに」担っていた工程は、入口を絞ると誰も担わなくなる
