## 症状（Symptom）

pullie x/08_followers の相手リサーチ（searchUsers）でクエリ「業務改善 情シス」だけが
**導入日（8/17）から毎回 HTTP 400**。warn止まりのグレーススキップだったため止血はされていたが、
2クエリ中1クエリが死んだまま3日間、リサーチレーンが半減稼働していた。

## 根本原因（Root Cause）

X API `GET /2/users/search` の query パラメータは
**`^[A-Za-z0-9_' ]{1,50}$` に一致する必要がある（= ASCII英数字のみ・日本語は仕様として不可）**。
エラーdetailに正規表現がそのまま書かれていたが、DBログが150字で切り詰められており
肝心の正規表現部分が欠落 → 「なぜかこのクエリだけ失敗する」に見えていた。

## 修正（Fix）

- RESEARCH_QUERIES を ASCII語へ変更: `["kintone", "業務改善 情シス"]` → `["kintone", "cybozu"]`
  （cybozu = エコシステム名。実走でCybozu公式系12候補を取得し狙った母集団と確認）
- API仕様の正規表現をコードに焼き込み（`SEARCH_QUERY_RE`）、仕様外クエリは
  **APIに投げる前に理由つきwarnでスキップ**（境界バリデーション — 編集ミスの再発を即知らせる）

## 予防ルール（Prevention）

1. **外部APIの4xxは「エラーが出た」でなくdetail全文を読む** — バリデーション系はdetailに
   仕様（正規表現・許容値）がそのまま書いてあることが多い。ログの切り詰め幅（150字等）が
   診断情報を落とすなら、直接再現して全文を取る
2. **恒久的に失敗し続けるwarnはエラーと同格** — グレーススキップで全体が動いていても、
   同一箇所のwarnがN日連続なら仕様違反を疑う（初回から一度も成功していない機能は
   コードでなく前提を疑う — [[x-api-reply-restriction-403]]と同じ教訓）
3. 判明したAPI仕様の制約は**呼び出し側コードに正規表現ごと焼き込み**、投げる前に検証する
