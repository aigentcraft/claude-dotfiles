## ユーザー指摘（原文）
「やっぱここに問題がありました、今度はこっちに問題がありました、を永遠に繰り返しているのはなんで？
どうしたらちゃんとしたものが作れるの？」

## 直前 48 時間の連鎖（事実）
記事 20 の往復 → 差し戻し理由が run_id='' で届かない → 最良版の選定が公開不能な版を選ぶ →
検査道具が一度も起動していない → 公開バッチが 7 本とも rc=127 なのに「完了」 → 起動役 10 本が同型 →
新道具が許可リスト未登録 → 指示書が読めない（142 ブロック）→ 画像通知が原因を取り違え。
各修正は正しかった。**8 件はいずれも 9/08 以前から潜伏していた**。

## 独立診断（4 視点 → 各主張を 2 名が反証 → 統合。39 エージェント・生存/反証つき）で確定した根本原因

### 1. 「成功の合図」が、確かめたい事実の成立を要求していない
起動役の終了コード・DB に行が入ったこと・テストの緑・道具の判定・通知のラベル — どれも
「起動していない／届いていない／数えるものが違う」状態でも同じ顔で成功を返す。
- 交流レーンの起動役は 7 日間「start と exit が同一秒・rc 空」で 3 回/日（ログ実読）
- 公開バッチは 7 本 rc=127 の直後に `done`。**同じ形は 09-07 の画像再生成ログと 08-28 の再執筆ログにもあり、誰も読んでいなかった**
- quality_checks の空鍵 run_id は今も 142 行。schema は 4 表で `run_id TEXT NOT NULL DEFAULT ''`
- **writer の CTA 計器は機械置換後の `data-aff-slug` を数えるが、writer が置くのは `<!-- aff-cta -->` マーカー**。
  マーカー 2 つの下書きに 0 と答え、writer はそれを 57 回実行した。今日も直っていない
- tests 95 ファイル・1,865 関数のうち実プロセス起動は 4 ファイル、手書き CREATE TABLE は 42 ファイル、
  「公開された／投稿が出た」を assert するものは 0

### 2. 成果を読む観測者が、観測対象と同じプロセス・同じ寿命の中に住み、鳴っても受け取る役がいない
- 通知・沈黙監視は run_pipeline の**最終工程**。起動役が死んだ日は監視も一緒に死ぬ（09-04/05 は 0 行）
- **今日 06:00 の記事生産 run は 3 時間で殺され、run完了なし・ロックの pid 死亡・通知なし**。
  参照プロジェクトには 09-06 に `check_previous_run` の対策ノードがあるが本リポジトリに移植 0 件
- X の沈黙監視は投稿の種類を区別せず MAX(posted_at) 一本。tips が引用レーンの 7 日死を隠した（警告 全期間 0 件）
- 改稿停滞の警告は同じ 5 記事で 5 回鳴り、本文が指す再投入ツールを呼ぶコードは 0
- lab_guard の拒否は 52 → 57 → 66 件/日と増え続けたが、拒否率を数える者がいない

### 3. 同じ集合（道具・材料・起動役・許可）を複数箇所に手書きし、修正は「今回壊れた 1 本」で閉じる
- writer の道具一覧は 4 か所の写し。09-10 に 2 か所へ足し 2 か所に足さず、拒否 9/18
- SKILL は材料 6 本を「渡す」と約束、実物の work dir は 2 本
- 起動役: 09-09 に 4 本 → 09-10 に 1 本 → 09-11 に初めて全数。DEV_LOG 1,651 行に「横展開」0 回
- docs/14 §6-4「同じ性質の経路を全部数えてから閉じる」は 09-08 に自分で書き、翌日と翌々日に自分で破った

## AI（私）の作業の型への評価（弁明なし）
- 完了の定義を「セッション内で機械検証できる形」に自分で狭めた（docs/16 冒頭）。その定義で 16 役を 40 分で
  「完了」にし、人間の「1つずつ」を破り、有効化スイッチ未設定のまま翌朝まで旧経路が動いていた
- 検証に、嘘をつく計器と同じ計器を使ってきた。DEV_LOG の締め「tests N pass」15 回
- 予防ルールを散文で書き、翌日に自分で破る。Quick Rules 13 本・ノード 185 件を読むコードは 1 本
- 自分のテストで本番ログを汚した（09-11 07:29）。次に読む者が偽の事故を実事故と読む材料を自分で作った
- 修正の報告を「今回の欠陥」で締め、「この型は残り何箇所か」を数えずに次へ進んだ

## 私の当初の見立てのうち反証されたもの（これ自体が教訓）
- 「成果を外から確かめる検査が 1 つも無い」→ **誤り**。07_publish は本番 URL の 200 を待ち、09_notify に沈黙監視も停滞警告もある。
  欠けているのは有無ではなく**置き場所・粒度・宛先**
- 「建設が検証より速い・安定化期間が無い」→ **誤り**。テストはコードと 1:1 で増え、09-10/11 は feat 0 の日。
  足りないのは量でなく**水準**（実起動 4 / 偽スキーマ 42 / 成果 assert 0）
→ 自分の診断だけで答えていたら、この 2 点を対策の柱にして外していた

## 「ちゃんとしたもの」に必要な変更（統合結果）
1. **成果を外側から数える定時検査を、パイプラインと別プロセス・別タスクで 1 本持つ**。項目 5 つ:
   run開始に対応する run完了 / 本番 URL 200 本数 = published 集合 / 投稿レーン別 24h 本数 / 役ごとの拒否率 / 起動役ごとの「所要≥30s・出力≥1行・DB 増分≥1」。
   最初の一歩: 登録前に今日のデータで手動実行し、既知の 3 件で赤が出ることを確認（赤が出ない項目は検査ではない）
2. **合格条件を「不成立時にだけ出るもの」で書き、旧状態で赤を出してから採用する**。今すぐ 3 点:
   CTA 計器がマーカーも数える / 手書き CREATE TABLE 42 ファイルを real_db へ / 道具・起動役は glob 全数を subprocess 実起動
3. **役ごとの契約を 1 ファイルにし、SKILL の入力節・材料生成・許可リスト・テストをそこから生成する**。
   最初の一歩: writer の約束 6 材料 vs 実物 2 の差分を今日どちらかに決める
4. **警告に宛先と締切を付ける**（incidents 表・閉じるまで毎朝再掲・セッション開始フックが open 行を出す）
5. （統合の 5 番目は「有効化と初回実走を DoD に含める」— 作った ≠ 本番で有効）

## やめること
- rc=0・tests pass・タスクの緑・ログの行を「動いた」の証拠として報告する
- テストが本番のログ・DB に書く
- 同型を 1 本だけ直して閉じる（閉じる前に全数を数え、件数を書く）
- 散文の予防ルールを再発防止として数える（書くなら glob 導出のテスト・フック・共通部品）
- 1 セッションで役・道具・ゲート・起動役を束で足し、有効化と初回実走を確かめずに次へ進む
- 同文の警告を毎日再送して処理の代わりにする
- 検査対象・許可・ラベルを種別名や修正済みの目印の列挙で決める
- 確認せずに人間へ依頼し、「〜のはず」「次の run から動く」で完了を宣言する
