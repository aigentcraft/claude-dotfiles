## ユーザーの指摘（原文の意図）

「**同じ動きをただ3回やって不合格でした。コード処理して回してるんだと変わんないから
意味がないです**」
「不合格だった原因を分かったうえで、それを改善するための動きがちゃんとできてるのか、分かんない」

## 何が起きていたか

記事が検閲で不合格になると、パイプラインは最大3回まで書き直させる。その各ラウンドで:

1. 検閲エージェントが不合格理由を具体的に出す
2. **編集長エージェントが「書き手向けの修正指示」を生成する（LLM課金あり）**
3. その指示を **`db.log(...)` でログに1行書いて、それで終わり**
4. パイプラインは書き手を `04_write_article.py --article-id N` で呼ぶ
   — **初回とまったく同じ引数**
5. 書き手は同じファクトシートから、**何が悪かったか知らないまま白紙で書き直す**
6. 当然ほぼ同じものが出て、同じ理由で落ちる

これを3回繰り返して破棄。**3回とも同じ入力・同じ出力**だった。

決定的なのは、検閲ワーカーの設計コメントに**こう書いてあった**こと:

> ・差し戻し(C/F系) → 機械の内部ループ。通知せず、**eicの修正指示をDBに記録して writer 再実行へ**

**意図は文書化されていた。実装だけが無かった。** 書き手側のコードを `quality_checks` /
`must_fix` で grep しても一致ゼロ＝一度も読んでいない。

## 根本原因

**「生成した」ことと「届いた」ことを取り違えていた。**
指示を作るところまでは動いていて、ログにも出るので、目視では機能しているように見える。
しかし受け手のコードに読む処理が無い。**経路の終端がログだった。**

リトライループは「同じ処理をもう一度走らせる」だけでは学習にならない。
LLMを呼んでいても、**入力が同じなら出力は同じ**で、それは決定論的な再実行と変わらない。

## 修正

- 検閲側: 指示を `workflow_events` に残す（新しいテーブルもモジュールも作らない）
- 書き手側: 差し戻しラウンドでは **前回の原稿 + 編集長の修正指示** をタスクに含める。
  併せて「**同じ原稿を出し直せば同じ理由で落ちる**」「直しようがない指示は節の書き方を
  変えて回避してよい」を受入条件として明示する（＝逃げ道も与える）

## 予防ルール

- **エージェントに何かを生成させたら、それが誰にどう届くかを最後まで辿る。**
  `log()` で終わっている出力は、**誰にも届いていない**
- **リトライの前に「入力は前回と変わったか」を確認する。** 変わっていないなら、
  それはリトライではなく同じ処理の再実行。LLMを使っていても学習にはならない
- **設計コメントは実装の証拠にならない。** 「〜してwriter再実行へ」と書いてあっても、
  受け手側を grep して読む処理があるか確かめる
- **不合格ループを作るときは、必ず「前回の成果物」と「なぜ落ちたか」を次のラウンドへ渡す。**
  渡さないループは、回数を増やすほどコストだけが増える
