## 症状

1本の記事が **9時間で27回書き直された**。LLM呼び出し188回。止めたのは設計上の
ラウンド上限（最大3回）ではなく、**日次コスト上限**だった。

| 実測（記事42・2026-09-10） | |
|---|---|
| `article.drafted` | **27回** |
| `images.generated` | 26回 |
| `review.passed` | **15回**（検閲は毎回通っている） |
| `preview.visual_rejected` | **15回**（通ったあと機械ゲートが差し戻す） |
| 停止理由 | `DailyCostLimitExceeded: $101.39 >= $100.00` |

## 何が起きていたか

3つの欠陥が重なっていた。

### ① ステータスコードの二重用途がラウンド上限を無効化していた

`review_rounds()` は「**最後の H01 以降**のreviewer実行」だけを数える。
H01 の意味は「人間差し戻し＝新しい執筆サイクルの開始」で、
人間が差し戻したら前サイクルの回数を持ち越さない、という正しい設計だった。

ところが `06b_preview_deploy` の**AI側の差し戻し**（完全性ゲート・視覚検品・機械検品）も
同じ `H01` で記録していた。結果:

1. 06bが差し戻す → H01を書く
2. 次のループが `review_rounds()` を呼ぶ → **たった今書いたH01以降＝0回**
3. 上限（3回）に永久に到達しない

さらに `apply_approvals.rework_pending()` が「H01があるのにreviewer実行が無い＝書き直し
未着手」と誤認し、**15分ごとに書き直しを再起動**していた。ループの原動力が2つあった。

### ② 再実行しても直らないものを「再試行で果たせる」に分類していた

差し戻し理由は `shot_mismatch`（撮れた画像が本文の要求する状態と違う）13件。
だが撮影カタログは決定論なので、**05を再実行すれば同じ画像が出る**。
「やり直せば果たせる失敗」ではなく、原理的に果たせない指示を無限に投げていた。

同様に、撮影失敗（`shot`）4件も原因は `DemoAppError: 未知の型: 品番(ルックアップ)` で
決定論的に再現し、しかも**掃除（sweep）が既にテキスト代替を入れて本文は成立していた**。
掃除側の行は `structural=1` になるが、原因側の `shot` 行は `structural=0` のまま残るため、
「掃除済みは差し戻さない」という既存の意図から漏れていた。

### ③ 判断者が見て通したものを、機械のゲートが覆していた

reviewer は**実画像を開いたうえで** Q05/Q09 を pass し、限界まで書いていた:

> app_graphsのみ「初期状態(区分/レコード数)」の画面で、本文が要求する最終形
> (品番/合計/符号付き数量)ではない

つまり担当の判断者は見て・気づいて・そのうえで通していた。その判断を、
同じ事実を根拠に機械のゲートが15回差し戻していた。

## 修正

- 06bのAI差し戻しを `H01` → **`G01`**（ゲート差し戻し）へ。H01は人間差し戻し専用に戻す
- 完全性ゲートの対象から `shot_mismatch` を外す
  （画像は**存在する**。中身の妥当性は Q05/Q09＝reviewerの仕事で、graceは既に届いている）
- 掃除済み（同じrefに `shot_placeholder` がある）撮影失敗も対象外
  （代替テキストで本文は成立済み）
- 実測での効果: 記事42の差し戻し対象 13件 → **0件**。
  記事41は 20→16 で、残ったのは画像生成の外部クォータ切れ＝**本当に再試行で直る**もの

## 予防ルール

- **「新しいサイクルの開始」を表す印を、AI側の差し戻しに流用しない。**
  リセットの意味を持つマーカーは、リセットしてよい主体だけが書く
- **ループの上限を書いたら、「その上限が実際に効く経路」を1度は実データで確かめる。**
  上限のコードがあることと、上限が効くことは別。数え方の起点が動く実装は特に危ない
- **「再試行で直る」に分類する前に、再実行が決定論かどうかを見る。**
  同じ入力から同じ出力が出る工程を retry に分類すると、無限に投げ続ける
- **機械のゲートと担当の判断者が同じ事実を見ている場合、どちらが勝つかを決めておく。**
  判断者が実物を見て通したものを機械が覆す構造は、無限ループか品質の後退のどちらかになる
- **「上限に当たって止まった」を正常終了と読まない。** 本来の上限ではない別の上限
  （コスト・時間・API制限）で止まったなら、設計した上限は効いていない
