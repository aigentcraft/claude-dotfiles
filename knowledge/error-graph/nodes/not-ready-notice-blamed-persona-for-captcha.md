## ユーザーの指摘（原文）

「Captchaが出たということと、ペルソナに不足情報があるという回答が来ている。案件ボードの＃77」

## 1. Plan / Context

インディードの［応募内容を作る］は、エージェントが普段の Chrome で応募フォームを記入し、
承認カードを出す。進めない事情がある時は承認ボタンを出さず、案内を 1 行添える。

## 2. Do / The Error

#77 でエージェントは求人ページを開いた時点で Cloudflare の「私はロボットではありません」に当たり、
正しく止まった（突破しない）。承認カードには理由（CAPTCHA）が出ていたが、続く案内は
「**不足している情報があるため**… `persona.md` に事実を足して」だった。利用者には 2 つの別の問題に見えた。

## 3. Check / Root Cause

- 案内の文面が**理由に関わらず 1 種類**だった。書いた時に想定していた止まり方（設問に答える材料が無い）しか見ていなかった
- 止まる理由は少なくとも 3 種類ある: 関門（CAPTCHA）・人物像に無い情報・その他（募集終了など）

## 4. Act / Prevention Strategy (Fix)

`notReadyNotice(plan, jobUrl)`（純関数）で理由ごとに言い分ける。
関門 → 「普段の Chrome で求人ページを一度開いて確認を済ませてから押し直す」（リンクつき）／
人物像 → persona.md ／ その他 → 上の「進めない事情」を見るよう案内。selftest 3 件、故障注入で FAIL を確認。

### 予防ルール

1. **止まった時の案内は、止まった理由から組み立てる。** 1 種類の文面で済ませると、別の理由の時に誤った行動を指示する
2. 案内が「利用者に何かをさせる」なら、その行動が理由に合っているかを分岐ごとに検査する

## 再発（2026-09-27・承認済みフォームの送信・出荷前に発見）

手元のテスト用フォームで「承認に無い必須の欄（電話番号）」を試したら、送らずに止まったのは正しいが、
案内が「**ログイン・CAPTCHA などで進めなかった**」になった。エージェントは `missing: ["電話番号"]` と一緒に
`blocked: true` も立てており、判定（`judgeFormOutcome`）が blocked を先に見ていた。
本人は「何を答えればよいか」ではなく「どこで詰まったか」を探しに行ってしまう。

3. **理由の旗が複数立ちうる時は、本人が次にできることが具体的な方を先に見る**（足りない欄 → 関門 の順）。
   エージェントの旗は排他でない前提で判定を書く。selftest に**実物の報告の形**（両方立った形）を入れる
4. 報告の道具の説明にも「欄が足りないだけなら blocked にしない」と書く（指示と判定の両方で塞ぐ）

## 再発（2026-09-29・#71 Leaner・利用者の指摘）

履歴書・職務経歴書の**添付が必須**で止まったのに、案内が「人物像に無い情報があるため… `項目: 値` の形で返信して」だった。
理由の 3 行目「電話番号欄（**任意**）は本人の携帯番号が人物像に未記入」に `PERSONA_WORDS` が反応した。
添付は代理でしないので、何を答えても進まない。本人は自分で応募し、その報告を書式違いで突き返された
（詳細: [[uc-persona-reply-bounced-for-format.md]]）。

5. **任意の欄は止まった理由に数えない。** 旗（理由の行）を正規表現で読むなら、先に「任意」を外す
6. **答えても進まない理由（添付）を、答えれば進む理由（人物像）より先に見る。** 順は 関門 → 添付 → 人物像
7. selftest には**実物の理由の行をそのまま**入れる（今回も、想定した 1 行の例では通っていた）
