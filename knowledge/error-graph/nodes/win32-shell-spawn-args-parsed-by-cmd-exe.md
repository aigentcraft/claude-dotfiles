## 症状
Node の `spawn('node', ['-e', 'setTimeout(()=>{},60000)'], { shell: true })` を Windows で実行したら、
- プロジェクト直下に **`{}` という 0 バイトのファイル**が出来た（`git status` に `?? {}` が現れて発覚）
- 子プロセスは即終了し、「孫プロセスが生き残るか」を測るテストが**何も測れないまま「children=[]」**を返した

## 根本原因
`shell: true` は Windows では `cmd.exe /d /s /c "<command line>"` になる。引数は **cmd.exe が再解釈**するので
`()=>{}` の `>` が**出力リダイレクト**、`{}` がその出力先ファイル名になった。`&` `|` `^` `<` も同様に効く。
Node の `spawn` の引数配列は「そのまま渡る」という POSIX の感覚が Windows + shell では成り立たない。

前提として shell が要る理由: npm グローバルの `claude` の実体は `claude.cmd`（npm シム）で、
`spawn('claude')` は `.exe/.com` しか探さず **ENOENT**（実測）。Node 20.12 以降は `.cmd` を shell 無しで
起動すると EINVAL で弾かれる。だから cmd.exe を通すしかなく、引数の再解釈が付いてくる。

## 修正
- 引数は**定数だけ**（`-p` / `--model` / モデル名）にし、本文はすべて **stdin** で渡す。コードのコメントに固定した
- テストは引数にコードを載せず、スクリプトファイルを渡す形に変えた
- タイムアウト時の停止は `taskkill /PID <shell pid> /T /F`。`child.kill('SIGKILL')` は cmd.exe しか殺さず
  孫（node / claude.exe）が生き残る（PID を追跡して実測: child.kill → 生存 yes、taskkill /T → 生存 no）

## 予防ルール
1. **`shell: true` で渡す引数にメタ文字（`> < | & ^`）や利用者由来の文字列を入れない。** 本文は stdin
2. shell 経由の子プロセスを止める時は **`taskkill /T`** でツリーごと落とす（macOS の SIGKILL と分岐する）
3. 「テストが通った／空だった」は「測れた」ではない。**cwd に見覚えの無いファイルが出来ていないか**を見る
4. 関連: [[windows-claude-cli-subprocess-needs-cmd-and-gitbash.md]]（Python 側の同じ穴）。
   claude CLI は環境によって `CLAUDE_CODE_GIT_BASH_PATH` を要求する。対話セッションからの起動では通ったが、
   タスクスケジューラなど別環境で動かす時は再実測する

## 2 例目（同日・2026-09-19）— 今度は「説明文の中のコマンド例」が実行された

`node -e "…"` の**二重引用符の中**に、利用者への説明文としてバッククォート付きの
コマンド例を書いた。

```
const rep='… 回復は `npm run login -- indeed --manual` で有人ログインを …';
```

二重引用符の内側でバッククォートは**コマンド置換**になる。bash は説明文のつもりの 2 か所を
実際に実行した。

- `npm run login -- indeed` — 無人ログインを再試行（レート制限下で 429 を積み増した）
- `npm run login -- indeed --manual` — **画面付きブラウザを起動**し、10 分間人間の操作を待った

利用者は開いた覚えのないブラウザを操作しており、「ホーム画面に勝手に戻る」と報告して初めて
発覚した。**外向きの操作が、文書を書くつもりのコマンドから起きた。**

### なぜ 1 例目の教訓が効かなかったか
1 例目は「`spawn(shell:true)` の引数」という**コードの話**として書いていた。
今回は「AI が自分で打つシェルコマンドの中の説明文」で、同じ原理なのに別物に見えていた。
危険なのは `shell: true` ではなく、**コマンド例を含む文字列をシェルに解釈させること**そのもの。

### 仕組み（宣言ではなく手順として固定する）
1. **`node -e "…"` を使わない。** スクリプトは必ず `cat > file <<'EOF'` の
   **クォート付きヒアドキュメント**でファイルに書いてから実行する。
   クォート付きヒアドキュメントの中では `` ` `` も `$` も展開されない
2. コマンド例・URL・記号を含む文章を扱う処理は、**例外なくファイル経由**にする
3. 二重引用符の中に `` ` `` `$(` `$` を書かない。書いたら手が滑っていると考える
4. **外向きの操作（ログイン・送信・応募）を起こしうる語を文字列に含む時は特に警戒する。**
   今回は「回復手順を文書に書く」という完全に無害な意図から、実ログインが 2 回走った

## 3 例目（同日）— ヒアドキュメントの中の JS 文字列でエスケープが失われた

`cat > patch.cjs <<'EOF'` で書いた JS の中に `split('\n')` と書いたつもりが、
出力されたファイルでは `split('` + 実際の改行 + `')` になり、生成したコードが構文エラーになった。
**3 回とも「コードを含む文字列をシェル経由で書いた」ことが原因**だった。

### 手順として固定したこと
- **コード片は平文ファイルに書いて読み込む。** 置換したい本文を `cat > block.txt <<'EOF'` で
  書き、スクリプト側は `fs.readFileSync(blockPath)` で差し込むだけにする。
  こうするとエスケープを 1 つも書かずに済む
- 壊れた場合の修復も、`String.fromCharCode(92)` などでエスケープを**書かずに**組み立てる
