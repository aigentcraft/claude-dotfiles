## 形
人間の操作を外の系（Discord のボタン → Cloudflare の受け口 → D1）に置くと、**押した瞬間に「🟢 承認しました」と
表示が変わる**。実体（家の DB の記事の状態）が動くのは、あとで走る取り込みが D1 を読めた時だけ。
この 2 つの間には、誰も見ていない区間がある。

weevee の初版は、その区間の失敗を握りつぶしていた:

```python
try:
    buttons = ingest_buttons(...)
except Exception as e:
    db.log(con, WORKER, "error", f"...: {e}")   # ログ 1 行
    print(...)                                   # ログファイル 1 行
# → main() はそのまま続行して return。rc=0。Task Scheduler の履歴は「成功」
```

Cloudflare の API トークン失効・D1 の id 不整合・一時的な 5xx のどれかが続くと、
**押した人は「承認しました」を見て待ち、記事は永久に review のまま**。
定時タスクの履歴も緑、通知も出ない。既存の障害エスカレーションは記事生産 run の
execution_logs しか見ていないので、独立タスクのこのエラーはどこにも届かない。

## なぜ普通のテストで見つからないか
このプロジェクトの検査は「例外メッセージの文字列がソースに含まれているか」までは見ていたが、
**rc がいくつか / 通知が出るか**を見ていなかった。実装は「読めないことを『押されていない』にしない」と
コメントまで書いてあり、意図は正しいのに出口（rc・通知）に届いていない。

## 直し方（2 つで 1 組）
1. **中から**: 失敗した run は rc≠0 を返し、ops に 1 回鳴らす（同じ故障の連投は 24 時間抑える）。
   文面には「押した画面には成功と出ているが、実体は動いていない」と、**代わりの手段**（返信での承認）を書く
2. **外から**: 別プロセスの定時検査が「D1 に積まれたまま取り込まれていない押下」を数える。
   透かしより新しい行が取り込み間隔の 2 回分を超えて残っていれば赤。
   取り込み側の中で数えると、取り込み側が死んでいる時に 0 件に見える（[[sweep-target-list-must-not-be-the-fixed-set]] と同型）

読めなかった時は**緑にも赤にもせず「不明」の印を付けて赤側に倒す**。
「押されていない」と「読めていない」を同じ 0 件にしない。

## 予防ルール
- 人間の操作を外の系に置いたら、**その操作が実体に届いたかを家の側から数える検査**を同時に作る。
  表示が先に成功を見せる設計では、表示は証拠にならない
- 握りつぶす except を書いたら、その run の**終了コードと通知**まで決める。
  ログ 1 行は「記録した」であって「知らせた」ではない
- 独立した定時タスクを足したら、既存のエスカレーションがそのワーカー名を見ているか確かめる
  （見ていなければ、そのタスクのエラーはどこにも届かない）
