## 1. Plan / Context

fukugyo-hootl（副業サイト自動化）は 1 サイト目にママワークス、2 サイト目にインディードを足した。
新着検知・Discord 通知・返信案の生成・**送信**はいずれも `record.siteId` を見て分岐するよう
多サイト対応済みだった。

## 2. Do / The Error

利用者からの指摘（2026-09-21）:

> 想い結びのスレッドでママワークスの企業とのメッセージページが取得できなかったと通知が来ているがなんで？

インディードの返信案で［非承認（修正指示）］を押すと、毎回こう出る:

```
⚠️ ママワークス側で該当スレッドを再取得できませんでした。
```

インディードの話をしているのに**ママワークスが名乗る**ため、利用者は
「ママワークス側で何か壊れた」と読む。実際は 1 文字もママワークスに触れていない。

## 3. Check / Root Cause

`onReject` だけが再取得をハードコードしていた。

```ts
const threads = await fetchInbox(10, sources);      // ← sites/mamaworks/inbox.ts のみ
const thread = threads.find((t) => t.key === record.key);
if (!thread) {
  await bridge.postNotice(id, '⚠️ ママワークス側で該当スレッドを再取得できませんでした。');
```

鍵は `indeed:<会話ID>`。ママワークスの受信箱にあるはずがなく、**インディードの返信案では
100% 失敗する**。エラー文にもサイト名が直書きされていた。

**なぜ見逃したか**: 多サイト化のとき「正常系（受信→通知→送信）」は全部辿ったが、
**やり直し・救出・置き去り回収といった回復系の経路**を数え上げなかった。
回復系は普段走らないので、動作確認でも踏まない。

また、失敗が**例外でもログの警告でもなく、利用者向けの丁寧な文面**として出たため、
「仕組みが対応していない」ではなく「今日はサイトの調子が悪い」に見えた。

## 4. Act / Prevention Strategy (Fix)

1. 再取得をサイトごとに分岐する関数（`refetchThread`）に切り出し、`record.siteId` で選ぶ
2. エラー文のサイト名は**レジストリから引く**（`siteLabel(site)`）。文面に固有名詞を直書きしない
3. **2 つ目の実装を足す時のチェック**: 正常系だけでなく、その資源を触る
   **回復系の経路を全部数える**（やり直し・救出・置き去り回収・再送）。
   `grep` で「1 サイト目のモジュールを直接 import している箇所」を洗うのが早い

### 汎用ルール

> **N 個目を足したら、「1 個目の名前がコードと文面に残っていないか」を grep で数える。**
> 正常系が通ることは、回復系が通ることの証明にならない。
> 回復系は普段走らないので、壊れていても**利用者が踏むまで誰も気づかない**。

> **利用者向けの失敗文面に固有名詞を直書きしない。**
> 文面が実体とずれると、利用者は「対応していない」ではなく「調子が悪い」と読み、
> 構造的な欠陥が一時的な不調として何度も見逃される。
