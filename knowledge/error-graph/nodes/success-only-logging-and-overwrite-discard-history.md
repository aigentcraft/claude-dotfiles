## 症状

エージェントが失敗した時の思考・ツール使用の記録が無い。実測: `llm_calls.ok=0` の45件中
**41件で `reflections.process_log` が空**。障害調査のたびに「なぜそう判断したのか」が
分からず、推測で直すことになっていた。

同じ調査で二つ目の欠落が出てきた。`run_id` は**使い回されている**（2回以上の `llm_call`
を持つ `run_id` が222件・最大12回）のに、保存は上書きだった:

```python
con.execute("UPDATE reflections SET process_log=? WHERE run_id=?", (process_log, run_id))
```

→ 12回呼ばれたエージェントの思考は**最後の1回しか残っていない**。
「41件が空」の裏で、成功した実行でも履歴が静かに消えていた。

## 根本原因

1. **記録が成功パスにしか無い。**
   ```python
   if result.ok:
       _db.save_process_log(...)   # 失敗した result.events はここで捨てられる
   return result
   ```
   `_run_once` は kill された時も `events=events` を返している（材料は手元にあった）。
   捨てていたのは呼び出し側。

2. **キーが1回きりだという暗黙の前提**で `UPDATE ... SET x=?` を書いた。
   キーが再利用されると、上書きは**エラーを出さずに履歴を消す**。

共通するのは「計測が、観測したい対象の一部しかカバーしていない」こと。しかも
**足りないことが症状として出ない** — 空のログは静かで、上書きは成功する。

## 修正

- 記録を成功パスから**試行ループ本体へ移動**し、成否に関わらず1試行ぶんを記録する
- `save_process_log` を `COALESCE(process_log,'') || ?` の**追記**へ変更
- 見出しには事実だけを書く（時刻JST・エージェント・試行n/N・成否・エラー文・コスト・
  turn数・所要）。失敗の**原因は書かない** — 読む人間とL4の仕事（ai-behavior R18）
- 空の thinking ブロックは出さない（実測: 既存の思考1964個中、中身があるのは826個=42%）

実走検証: `OVERALL_TIMEOUT_SEC` を45秒に詰めて複数ターンのエージェントを本物の kill に
かけたところ、**8,780字・ツール使用17回分**が記録された（従来は全部捨てられていた分）。

## 予防ルール

- **記録・計測は、失敗パスから先に書く。** 成功時のログは「動いている」ことしか教えない。
  調査に要るのは失敗時の中身
- **`UPDATE ... SET col=?` を書く前に、そのキーが一意か実測する。** 使い回されるキーなら
  追記（`COALESCE(col,'') || ?`）にする。上書きは**成功しながら履歴を消す**
- **失敗を表す戻り値が中身（events・レスポンス・中間状態）を持っているなら、
  それは捨てる前提の設計ではない。** 関数の出口で「捨てている材料が無いか」を確認する
- **自律判断へ移行する前に、失敗の記録を先に直す。** 判断させる移行では失敗が仕事の
  一部になる。思考が残らない状態で始めると、原因を推測でしか語れない
  （docs/12 で Phase 1-2 を Phase 2 より先に置いた理由）
