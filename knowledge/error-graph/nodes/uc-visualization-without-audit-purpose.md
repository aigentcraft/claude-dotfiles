## 1. Plan / Context
ユーザーに「各エージェントの活動実績を常時確認できるように」と依頼され、各エージェント1行の集計ダッシュボード（呼出数・累計コスト・最終稼働・直近の仕事）を作り、「仕組み化完了」と報告した。

## 2. Do / The Error
ユーザー指摘: 「ただの概要一覧で全然各エージェントの活動実績が全部確認できるようなものになってない。エージェントの選択ができて、日別に活動実績を確認できるようにしないと。**仕組化できたように見えているだけで、実際にはうまくいっていないということがないか確認したいためのもの**」。
→ 作ったのは「集計」であって「監査」ではなかった。実際には llm_calls 251件中 **35件が失敗**（300秒無応答killなど）・reflections **19件がrunningのまま孤児化**していたが、概要サマリーではその異常が1件も見えなかった。

## 3. Check / Root Cause
「可視化して」の**目的**（＝実際にうまく動いているかを監査し、失敗・停滞を発見する）を確認せず、見栄えのする集計で満足した。「確認できる」を「一覧できる」と浅く解釈し、ドリルダウン（エージェント選択→日別→個別試行→失敗）の必要性を汲まなかった。加えて「仕組み化完了」と報告する前に、そのツールで実際に異常を発見できるか自分で使っていなかった（前セッションで確立した「実走検証」の教訓を、コードだけでなく可視化物にも適用すべきだった）。

## 4. Act / Prevention Strategy (Fix)
**Fix:** エージェント選択・日別タイムライン・1試行ごとの成否/エラー/コスト/所要・「失敗のみ」フィルタ・未完了(running)警告を備えた監査ツールに作り直し、Playwrightで「35失敗・19孤児が実際に画面で辿れる」ことを実証した。
**Prevention:**
1. 「可視化 / ダッシュボード / 一覧」要求では、作る前に **「それで何を判断・発見したいのか」** を明確にする。監査目的なら、異常（失敗・停滞・逸脱）を1件ずつ辿れる粒度を最初から設計する。
2. 集計サマリーは「全体の健康」には有効だが「個別の異常発見」には無力。監査要求にサマリーだけで応えない。
3. **可視化物も「実走検証」の対象**。「仕組み化できた」と言う前に、その仕組みで既知の異常（今回は失敗ログ）が実際に発見できることを自分で確認する。「見せかけの完成」を報告しない。
