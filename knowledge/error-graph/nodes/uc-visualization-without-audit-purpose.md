## 1. Plan / Context
ユーザーに「各エージェントの活動実績を常時確認できるように」と依頼され、各エージェント1行の集計ダッシュボード（呼出数・累計コスト・最終稼働・直近の仕事）を作り、「仕組み化完了」と報告した。

## 2. Do / The Error
ユーザー指摘: 「ただの概要一覧で全然各エージェントの活動実績が全部確認できるようなものになってない。エージェントの選択ができて、日別に活動実績を確認できるようにしないと。**仕組化できたように見えているだけで、実際にはうまくいっていないということがないか確認したいためのもの**」。
→ 作ったのは「集計」であって「監査」ではなかった。実際には llm_calls 251件中 **35件が失敗**（300秒無応答killなど）・reflections **19件がrunningのまま孤児化**していたが、概要サマリーではその異常が1件も見えなかった。

## 3. Check / Root Cause
「可視化して」の**目的**（＝実際にうまく動いているかを監査し、失敗・停滞を発見する）を確認せず、見栄えのする集計で満足した。「確認できる」を「一覧できる」と浅く解釈し、ドリルダウン（エージェント選択→日別→個別試行→失敗）の必要性を汲まなかった。加えて「仕組み化完了」と報告する前に、そのツールで実際に異常を発見できるか自分で使っていなかった（前セッションで確立した「実走検証」の教訓を、コードだけでなく可視化物にも適用すべきだった）。

## 4. Act / Prevention Strategy (Fix)
**Fix:** エージェント選択・日別タイムライン・1試行ごとの成否/エラー/コスト/所要・「失敗のみ」フィルタ・未完了(running)警告を備えた監査ツールに作り直し、Playwrightで「35失敗・19孤児が実際に画面で辿れる」ことを実証した。
**Prevention:**
1. 「可視化 / ダッシュボード / 一覧」要求では、作る前に **「それで何を判断・発見したいのか」** を明確にする。監査目的なら、異常（失敗・停滞・逸脱）を1件ずつ辿れる粒度を最初から設計する。
2. 集計サマリーは「全体の健康」には有効だが「個別の異常発見」には無力。監査要求にサマリーだけで応えない。
3. **可視化物も「実走検証」の対象**。「仕組み化できた」と言う前に、その仕組みで既知の異常（今回は失敗ログ）が実際に発見できることを自分で確認する。「見せかけの完成」を報告しない。

## 続報（同セッション・2段階の作り直し）
監査ツールに作り直した後、今度は「**ただのログが並んでいるだけで報告書になっていない**」と再指摘された。タイムライン（生ログの整形表示）も「報告書」ではなかった。報告書とは、DBの記録（検品コメント・失敗種別・繰り返しパターン）を**集計・分類・診断**して「何が問題か・なぜか」を示すもの。結局 概要サマリー→タイムライン→診断レポート と2度作り直した。
- **追加の予防ルール**: 可視化は「データを並べる」で止めず「読み手が何を判断・発見したいか」まで踏み込み、集計・分類・診断（問題の言語化）まで到達させる。生ログの整形は可視化の素材であって報告書ではない。DBに記録されている豊富な情報（今回は`reflections.quality_check`の検品判断文・`quality_checks.comment`の不合格理由・失敗種別）を最初に棚卸ししてから設計する。

## 続報2（2026-08-15・鮮度と情報設計で3度目の指摘）
翌日、「5時に始動して更新されているはずなのに**昨晩の状態のまま**。即時更新されないと困る。**レイアウトもただ並べただけで構造化されておらず、非常に使いずらい**」と再々指摘。
- 鮮度の実態: 5時runは正常完走しファイルも06:07再生成済み**だった**。UTCタイムスタンプの素通し表示で朝runが「昨晩20〜21時」に見えていた（技術根因は [[utc-timestamps-render-as-last-night.md]]）+ 再生成がrun末尾のみで始動〜完了の約1時間は前日状態のまま + 生成時刻の表示が小さく「古いのか判定」が見る側でできなかった
- 構造の実態: 指摘のたびにセクションを縦に**継ぎ足し**てきた結果（診断→品質→タイムライン→成果物→過程）、目的別の入口がない1枚の長大ページになっていた
- Fix: ①全時刻JST化 ②run_pipelineの**各ステップ後**に再生成（始動直後から反映） ③ヘッダーに生成時刻+経過チップ（20h超で更新停止警告の自己申告） ④3タブ再設計（日次の報告[日別チップ]/エージェント別報告書[部署ナビ・成果物先頭]/品質・障害[累積]）+15分自動リロード+表示状態復元
- **追加の予防ルール**:
  1. 可視化物は「**いつ時点の・どのタイムゾーンの・何を**見ているか」を自身で表示する（生成時刻・経過・更新契機）。鮮度が自己申告されない画面は「古い」と「古く見える」を見る側が区別できず、正常動作でも不信を生む
  2. 更新タイミングは作る側の都合（run末尾）でなく**見る側の期待**（始動したら反映され始める）に合わせる
  3. 指摘対応でセクションを継ぎ足したら、3回目には情報設計（IA）ごと再構成する。「並べる場所を増やす」は構造化ではない
