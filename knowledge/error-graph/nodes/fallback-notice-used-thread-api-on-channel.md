## 1. Plan / Context
インディードの新着を通知メールから知らせる（C-1）。本文を Claude in Chrome で読めたら既存の流れへ、
読めなければ**リンクだけの通知に落とす**（C-2）。後者は「通知は必ず届ける」ための予備の経路。
知らせる先は、企業の案件の投稿（スレッド）があればそこ、無ければ `#やり取り`（チャンネル）。

## 2. Do / The Error
```
[13:56:52] インディードの会話を読みました: インベスター・コミュニケーションズ株式会社（0 通 / $0.22）※関門で読めず
[13:56:52] [FAIL] インディードの通知メールの確認に失敗: Discord スレッドが見つかりません: 1549672127668428822
```
予備の通知を `bridge.postNotice(threadId ?? channels.inbox, text)` で出していた。
`postNotice` は**スレッド専用**で、チャンネル ID を渡すと「スレッドが見つかりません」で例外になる。

## 3. Check / Root Cause
- **予備の経路を一度も通していなかった。** 試験した企業（実物 4 通）はどれも既存の案件の投稿があり、
  スレッド側しか通らなかった。チャンネル側は、案件の無い企業から初めて連絡が来た時に初めて通った
- `threadId ?? channels.inbox` で**型が同じ（string）なので、取り違えがコンパイルでも見えなかった**
- 送信の**後で**カーソルを進める作りなので、例外で抜けるとカーソルが進まず、**毎時同じ新着を $0.22 かけて読み直し、また落ちる**
- 「アーカイブ済みの旧チャンネルでは」という疑いも出たが、`settings` の `discord.channel.indeed.inbox` と
  Discord への問い合わせで、現役の「💬やり取り-7〜23時の毎時」だと確かめた（表は作成時の名前のままだった）

## 4. Act / Fix & Prevention
スレッドがあれば `postNotice`、無ければ `postToChannel` に分けた。

### 予防ルール
1. **「必ず届ける」ための予備の経路こそ、本番の前に 1 回通す。** 通常の経路しか試していない予備は、使われる日に初めて壊れる
2. **同じ `string` 型でもスレッド ID とチャンネル ID は別物。** `a ?? b` で混ぜる箇所は、受け手の関数がどちらを受けるかを確かめる
3. **有料の処理の後に失敗しうる処理を置く時は、失敗したら次回どうなるかを考える。** 進まないカーソルは、同じ課金を繰り返す
