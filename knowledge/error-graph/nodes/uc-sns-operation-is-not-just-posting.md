# UC: 「投稿だけが運用ではない」

## 症状（ユーザー指摘）
X運用自動化の打合せで、投稿の自動化だけを主軸に提案し、リプライ応対・メンション監視・
能動エンゲージ・分析を「無料枠では不可」「凍結リスクでやらない方針推奨」と切り捨てた。

## 根本原因
- 「運用」をAPI制約（write500/read100）から逆算して定義した。事業目的（受注=見込み顧客との
  接点作り）から定義すべきだった — 受注目的メディアのXは傾聴・応対・開拓こそがリードを生む
- ユーザーには scout-operator（TikTok: 候補発見→判定→いいね→フォロー→DM送信の自律実行）の
  運用実績があり、能動エンゲージの自動化は既に実践済みの領域。既存アセット（agents一覧）を
  確認せずに「やらない方が良い」と提案した

## 予防ルール
**運用系の自動化提案は「発信・傾聴・応対・開拓・分析・導線整備」の機能マップを先に描き、
各レーンの自動化度（全自動/HITL/保留）を事業目的から決める。技術制約は却下理由でなく
迂回設計の入力**（API不可→ブラウザ自動化・実機MCP等の代替経路を先に検討する）。
提案前にユーザーの既存アセット（エージェント・過去の運用実績）を確認する。
