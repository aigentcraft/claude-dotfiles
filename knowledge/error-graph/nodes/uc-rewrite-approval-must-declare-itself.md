# 人間に判断を求める通知は、その判断に必要な状態文脈（新規か更新か）まで運ぶ

## 症状（ユーザー指摘）
「Discordに届いてる承認依頼、過去に画像も見たことあるし内容もかぶってるんじゃないか。調べて」
— リライトレーン初実弾（2026-08-19朝・記事#1の同一URL更新）の承認依頼が原因。システムは
仕様どおり動いていた（企画キュー検品→リライト転換→検品2ラウンド→承認依頼）が、人間には
「重複記事の量産」に見え、不信と調査コストが発生した。

## 根本原因
- 06bの承認依頼文面が「タイトル+点数+プレビューURL」のみで、新規/リライトを区別しない。
- リライトは定義上「公開済み記事と似た題・同系画像・同テーマ」— 区別表記がなければ
  人間の目には重複記事と不可分。
- レーン実装（2b/04/07の初出日保全）はDB側で完結していたが、人間接点（通知文面）まで
  リライト文脈が運ばれていなかった。[[instant-approval-path-skips-sns-fanout.md]] の
  「新レーンが既存インフラに合流する時、下流の片側だけ結線される」パターンの表現層版。

## 修正（2026-08-19）
- 06bの承認依頼（Bot embed / Webhookフォールバック両方）に、articles.published_at の有無で
  機械判定するリライト行を追加:
  「♻️ 公開中記事のリライトです（同一URLの更新・初出日保全 — 記事は増えません）現行版 → URL」
  （published_atはリライト中も保持される不変条件 — 実DBの記事#1で検証済み）
- 付随修正: リライトで未参照化した旧図版が孤児ファイルとして残る問題（fig-4.png実例）を
  07_publishの公開時掃除 `remove_orphan_images()` で恒久対策（最終mdへのファイル名出現で
  判定・誤削除方向に倒れない・単体テスト済み。git addのdir指定は削除も段階化する）。

## 予防ルール（一般化）
- **人間に判断を求める通知は、判断を変えうる状態文脈を必ず文面に含める**（新規/更新、
  初回/再送、既存物を上書きするか）。システムが知っている文脈を人間に隠すと、正常動作が
  異常に見え、信頼と調査コストで支払うことになる。
- 新レーンを既存の人間接点（承認・通知・レポート）に合流させる時は、**文面がそのレーンを
  表現できるかまで移植チェックリストに含める**（docs/09_note-org.md の原則移植チェック
  リストに「人間接点の文面」観点を足すのと同趣旨）。
