## ユーザーの指摘（原文）

「案件ごとにスケジュールが決まったらグーグルカレンダーを確認してまだスケジュール登録が無ければ入れておくような動きもなく、非常に受け身。」
「LINEやメールの内容の通知も案件DBと明らかに関係のないものが混じっているし、求人媒体からの案件の案内も私が受けたい要件に合ってないものを通知したりとか、内容をURLまで見に行って確認したりしないままただ通知するだけになっている。」
「Gメールもなぜかブラウザで見に行ってるし。」

## 1. Plan / Context

常駐は「新着を知らせる → 返信案を出す → 承認で送る」を軸に作られ、それ以外の動きは
本人がスレッドに書いた時だけ、常駐の Claude Code（Chrome・デスクトップ操作）が行う。
メールは IMAP で読み、仕分けは Haiku（「迷ったら関係あり」）、関係ありは担当エージェントが本文を読んで通知する。

## 2. Do / The Error（2026-10-03 の実測）

- **カレンダーに関わるコードが 1 行も無い**（`src` を calendar / カレンダー で検索して 0 件）
- 本人がカレンダー登録を頼んだのは 4 回（スレッド 3 回・対応事項の完了の入力欄 1 回）。
  スレッドの 3 回は常駐の Claude Code が Chrome で入れた（1 回 $0.19〜0.77）。
  **完了の入力欄に書いた「グーグルカレンダーに登録して」（ケイビーカンパニー・10/7 17:00 Zoom）は誰にも渡らず、どのカレンダーにも入っていなかった**
- 予定が 2 つのカレンダーに割れている: 個人（アイドマ・Wonder Wall・ピクチャー）／副業用（ユニタス 2 件）
- メールの仕分けの指示が「迷ったら related=true」。LINE は「未読が増えた個人の会話」なら案件 DB と照合せずに通知
- 求人媒体からの案件の案内は、リンク先を開いて条件と照らす経路が無い（案件探索の判定に乗らない）
- 常駐の Claude Code にメールを探す・読む道具が無いため、Chrome で Gmail を開いて検索していた（IMAP の仕組みは既にあるのに渡していない）

## 3. Check / Root Cause

- **「起きたことを人に知らせる」までが仕事の範囲になっていた。** 予定・期限・準備のように、知らせた後に誰かがやるべきことを秘書側が引き取る設計が無い
- **人の自由な指示を受ける口が一部だけ。** スレッドの書き込みは常駐に渡るが、完了の入力欄の文字は「返信案の材料」として保存されるだけ
- **通知の前に確かめる段が無い。** 関係の判定は件名と冒頭だけで、迷ったら流す。リンク先は見ない
- **道具の不足をブラウザ操作で埋めていた。** 既にある読み取り手段（IMAP）を常駐に渡していない

## 4. Act / Prevention Strategy (Fix)

2026-10-03 一部を実装（fukugyo-hootl）:
- 常駐の Claude Code に `search_mail` / `read_mail`（IMAP。言葉は IMAP に渡さず手元で絞る）を渡し、指示に「ブラウザで Gmail を開かない」
- 完了の入力欄の文字は Haiku で「記録以外の依頼」があるかを見て、あれば常駐へ渡す（本人の入力だけ）
- #🗂秘書 で秘書に聞ける（全体を見る役割・本人の書き込みだけ）

**未着手**（利用者の判断待ち）: カレンダーへの自動登録（どのカレンダーに揃えるか）、メール・LINE の通知を案件 DB と照合して絞る、
求人の案内メールのリンクを開いて条件と照らす

### 予防ルール

1. **知らせた後に誰かがやることがあるなら、秘書がやれる分は秘書がやる。** 取り消せる・外に出ない操作（自分のカレンダー・整理・下書き）は頼まれなくてもやって、やったことを報告する
2. **人が文字を書ける欄は、全部 LLM に意図を読ませる。** 保存するだけの欄を作らない
3. **通知する前に確かめる。** 案件 DB と照合し、リンクは開いて読む。迷ったものは個別に通知せず、まとめに一行で載せる（捨てない・うるさくしない）
4. **エージェントにブラウザで代わりをさせる前に、データを直接読む道具を渡せないか考える**
