## 状況
LLM エージェントに「出す前に自分で検査を回して直してから出せ」と命じる設計。
指示書には「**不合格のまま出すな**」と書いてある。

## 条件はひとつ
> その役が、その段階で**契約どおりに正しく行動した**とき、判定が不合格 → 合格に**変わる**こと。

崩れると 2 通りに壊れ、**どちらも rc=0 でログ上は正常に見える**。

| | 症状 | エージェントの反応 |
|---|---|---|
| **永久に赤** | どう直しても通らない | 契約を破って通す（捏造）か、同じ検査を何十回も回す |
| **永久に緑** | 壊れても合格を返す | 誰も気づかない |

## 実例（2026-09-14 に 1 日で 6 件）

**永久に赤**
- 収益導線の計器が、機械置換**前**の下書きに、置換**後**にしか現れない属性を数えていた。
  ライターが置けるのは位置マーカーだけで、リンク HTML を書くことは契約が禁じている
  = **合格は契約違反でしか作れない**。実測 227 回実行（1 記事で 36 回）
- 「残してよいコメント」の一覧が 2 箇所にあり中身が違った。存在しない接頭辞が入り、
  ライターが置けと命じられている接頭辞が抜けていた → 契約どおりの下書きを毎回 NG（73 回実行）

**永久に緑**
- NG 語彙の台帳を指すパスが、5 日前のディレクトリ整理で消えた場所のままだった。
  実装は `if not path.is_file(): return []` — **黙って空を返す**。禁句が全部素通りし、
  記録には「検査した結果 0 件」と残る
- 照合対象が 0 語なのに「NGワードなし」と報告していた

## 予防ルール
1. **計器を作ったら「正しい成果物」で 1 回通す。**「壊れた成果物で赤が出る」だけでは半分
2. **対象は表から導く。** 役ごとの計器一覧を単一ソースに置き、
   「その役の計器すべてが、契約を満たした成果物で緑になる」を毎回検査する（列挙で持つと増えた時に漏れる）
3. **「検査できなかった」を「合格」と同じ値にしない。**
   台帳が無い・語彙が 0 件・照合対象が空 は全部**未検査**。法令系は fail-closed
4. **段階で意味が変わる述語に、どちらとも読める名前を付けない。**
   `count_ctas` は「下書きの枠」か「公開面のビーコン」か区別できず、取り違えたまま 2 週間動いた
5. **指摘には宛先を持たせる。** 直せない相手に出した指摘は、直らないまま永久に往復する
