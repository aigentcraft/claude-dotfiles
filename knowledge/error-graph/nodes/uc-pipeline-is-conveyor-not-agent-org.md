## ユーザー指摘（原文）
「機械的なハードコードばかりで、AIエージェント組織になっていないから、こういうお粗末なものが出てくる。
実際書かれている記事の内容も、競合記事を参考にしているとは思えない。誰も望んでないような分析や検証、
すでに他のサイトでとうの昔に書かれているようなのを今更書いて、しかも他のサイトの記事より劣ってるって
どういうこと？根本的にズレているから直さないとだめ。機械的なコードでその場しのぎの解決を繰り返してるだけ」
→ 続けて「機械的な処理を機械的に回すだけのハードコードである問題点についてはどうですか」
→ **「LLM化については編集長だけではありません。すべてです」**

## 実測した症状（推測ではない）
- 検索 30 日: 表示 65・クリック **0**。提携 4 件・成果 **0**
- 企画を止める機械ゲートは本番で**発火 0 件**（判定に要る SERP 実データが 28 行・全部同一クラスタ）。スコアの 2/3 が「不明」定数
- 競合本文が届くのは企画工程だけ。**writer には 0 字**。しかも「競合の数値を本文に書くな」と禁止
- 「上位の過半が扱う必須要素」は **19 記事中 18 記事で空**。空振りが無音で、reviewer が自分ででっち上げて採点していた
- エージェント 15 体に対し、出力を却下・書き換える機械地点 **268**（1 体あたり 18）
- ゲートが 1 つも無い唯一の LLM 出力は、**成果物を誰も読まないもの**（障害通知文・822 回中 1 回）

## 根本原因
**指揮者が Python スクリプトだった。** `run_pipeline.py` が企画→案件→競合→取材→執筆→作図→検閲の
固定 6 工程を、どの記事にも・どんな状況でも・必ず 1 回ずつ流す。「取材が薄いからやり直す」「競合を読んで
構成を変える」「今日はやめる」を決める場所が無い。各ワーカーも固定プロンプト→JSON→DB で、
エージェントはスクリプトが渡すと決めたものしか見えない。

**ゲートを足すたびに、その工程の判断が 1 つ減る。** 欠陥 → ゲート追加 → その工程は次から考えなくなる、の繰り返し。

## さらに重い事実
**同じ指摘を 2026-08-18 に受けていた。** `02_select_topic.py` の冒頭に
「機械順の priority_score 選定は不採用 — 人間指示『機械的な処理をするからそうなる』の教訓を初日から反映。
コードは状態機械のみ」と書いてある。**教訓は正しく採用され、3 週間で風化した**（同じファイルに 9/6 で機械ガードが 2 個追加）。
方針・設計原則の文言では止まらない。

## 修正（docs/14_realignment.md）
1. **全役割を LLM 化**（人間決定⑭）。1 役 = `claude -p` セッション + 散文ブリーフ + Read/Write/Bash + 隔離 cwd。
   Python は ①道具（エージェントが自分で呼ぶ CLI）②状態機械（ロック・再開・kill）③3 種のゲートだけ
2. **ゲートを道具に変える**。268 個の検査に溜まった知見は捨てず、壁ではなく計器にする
   （コンプラ検査は writer が執筆中に自分で回して直す。公開直前に法令ゲートとしてもう一度だけ機械が回す）
3. **ゲートに寿命を持たせる**。発火率を週次集計し、連続 0 発火は退役候補（方針では止まらないものは機械でしか止まらない）
4. 移行は 1 役ずつ。第 1 号 x-creator を実装して実走で確かめてから次へ

## 予防ルール
1. **欠陥が出たら「どの役が気づくべきだったか」を先に問う。** 材料が届いていないなら渡す。判断を機械に奪われているなら返す。
   ゲート追加はその次（3 種に該当する時だけ）
2. **機械で塞いでよいのは 3 種**: ①法令・規約 ②不可逆（公開・投稿・削除）③物理的事実（画像が切れている・404・ファイルが無い）。
   品質・面白さ・優劣はエージェントの判断に残す
3. **判定に使う入力が空なら、判定を出さない。** 定数に落として GO を出さない。空だったこと自体を通知する
4. **「順番に流れる工程」を新設しない。** 新しい仕事は「編集長が必要な時に呼ぶ道具」として作る
5. **教訓は風化する前提で、機械（発火率の計測）と直し方のルール（docs/14 §6）に落とす**
