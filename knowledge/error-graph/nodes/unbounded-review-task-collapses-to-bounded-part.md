## 症状

AI組織の知識ベース `domain_knowledge` が**実質「昇格専用」**になっていた。
316件のうち `retired` は**1件だけ**。知見は毎日増えるが、一度 verified になったものは
（意見・目視の印象であっても）全エージェントのプロンプトに注入され続ける。

能力が無かったわけではない:
- 実装側は `update` で `status` を `retired` にできる経路を**元から持っていた**
- エージェント定義にも「鮮度切れのretired化」と**明記されていた**

## 根本原因

**「やってよい」と書いてあるだけでは実行されない。仕事に境界が無いと、
エージェントは境界のある部分だけをやって完了と見なす。**

キュレーターに渡していた材料は `id / 種別 / 状態 / タイトル / 本文80字` の316行。
これは「重複していないか」を見るには足りるが、「これはもう注入すべきでないか」を
判断するには**由来も更新日も無い**。加えて316件を毎回眺める仕事には終わりが無い。

実走で本人の発話が残った（失敗時思考ログの実装で初めて見えた）:

> 新しいファクトシートと自己回顧素材を既存knowledge(300件超)と突き合わせて**重複排除**中です

出力は `"update": []`。見送り理由もすべて「重複のため」。
**境界のある部分（新規分の重複排除）だけをやって終わっていた。**

第1弾の対処（由来と更新日を材料に足す）だけでは変わらなかった — これは実走で確認済み。
材料を足しても、仕事の**形**が無限界のままだったため。

## 修正

1. **注入時に由来を消さない。** `domain_knowledge` の `source` は記録されていたのに
   注入クエリが `SELECT` していなかった。結果、受け取る側には
   「目視の印象」も「週次PDCA実測」も**同じ重みの検証済みナレッジ**として届いていた
   （119件の出典は `visual-inspector（目視）`）。分類も重みづけもせず**出典の文字列をそのまま**見せる
2. **境界のある再点検にする。** 毎回 N件（既定8）だけを「今回の再点検対象」として提示し、
   **全件に verdict（keep/demote/retire）と理由を必ず返させる**。
   `reviewed_at` 列を追加し、点検が古い順にローテーション
3. **選択は機械、判断はエージェント。** 「どれを見せるか」は点検日順で機械が決める
   （内容では選ばない＝何を疑うべきかを機械が決めない）。keep/demote/retire は司書の仕事
4. 理由が空・verdictが不正なものは**適用せず拒否**（触らない）

実走検証: 再点検8件に対し、他の知見を相互参照した実質的な理由つきで8件の判定が返った
（例: 出典ドメインの404報告 dk87 と、その後の生存確認 dk132 を突き合わせて keep）。
`update` も 0→4件に増えた。降格・退役の分岐はLLMを差し替えた決定論テストで確認
（keep→verified / demote→candidate / retire→retired / 不備は拒否して非適用）。

## 予防ルール

- **「やってよい」と書くだけでは実行されない。** 実行してほしい判断は
  **境界のある単位**（今回はこのN件）にして、**全件に答えを返させる**形にする
- **無限界の仕事を渡すと、境界のある部分だけが実行される。** 「全部を見て必要なら直して」は
  実質「新しく来た分だけ見る」になる
- **能力の有無ではなく行使の有無を実測する。** 経路を実装したら
  「実際に使われた件数」をDBで数える（1/316 のような偏りは仕組みの症状）
- **材料から由来を落とさない。** 出典は記録するだけでは足りず、
  **使う側に届くまで**が経路。ただし由来を分類・重みづけするのは渡す側の仕事ではない
- **選択と判断を分ける。** 「どれを検討するか」の絞り込みは機械（機械的な足切り）、
  「どう扱うか」はエージェント（判断）。この線を越えると R18 の判断ハードコードになる
