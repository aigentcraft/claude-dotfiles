## 1. Plan / Context

企業からのメッセージを検知したら、通知を出し、返信案を生成して承認を待つ。
**通知が本体、返信案はおまけ**という原則で、生成の失敗は警告へ劣化させ、
記録を `failed` として残す設計にしてあった。劣化したものは次の巡回で拾い直す。

巡回は企業の営業時間に合わせて 1 日 3 回（8 時・12 時・18 時）。

## 2. Do / The Error

同じ設計から、**性質の違う 2 つの詰まり**が出た。

### ① 復帰経路そのものが無かった（送信失敗）

承認ボタンは押した時点で無効化される。送信が失敗すると
**ボタンも状態も戻らず、完全な手詰まり**になる。

```
[承認] → disableButtons() → 送信 → 失敗 → state='failed'
          ↑ 無効化済み                      ↑ onApprove は awaiting_approval しか受けない
```

1 社が 1 日以上この状態で止まっていた。送信失敗の原因自体はその後修正済みで、
**押し直せれば送れる状態だったのに、押せなかった。**

### ② 復帰経路はあったが、契機が遅すぎた（生成失敗）

18 時の巡回で 2 社から新着。通知は届いたが、生成に使う CLI の一時的な不調で
返信案が両方作れなかった。記録は `failed` として残り、次の巡回で再生成される——
**その次の巡回は翌朝 8 時。14 時間後。**

CLI はその 1 時間後には復旧していた。
**直っているのに、システムはそれを知る機会を持っていなかった。**

## 3. Check / Root Cause

**回復の「有無」は設計したが、「いつ効くか」を設計していなかった。**

- ① は経路が無い。これは見つけやすい欠陥
- ② は経路がある。しかも正しく動く。**動く時刻が遅いだけ**

②が厄介なのは、テストでは通ることだ。巡回を手で 1 回回せば復旧するので、
「自己回復する」という報告は嘘ではない。**再現しないのは時間軸だけ**。

根本には、**回復の周期を主たる仕事の周期に相乗りさせた**判断がある。
巡回が 1 日 3 回なのは「企業の営業時間に合わせ、深夜に通知を飛ばさないため」で、
**回復の速さとは何の関係もない理由**だった。乗る理由が無いものに乗っていた。

## 4. Act / Fix & Prevention

- ① 送信失敗の直後に、同じ返信案を出し直して再承認できるようにした。
  失敗の種類を型（`not-found` / `stale` / `not-reflected`）で返し、
  **`stale`（相手から新着が来ていた）だけは出し直さない**（その案はもう的外れ）
- ② 主たる巡回とは別に、**取り残しの復旧だけを短い間隔で回す**経路を足した。
  スレッドを ID で直接開けるので、受信箱を丸ごと読まずに 1 件ずつ安く試せる

回復を速く回すと、壊れたままの対象に**再試行のたびに課金**しうる。
そこで試行回数で打ち切りつつ、**主たる巡回のたびに回数を戻す**。
打ち切りは「短い周期で課金し続けない」ための制限であって、諦めではない。

### 予防ルール

1. **回復経路は「存在するか」ではなく「いつ効くか」まで設計する。**
   自己回復すると書けた時点で満足しない。*どれだけ待つのか*を数字で言えるか確かめる。
2. **回復の周期を、主たる仕事の周期に安易に相乗りさせない。**
   主たる周期には固有の理由（営業時間・コスト・レート制限）がある。
   その理由が回復にも当てはまるかを別に問う。たいてい当てはまらない。
3. **不可逆操作の UI を無効化したら、失敗時に戻す経路を同時に書く。**
   「押したら無効化」は二重実行を防ぐ正しい設計だが、
   失敗経路を書かないと**成功時だけ正しいシステム**になる。
4. **速い再試行は課金を伴う。** 上限で守りつつ、**上限を戻す契機**も置く。
   戻さない上限は、時間が経つほど静かに諦めていく。
5. **失敗の理由は、人間が見る場所とログの両方に出す。**
   この件では理由を通知先にだけ出しており、運用ログには「誰が失敗したか」しか
   残っていなかった。原因を追うのに別の画面を開かせない。
