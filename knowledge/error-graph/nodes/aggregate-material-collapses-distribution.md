## 1. Plan / Context
ops-auditor は「判断を機械化しない」方針で、機械は生データの整形だけを担い、
何が壊れていて何が仕様かはLLMが毎朝判断する設計（2026-08-23 人間指摘への対応）。
材料は `_dist()` ヘルパーで `GROUP BY` 集計を並べる形で渡している。

## 2. Do / The Error（発覚 2026-09-05・人間が所見の1行を指して確認を求めた）
監査材料のこの1行:

```
- kind=tips status=blocked n=4 last_created=2026-08-31 06:40:41 last_posted=None
```

からLLMが出した所見:

> 「同日生成の4件はblocked状態のまま滞留」

実測すると:
- 4件のうち **3件は2026-08-24生成**（`MAX(created_at)`が8/31なので同日と推測された）
- blocked の article_link 6件は **全件その記事に生きた投稿が存在**（再生成が成功した証拠）
- 再生成上限 `MAX_BLOCKED_PER_ARTICLE=4` に達した記事は **ゼロ** ＝ 止まっている仕事はない
- つまり blocked は「ゲート不合格になった草案の記録」であって滞留ではない

**前日にも同じクラスの欠陥が出ていた**: 同じ材料が `MAX(created_at)`（生成日時）しか
持たず `posted_at`（実投稿）が見えないため、週次生成→数日かけて排出するTipsレーンを
「4日間の機能死」と誤診した（`posted_at` 追加で解消）。

**そして報告側も同じ間違いをした**: Claude が ops-auditor の所見を**検証せずに人間へ転送**し、
「再挑戦も破棄もされない滞留」という誤情報をそのまま伝えた。

## 3. Check / Root Cause
1. **集計は分布を潰す。** `GROUP BY x` + `MAX(ts)` は「代表値1つ」しか渡さない。
   LLMは欠けた分布を**推測で埋め、しかも断定形で書く**（「同日生成の」）
2. **材料に「正常/異常の判別軸」が無い。** blocked の件数だけでは、
   「不採用草案（正常）」と「再生成が止まった（異常）」が区別できない。
   区別に必要な事実（同じ記事に生きた投稿があるか／再生成上限に達したか）が材料に無かった
3. **単調増加する累計を健全性指標に使っていた。** `09_notify` の `blocked_n` は全期間累計で、
   必ず増え続けるため診断価値がない
4. **下流（人間への報告）に検証段が無かった。** LLMエージェントの所見は「観測」ではなく
   「解釈」なのに、そのまま事実として転送された

## 4. Act / Prevention Strategy (Fix)
- **材料に分布を入れる**: `MAX` だけでなく `MIN`（oldest）も出し、「いつからいつまでの何件か」を
  LLMが推測せずに読めるようにした
- **材料に判別軸を入れる**: blocked に `with_live_sibling`（同じ記事に生きた投稿があるか）を追加し、
  さらに「再生成が止まった記事（blocked>=上限）」を別セクションで出して
  **0行なら滞留なし**と読めるようにした。ラベル自体に判別の仕方を書く
- **累計を窓で切る**: `09_notify` の `blocked_n` を直近14日に限定し、文言も
  「blocked累積」→「直近14日のゲート不合格」へ

**予防ルール（横展開可能な一般形）**
1. **LLMに渡す集計材料は、代表値だけでなく分布を含める。**
   `MAX(ts)` を出すなら `MIN(ts)` も出す。1行に潰した瞬間、欠けた部分は推測で埋められる
2. **「その数値が正常か異常か」を判定するのに必要な事実を、材料の側に用意する。**
   判別軸が無いと、LLMは数値の大きさや新しさから物語を作る
3. **単調増加する累計を健全性指標にしない。** 窓を切るか、率にする
4. **エージェントの所見は「観測」ではなく「解釈」。** 人間へ転送する前に、
   根拠となる生データを1回引いて裏を取る。**自分の原理を自分に適用すること**
   （docs/12 原理6「分からないことを分かったことにするな」は、報告する側にも効く）
