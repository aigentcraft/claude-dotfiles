## 症状
記事 20 が毎晩 `06b_preview` の完全性ゲートで落ちて draft に差し戻され、**7 ラウンド同じ 2 本の
壊れた内部リンクで止まり続けた**。ログには毎回同じ 2 行が出るが、誰も直さない。
定時タスクは rc=0（パイプライン自体は正常終了）なので異常には見えない。

```
完全性ゲート不合格 → draft差し戻し:
  ['内部リンク先が存在しない（未公開/slug 違い）: /ja/blog/discord-bot-vps-free-hosting-cost-comparison/', ...]
```

## 根本原因（2 つが噛み合って無限ループになる）

1. **材料が渡っていない。** writer は SKILL.md #8 で「`/ja/blog/{slug}/` 形式で内部リンクを入れる」と
   指示されながら、**公開済み記事の一覧を一度も渡されていなかった**（材料は competitors.md と
   feedback.md だけ）。そこで「ありそうな slug」を自分で作り、さらに本文で
   「無料ホスティング各社の料金体系をさらに詳しく比較した記事も公開しているので」と**存在しない記事を
   紹介した**。リンク切れである以前に読者への嘘。

2. **指摘に宛先が無い。** 06b は指摘を `quality_checks` に `run_id=''` で入れていた。
   04 の `sendback_context` は「直近ラウンドの指摘」を **run_id で束ねて**拾う設計なので、
   空文字の行はどのクエリ分岐にも掛からない。ラベル `【プレビュー機械プローブ】` は用意されていたのに
   **一度も表示されたことがなかった**（P01 は `NOT IN ('H01','E01','P01')` で明示的に除外もされていた）。
   実測: 旧コードで `sendback_context()` を呼ぶと戻り値は空文字列。

つまり「機械は毎晩正しく検出し、正しく記録し、**誰にも渡していなかった**」。

## 修正
- **材料を渡す**: `workers/shared/internal_links.py` に公開済み記事の台帳（`published` / `materials_md`）。
  04 が `materials/internal_links.md` として writer の作業 dir に置く。空なら「張らないこと」と書く。
- **計器を渡す**: `tools/check_links.py` — writer が出す前に自分で回す。判定集合も**文言も**
  06b のゲートと同一にする（違う言葉で言うと本人は同じ指摘だと気づけない）。
- **宛先を与える**: 06b が P01 に `run_id = "preview-" + uuid` を振る。04 は直近の P01 run_id を拾う。
  既存行は migration 017 で**各記事の最新バッチだけ**に鍵を付ける（古い指摘は載せない）。
- **順位**: P01 は `category='Q'` だが好みの指摘ではなく公開を物理的に止める破綻なので C/F と同順に上げた。

## 予防ルール
1. **「エージェントに X をさせる」なら、X に必要な材料が渡っているかを先に実測する。**
   指示（SKILL.md）と材料（work dir のファイル）は別物。指示だけ足すと、LLM は
   もっともらしい嘘で穴を埋める（存在しない slug・存在しない記事の紹介文）。
2. **記録した指摘は「誰がいつ読むか」まで辿ってから完了とする。** DB に入れた ≠ 届いた。
   検出側を書いたら、受け取り側で実際に文字列が現れることをテストで固定する。
3. **空の鍵（`run_id=''`・`''` の外部キー）で行を入れない。** 後から束ね直せない行は、
   検索も除外もできず、静かに孤立する。
4. **同じ差し戻しが 3 ラウンド続いたら「直せていない」ではなく「届いていない」を疑う。**
   ラウンド数が増えるだけで内容が変わらないのは、指摘が読まれていない兆候。

## 同じ調査で出た 2 件（同型）

### 最良版が公開面ゲートを通れないなら、それは最良版ではない
`finalize_exhausted` は差し戻し上限を超えた記事の「スコア最高の版」を復元して人間承認へ回す。
記事 20 の round 4 は score 73・残り Q03 のみで選ばれ続けたが、**その版には壊れたリンクが 2 本あり
06b を絶対に通れなかった**。修復レーンは 1 run 1 回なので往復が遅くなるだけだった。
→ 選定条件に「そもそも公開面に出せる版か（物理）」をスコアより先に置く。
**順位づけの前に足切りを置く** — 上位が全部失格候補なら、順位は意味を持たない。

### 道具は「呼べば動く」ことをテストで固定する
`tools/check_compliance.py`（writer の C 系計器）は `ModuleNotFoundError: No module named '_lib'` で
**一度も動いたことがなかった**。06_review は `from _lib import …` を使い、07_publish は同じ dir に
居るので通るが、tools/ から importlib で読むと sys.path に無い。
単体テストは純関数だけを見ていたので気づけなかった。表示も `check_code` を読んでいて
（実際のキーは `code`）全部 `None` と出ていた。
→ CLI は subprocess で起動し、**例外が出ないことと最終行の 1 行 JSON** を固定する。
中身の判定を検査するテストは、その道具が起動することを保証しない。
