## 1. Plan / Context
kintone ダッシュボードに「残白」（契約済み・未入金の残高）を追加する案件。元データは契約フォロー表の `入金予定日`。

実現可能性調査の段階で、**入金予定日が実績として信頼できるか**を次の方法で検証した:

> 契約フォロー表の金額を「入金予定日の月」で集計し、営業日報の黒契約金額（＝実際に入金された額）と月ごとに突き合わせる

結果は **2026年3月〜8月の6ヶ月すべて差額0円**。これをもって「入金予定日は予定変更のたびに更新されており、実際の入金日として信頼できる」と結論し、`申込日 <= 基準日 かつ 入金予定日 > 基準日` という計算ロジックを確定させた。

## 2. Do / The Error
実装・デプロイ後、敵対的レビューのエージェントが同じデータを独立に測り直して発覚:

| 店 | ダッシュボード表示 | 実際の残白 | 差 |
|---|---|---|---|
| 北見 | 2,065,380円 (23件) | 2,500,810円 (29件) | **−435,430円 (−17%)** |
| 網走 | 140,800円 (3件) | 429,400円 (7件) | **−288,600円 (−67%)** |

個人単位ではさらに悪く、ある担当者は 102,300円 表示に対し実際 390,900円（**−74%**）。

## 3. Check / Root Cause
**突合が「最終的に入金されたレコード」しか対象にしていなかった。**

- 黒契約金額（日報）に現れるのは**入金が完了した**契約だけ。だから「入金予定日で集計 vs 黒契約」の比較対象は、定義上、支払い済みレコードに限定される。
- そのレコード群については確かに `入金予定日 = 実際の入金日` に更新されていた。検証結果自体は正しい。
- しかし**まだ入金されていない延滞レコードは、入金予定日が古いまま放置される**。このグループは突合の母集団に一度も入っていなかった。
- 結果、「入金予定日は信頼できる」という結論を、検証していない母集団（未入金・延滞）にまで無自覚に拡張してしまった。典型的な**生存者バイアス**。

一致が6ヶ月続いたことが確信を強めたが、**何回一致しても、比較していない母集団については何も言えない**。

## 4. Act / Prevention Strategy (Fix)

### 修正
```js
// Before: 支払い済みレコードで検証した前提をそのまま使い、延滞が漏れた
'申込日 <= "' + D + '" and 入金予定日 > "' + D + '"'

// After: 「今も未入金」を OR で加える。延滞・予定日未設定も拾える
'申込日 <= "' + D + '" and (入金予定日 > "' + D + '" or 入金確認済み not in ("済"))'
```
修正後は、アプリ自身が持つ権威ある `残白` フィールド（`IF(入金確認済み="済",0,手数料合計)`）の合計と**担当者別まで完全一致**した。

### 予防策
1. **突合を設計したら「この比較に入らないレコードは何か」を明示的に書き出す**。「全件一致した」ではなく「◯◯という母集団について一致した」と記録する。今回なら「入金済みのレコードについては一致」と書けば、未入金が未検証だと即座に分かった。
2. **状態を持つデータ（済/未済・有効/無効・完了/進行中）を扱うときは、各状態を個別に検証する**。片方の状態だけで取った一致を全体の保証として使わない。
3. **権威ある値がアプリ側にあるなら、まずそれと突き合わせる**。今回は契約フォロー表に `残白` 計算フィールドが最初から存在していた。自作ロジックの検証は、遠回りな代理指標ではなく、この既存フィールドと比較するのが最短かつ確実だった。
4. **仕様が業務定義と食い違うときは実装前に数値で示す**。クライアント指示の式は「ざっくり説明」であり、本人の定義（「契約したけどまだ入金になっていない」）は延滞を含む。指示の文面よりも定義に忠実な実装を、差額の実測とともに提案する。
5. **敵対的レビューには実データへのアクセスを与える**。今回コードだけ読むレビューでは発見できず、ライブデータで測り直したレビュアーが見つけた。
